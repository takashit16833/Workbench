# SadServers

## 概要

AIが意図的に壊した実行可能なサーバー／バックエンド環境を用意し、その障害を自力で調査・復旧することで、バックエンドエンジニアとしての守備範囲を広げる個人的SadServersプロジェクト。

個別のコマンドや製品知識を暗記することよりも、障害に対して次の思考を繰り返せるようになることを重視する。

> 現象 → 仮説 → 観測 → 切り分け → 原因特定 → 修正 → 検証

障害を追う過程で、Linux / Unix、ネットワーク、HTTP、DNS、Reverse Proxy、DB、Redis、Docker、Observability、AWS、将来的にはKubernetesや分散システムなどの知識に自然に触れていく。

また、`ps`、`ss`、`top`、`sed`、`grep`、`find`、`lsof`、`curl`、`dig`、`journalctl` など、Linuxでの調査・運用に使うコマンドについても、問題解決の中で用途と読み方を身につける。

## 役割分担

### AI

- 学習テーマに適した障害シナリオを設計する
- Docker / Linux VM / AWS など、障害を自然に再現できる環境を選ぶ
- 正常系を設計した上で、意図的に障害を仕込む
- 復旧判定用のチェックを用意する
- 解決前は根本原因や正解を不用意に明かさない
- 必要に応じて、答えではなく切り分けにつながるヒントを出す
- 復旧後に障害報告書をレビューし、技術的な背景も解説する

### User

- 現象を確認する
- 仮説を立てる
- コマンド、ログ、設定、メトリクスなどを使って観測する
- 仮説を棄却・更新しながら原因を切り分ける
- 原因を特定して復旧する
- チェックを通して復旧を確認する
- 調査ログをもとに障害報告書を作成する
- AIレビューを受けて必要に応じて修正する

## Workbench と SadServers-Lab の役割

- **Workbench**: 学習・調査・知見の記録を残す Knowledge Base / Control Plane
- **SadServers-Lab**: Docker、VM、Terraform など、実際に壊れた環境を置く Execution Environment

1つの障害シナリオを1つのTaskとして管理し、`SS-0001`、`SS-0002` ... のように採番する。

Taskには、問題文、ゴール、環境へのSource、調査ログ、障害報告書、AIレビューを原則としてまとめて残す。障害報告書そのものは別Taskにせず、その障害対応Taskの成果物として扱う。

## 1シナリオの流れ

1. AIがSadServers-Labに壊れた環境を作る
2. Workbenchに対応するTaskを登録する
3. Userが環境を起動して現象を確認する
4. 仮説・観測・切り分けを調査ログとして残す
5. 原因を特定して修正する
6. 自動チェックで復旧を確認する
7. Userがテンプレートに沿って障害報告書を書く
8. AIが障害報告書をレビューする
9. 必要に応じて修正し、TaskをDoneにする
10. AIが仕込んだ障害の全容と周辺知識を解説する

## 学習方針

最初は、症状が明確で原因が1つの小さな障害から始める。慣れるにつれて、複数サービス、断続障害、性能劣化、複数原因、AWSなどへ徐々に広げる。

重要なのは「このコマンドを知っているか」ではなく、「この現象に対して何を観測すれば次の切り分けができるか」。知らないLinuxコマンドが有効な場面では、AIは必要に応じてコマンドの存在や見方を説明し、単なる答え合わせではなく今後再利用できる知識として定着させる。
