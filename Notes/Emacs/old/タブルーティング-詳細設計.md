# タブルーティング / Browsing History 詳細設計

## このノートについて

基本設計の内容を、実装するときに迷わないくらいまで具体化したノート。

ここでも、厳密さより **「読めばすぐ思い出せる」** ことを優先する。

関数名はまだ候補。実装してみて、もっと素直な名前や形があれば変えてよい。

この設計でいう Tab は `tab-bar` の Tab。
`tab-line` に表示する buffer のタブとは別物。

設計で名前を付けて使う言葉は、
[タブルーティング-用語.md](タブルーティング-用語.md)
にまとめてある。

## まず全体像

今回の中心は、

> **Tab をそれぞれ独立した作業スペースのように見せる**

こと。

ただし、

```text
Tab ≠ Project
Tab ≠ Repository
```

どの Tab に入るかはルーティング関数で決める。

```text
file
 ↓
ルーティング関数を上から試す
 ↓
行き先が決まる
 ↓
そのTabがあれば移動
なければ作る
```

そして Tab ごとに、

```text
buffer
Browsing History
Windowの並び
```

をできるだけ独立して見せる。

## パッケージとしての境界

Tab Routing も `.emacs.d` の内部機能ではなく、独立した Emacs Lisp パッケージとして実装する。

リポジトリ名は、

```text
emacs-tab-router
```

を候補とする。

パッケージ側に置くもの:

```text
Routing Function を順番に試す仕組み
Destination
Tab ID
Tab の検索 / 選択 / 作成
Misc の基本動作
Tab ID と任意の基準ディレクトリの保存 / 取得
Routing の再入防止
Tab Router 自身の ERT
```

`.emacs.d` 側に残すもの:

```text
.org を Org Tab へ送る
Workbench/Tasks を専用 Tab へ送る
どの Routing Function をどの順番で使うか
キーバインド
tab-line / mode-line などの見た目
Browsing History との接続
project.el / Dired / Magit / vterm との接続
```

つまり、

```text
パッケージ
  → Tab Routing の仕組み

.emacs.d
  → 自分の Routing ルールと使い方
```

と分ける。

Browsing History には依存しない。
Browsing History 側からも Tab Router を必須依存にしない。

パッケージとして公開する関数・変数は `tab-router-` を prefix にする。
個人設定用の `my/` prefix はパッケージ内部では使わない。

`use-package` からは package-vc 経由で読み込む想定。

```elisp
(use-package tab-router
  :vc (:url "https://github.com/takashit16833/emacs-tab-router.git"
       :rev :newest))
```

## ファイル構成

パッケージは最初から細かく分割せず、

```text
tab-router.el
```

を中心に始める。

基準ディレクトリの管理などが大きくなり、責務を分けた方が読みやすくなった時だけ別ファイルへ分ける。

Browsing History は別リポジトリの `browsing-history.el` にあり、Tab Router のファイル構成には含めない。

見た目、個人固有の Routing Function、キー設定は `.emacs.d/config/` 側へ置く。

## ルーティング関数

ルーティング関数は、1つの条件だけを見る小さい関数にする。

基本は、

```text
file
 ↓
マッチした → Destination
マッチしない → nil
```

という形。

たとえば `.org` 用なら、

```elisp
(defun my/route-org (file)
  ...)
```

のようなイメージ。

リポジトリなどを単位にするルールでは、root の判定に `project.el` を使ってもよい。
ただし、これは Routing Function の実装方法の1つであって、Tab Router 自体が Project という種類を持つわけではない。

### 順番は設定

ルーティング関数はリストで持つ。

候補:

```elisp
tab-router-functions
```

設定例:

```elisp
(setq tab-router-functions
      '(my/route-workbench-task
        my/route-org
        my/route-project))
```

これは例であって、固定ルールではない。

上から順に試して、最初に Destination を返したところで終わる。

```text
A → nil
B → nil
C → Destination
    ↑
  ここで決定
```

ルールは自由に追加・削除・並べ替えできる。

## Destination

Destination は、ルーティング関数が返す「行き先」。

まずは plist で十分。

```elisp
(:id org
 :name "Org")
```

リポジトリ単位のルールなら、

```elisp
(:id (repo . "/work/foo/")
 :name "foo"
 :directory "/work/foo/")
```

のように、任意で基準ディレクトリを持たせられる。

Org のように基準ディレクトリを固定しない Tab なら、`:directory` は指定しない。

Misc なら、

```elisp
(:id misc
 :name "Misc")
```

`:id` は Tab の同一性を表す値で、Tab Router はその中身を特別扱いしない。

`:directory` は任意で、その Tab に基準ディレクトリを持たせたい場合だけ指定する。

Destination は、

> どの Tab を使いたいか

と、その Tab に必要な最小限の情報を表す。

実際に Tab を選ぶ・作る処理はこの後に分ける。

## Misc

file がどのルーティング関数にもマッチしなかったら Misc。

```text
fileあり
 ↓
全部nil
 ↓
Misc
```

一方、file を持たない普通の buffer は、何もマッチしなければ今の Tab のまま。

```text
fileあり + no match → Misc
fileなし + no match → 何もしない
```

xref など、file を持たない buffer を特別にルーティングしたくなった場合だけ、専用の処理を追加する。

最初から特殊 buffer 全般を Routing 対象にしない。

## Tab ID と Tab の選び方

Tab には表示名とは別に ID を持たせる。

```text
表示名: Org
ID:     org
```

リポジトリ単位のルールなら、

```elisp
(repo . "/work/foo/")
```

のように root を含む一意な ID にしてもよい。

ただし、この `repo` という形は利用側の表現にすぎない。
Tab Router は ID を同一性の比較にだけ使う。

Destination が決まったら、現在の Tab 一覧を見て、

```text
1. 今のTabが同じID
   → そのまま

2. 別のTabに同じIDがある
   → そこへ移動

3. 同じIDがない
   → 新しいTabを作る
```

とする。

表示名が同じでも ID が違えば別 Tab。

旧設定にあった「ID のない同名 Tab を自動で拾う」互換処理は、新構築では入れない。

### Tab の状態を丸ごと作り直さない

Tab ID や基準ディレクトリを保存するために Tab 一覧全体を作り直すようなことはしない。

現在の Tab に、自分たちの情報だけを追加・更新する。

tab-bar が持っている Window 状態や Bufferlo の情報などを壊さないため。

## file を開く前に行き先を確定する

`find-file "src/foo.el"` のような相対パスは少し注意が必要。

Tab を先に切り替えると `default-directory` が変わり、別の `src/foo.el` を開く可能性がある。

なので、

```text
今のdefault-directory
 ↓
開くfileを絶対パスへ確定
 ↓
Routing
 ↓
Tab切り替え
 ↓
そのfileを表示
```

という順番にする。

Routing の判定と、実際に開く file が同じものを見るようにする。

## まず1つの表示経路だけつなぐ

最初から `display-buffer` 全体へ広く advice しない。

Emacs 31.1 には `display-buffer-in-tab` という標準の表示アクションもあるため、Tab へ表示する処理ではまず標準機能で足りる範囲を確認する。
ただし、これだけで `find-file` / `switch-to-buffer` の全経路を扱えるとは限らない。

Emacs では file を開く処理の中で、

```text
find-file
find-file-noselect
pop-to-buffer
display-buffer
```

など、いろいろな関数が関わる。

しかも `display-buffer` は「ユーザーが今見たいもの」以外にも使われる。

なので最初は、

> 普通に current window へ file を開く

という1経路だけつないで実動作を見る。

必要な経路は後から1つずつ増やす。

## Routing の再入を防ぐ

Routing の中から file 表示が呼ばれ、その中でまた Routing が走る可能性がある。

そのため Routing 専用の再入防止フラグを持つ。

ただし、

> Routing 中だから全部無視

のような大きすぎる抑制にはしない。

別 file を正当に開いているケースまで止めないよう、実際の呼び出し経路を見ながら最小限にする。

## Bufferlo とつなぐタイミング

新しい Tab を作った時は、

```text
Tabを作る
 ↓
目的のfileを表示する
 ↓
表示できた
 ↓
Bufferloをそのbufferから始める
```

の順番にする。

Tab 作成直後に `bufferlo-clear` しない。

その時点ではまだ `*scratch*` が current buffer の可能性があるため。

Routing は Bufferlo を直接呼ばず、

> 新しい Tab で目的の表示が成功した

ことだけ通知する。

Bufferlo 側がその通知を受けて初期化する形が分かりやすい。

表示に失敗した時は、成功通知を出さない。

最初から複雑な rollback は作らない。空 Tab が実際に困ると分かってから考える。

## 基準ディレクトリ

Tab は、必要な場合だけ基準ディレクトリを持てるようにする。

Destination の `:directory` がその情報になる。

```elisp
(:id (repo . "/work/foo/")
 :name "foo"
 :directory "/work/foo/")
```

なら、Tab を選択 / 作成した時に `/work/foo/` をその Tab の基準ディレクトリとして保存する。

保存先は Tab の alist に Tab Router 専用のパラメータを追加する形にする。
候補:

```elisp
(tab-router-directory . "/work/foo/")
```

Tab ID と基準ディレクトリは別の情報として扱う。

```text
Tab ID
  → どのTabかを識別する

基準ディレクトリ
  → そのTabで作業する時の基準
```

現在の Tab の基準ディレクトリを取得する公開関数を用意する。
候補:

```elisp
(tab-router-current-directory)
```

基準ディレクトリを持たない Tab では nil を返す。

### buffer の default-directory は変更しない

基準ディレクトリは Tab の状態であって、buffer の `default-directory` ではない。

Tab を切り替えた時に `default-directory` を書き換えない。

同じ `*scratch*` buffer が複数の Tab に表示されても、それぞれの Tab が別の基準ディレクトリを持てるようにするため。

### 基準ディレクトリがない Tab

Org のように複数のリポジトリをまたぐ Tab は、基準ディレクトリを持たなくてよい。

```text
Org Tab
├─ repo-a/foo.org
└─ repo-b/bar.org

基準ディレクトリ: なし
```

この場合、project.el / Dired / Magit / vterm などは通常どおり現在の buffer の状態を基準に動かす。

### project.el との接続

`project.el` は基準ディレクトリを利用する機能の1つとして扱う。

Emacs 31.1 には `project-current-directory-override` があり、`project-current` が Project を探す時に `default-directory` の代わりとして使える。

そのため `.emacs.d` 側では、

```text
明示的な directory 指定あり
  → その指定を優先

既存の project-current-directory-override あり
  → その指定を優先

それ以外 + Tabに基準ディレクトリあり
  → 一時的に project-current-directory-override として使う

Tabに基準ディレクトリなし
  → project.el の通常動作
```

とする。

これにより `*scratch*` のような共有 buffer が current でも、基準ディレクトリを持つ Tab では project 系コマンドをそのディレクトリ基準で使える。

Routing Function が対象 file の所属先を調べる時は、現在の Tab の基準ディレクトリに影響されないよう、

```elisp
(project-current nil target-directory)
```

のように対象 directory を明示する。

### Dired との接続

Dired は表示対象の directory を明示的に渡せる。

そのため個人用コマンドから、

```text
Tabに基準ディレクトリあり
  → dired にその directory を渡す

基準ディレクトリなし
  → 通常の dired
```

とする。

Dired 自体へ advice して `default-directory` を書き換える必要はない。

### Magit との接続

現行の Magit の `magit-status` は DIRECTORY を引数として受け取れる。

そのため `magit-status` 自体へ advice して `default-directory` を書き換えるのではなく、個人用コマンドから、

```text
Tabに基準ディレクトリあり
  → magit-status にその directory を渡す

基準ディレクトリなし
  → 通常の magit-status
```

とする。

### vterm との接続

vterm は Tab ごとに1つの buffer を再利用する。

```text
Tab A → vterm A
Tab B → vterm B
```

新しく vterm を起動する時は、

```text
Tabに基準ディレクトリあり
  → その directory から起動

基準ディレクトリなし
  → 現在の buffer の default-directory から起動
```

とする。

vterm buffer の保持や表示 / 非表示は `.emacs.d` 側の責務とし、Tab Router パッケージは vterm に依存しない。

### TRAMP の基準ディレクトリ

基準ディレクトリはローカルパスに限定しない。
TRAMP のリモートファイル名も Emacs のファイル名として、そのまま保持する。

```text
/ssh:host:/work/foo/
/docker:container:/workspace/foo/
```

Tab Router 側では、これらをローカルパスへ変換したり、保存時に存在確認のためのリモート I/O を行ったりしない。

```text
Tab Router
  → directory文字列を保持するだけ

Dired / project.el / Magit / vterm
  → 実際に利用する時に必要なリモートアクセスを行う
```

これにより、ローカルと TRAMP で Tab Router のデータ構造や API を分けない。

ただし TRAMP 上の `project.el` 探索や Git 操作はリモート I/O を伴うため、性能は実測して確認する。

## Browsing History の利用

Browsing History 本体の設計は、
[Browsing-History-設計.md](Browsing-History-設計.md)
に分ける。

History のデータ構造と履歴操作は Tab / Window に依存しない。

どの単位で History を持つかは設定で切り替える。
最初は `tab` を使う。

```text
browsing-history-current
        ↓
browsing-history-scope
        ↓
   tab / window
```

利用側は Tab や Window を直接調べず、
`browsing-history-current` から現在使う History を受け取る。

`tab` の場合は現在の Tab が持つ History、
`window` の場合は現在の Window が持つ History を返す。

これにより、Tab 単位から Window 単位へ変更しても、
記録処理や back / forward 側は変更しない。

移動前後で scope の所有者が変わった場合は、初期実装ではその移動を1つの History として記録しない。
たとえば Tab A から Routing によって Tab B へ移動しても、Tab B の履歴へ Tab A の Location は入れない。
back / forward も Tab をまたがない。

Window scope を実装する時は、Tab の Window 構成を保存・復元した後も History が残るよう
`window-persistent-parameters` の扱いを決め、統合 ERT で確認する。

Tab 単位で使う間は、Tab を複製した時に同じ History オブジェクトを意図せず共有しないこと、
Tab を閉じたり undo-close した時に壊れないことを確認する。

## どの移動を記録するか

これは Browsing History 本体の責務ではない。

Browsing History は、

> この Location を記録して

と呼ばれたら履歴へ追加するだけ。

どの Emacs コマンドを記録対象にするかは接続側で決める。

旧設定の `my-navigation.el` は、その対象を決める参考として使う。

接続側では、移動前の Location と scope の所有者を覚えてからコマンドを実行する。
成功後に移動先を取得し、移動前後で同じ scope の所有者だった場合だけ History を更新する。

```text
A から B へ移動成功
  ↓
履歴の現在地が A でなければ A を push
  ↓
B を push
```

キャンセル、失敗、同じ Location への移動では何もしない。

最初から広い範囲へ advice せず、必要な移動を1つずつ追加する。

Consult の preview のような、

> 候補をちょっと見ただけ

の動作は記録しない。

また、Browsing History 自身の「戻る / 進む」で発生した移動を、
新しい履歴として再記録しない。

back / forward の復元中は Routing も行わない。
履歴を作った後で Routing の規則が変わっても、復元中の Location を別の Tab へ送り直さない。
Browsing History が復元するのは Location だけで、Window の分割や配置は復元しない。

## Tab Routing と Browsing History は直接つながない

Tab Routing は、

> どの Tab で表示するか

だけを考える。

Browsing History は、

> 現在使う History に対して記録 / 戻る / 進む

だけを考える。

利用側は現在使う Browsing History を取得する関数を通して History を受け取り、
必要な時に Browsing History の操作を呼ぶ。

Tab / Window のどちらに History を置くかは、その取得処理にだけ閉じ込める。

## Misc の見た目

最初は Misc を普通に表示する。

Routing が正しく動いてから、必要なら隠す。

`tab-bar-tabs-function` で Misc を除外しない。

これは描画専用ではなく、Tab の選択など実際の操作にも使われるため。

隠すなら `tab-bar-format` 側など、表示だけを変える。

必要なら内部 API を1か所だけ使う方が、無理に大きな独自描画を作るより分かりやすい場合もある。

## テスト

### 小さい関数

ERT でまず確認しやすいのは、

- ルーティング関数の順番
- 最初にマッチしたものを採用すること
- file の no-match → Misc
- file なしの no-match → 何もしない
- Destination の基準ディレクトリを Tab へ保存できること
- 現在の Tab の基準ディレクトリを取得できること
- 基準ディレクトリなしなら nil になること
- Browsing History の追加 / 戻る / 進むの状態変化

あたり。

### Emacs の状態を使うところ

ここは少数の統合 ERT も書く。

特に、

- 同じ Tab ID を再利用できる
- ID が違えば同名 Tab でも分かれる
- Bufferlo の buffer が Tab ごとに混ざらない
- 表示成功後に Bufferlo が初期化される
- scope が tab の時、Tab A / Tab B が別の Browsing History を使う
- scope が tab の時、同じ Tab の複数 Window では同じ Browsing History を使う
- scope が window の時、Window ごとに別の Browsing History を取得できる
- scope が tab の時、同じ Tab なら別 Repository の file でも同じ Browsing History を使う
- Tab をまたぐ移動で別 Tab の Location が History に混ざらない
- back / forward の復元中に Routing や履歴追加が走らない
- 履歴の端で back / forward が循環しない
- 復元失敗時に idx が変わらない
- 相対パスで正しい file を開く
- `*scratch*` でも基準ディレクトリがある Tab では project.el がその directory を使う
- Dired に基準ディレクトリを明示的に渡せる
- Magit に基準ディレクトリを明示的に渡せる
- vterm が Tab ごとに分かれ、基準ディレクトリから起動する
- TRAMP の基準ディレクトリをローカルパスへ変換せず保持できる
- 基準ディレクトリなしの Tab では各機能が通常動作へ戻る
- 設定再読込で advice / hook が二重にならない

ことを見たい。

UI の見た目まで全部 ERT にしようとはしない。

## 性能

Routing は file を開いたり buffer を切り替えたりするたびに通るので、普段の操作を重くしない。

純粋な判定部分は、

```text
小さいリスト走査
文字列比較
ID比較
```

くらいに留める。

気を付けるのは、

- project.el の探索
- ファイルシステム
- TRAMP
- Tab 一覧
- 外部プロセス

など。

遅く感じたら、先に profiler / benchmark で確認する。

推測でキャッシュを増やさない。

## 起動時の読み込み

数十行程度の自作 Elisp を遅延ロードするために、かえって複雑になるなら普通に `require` してよい。

advice を基本コマンドへ付ける機能は、結局早い段階で必要になる可能性がある。

起動速度は実測して判断する。

Browsing History は小さい自作機能として実装し、不要な外部パッケージ依存を増やさない。

## 実装する順番

一気に全部つながない。


各段階で一度使ってみてから次へ進む。

## まとめ

実装の軸はシンプル。

```text
file / buffer
 ↓
自由に並べたルーティング関数
 ↓
Destination
 ↓
Tabを選ぶ / 作る
```

その Tab の中では、

```text
buffer     → Bufferlo
戻る/進む  → Browsing History
Window     → tab-bar
基準directory
           → 必要なTabだけ保持
           → project.el / Dired / Magit / vterm から利用
```

とする。

全部を自作しない。

全部を抽象化しない。

**標準機能や既存パッケージに任せられるところは任せて、必要な接着部分だけ小さく書く。**

このくらいの軽さを保つ。
