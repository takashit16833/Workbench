## そのまま維持してよい点

- **Tab と Project を同一視しない。** 複数 Repository のファイルを1つの Tab へ集める使い方と整合している。
- **ルーティング関数を順番に試す。** 条件の追加や並べ替えが簡単で、仕組みの本体に個別ルールを増やす必要がない。
- **表示名と Tab ID を分ける。** 同名 Project を区別でき、Tab の名前を変えても行き先の識別を保てる。
- **Tab を変える前に相対パスを確定する。** 行き先の判定と実際に開くファイルが食い違う問題を防げる。
- **履歴を Tab / Window から分離する。** `current` と `ensure-current` を分ける方針も自然。履歴を読むだけで空の履歴を作らずに済む。
- **Bufferlo の初期化を表示成功後に行う。** ソース上も `bufferlo-clear` は現在の buffer を残す処理なので、この順序には根拠がある。
- **広い表示処理へ一度に接続しない。** 少数の経路から始め、実動作を見て増やす方針は妥当。
- **性能改善は実測してから行う。** 最初からキャッシュや大きな仕組みを増やさない判断でよい。

## 先に補足したい点

### 1. 履歴に何をいつ積むか

対象: 履歴設計「挙動」「記録対象」、詳細設計「どの移動を記録するか」

`A → B → C` の例はわかりやすい。ただし、移動元と移動先のどちらを記録すればその例になるのかが書かれていない。

参考に指定された旧 `my-navigation.el` は、移動が成功した後に「移動元」を Better Jumper に記録する。新設計の `idx` は「現在見ている履歴位置」なので、この接続方法をそのまま使えるとは限らない。

たとえば A から B へ移動して A だけを記録した場合、現在地は B でも、履歴内には B がない。最初の back と、その後の forward をどう成立させるかを決める必要がある。

**補足案:** 同じ History の中で移動する場合について、次の例を決める。

| 操作 | 期待する状態の例 |
| --- | --- |
| 履歴なしで A から B へ移動成功 | A と B を残し、現在の履歴位置を B にする。 |
| B から C へ移動成功 | C を追加し、現在の履歴位置を C にする。 |
| back | B へ戻り、現在の履歴位置も B にする。 |
| forward | C へ進み、現在の履歴位置も C にする。 |
| back 後、移動コマンドで別の場所 E へ移動成功 | forward 側を捨てて E を追加する。 |
| キャンセル、失敗、同じ場所への移動 | 履歴と現在の履歴位置を変えない。 |

さらに「記録対象外のカーソル移動をした後の back」で、その直前の位置を forward 用に残すかも決めたい。

履歴本体には、空・1件・最古・最新の場合、連続した同じ場所の扱い、件数上限も必要。Emacs の `ring` を使うなら、0 が最新であり、`ring-ref` は範囲外の添字を循環させる。**ブラウザの back / forward の端では循環させず、呼び出す前に範囲を判定する。**

`ring` と `idx` の初期値、追加後の値、back / forward 後の値を小さな表にすれば、ERT の期待値も決めやすい。

### 2. 移動中に Tab / Window が変わった時の記録先

対象: 履歴設計「History の取得」、詳細設計「Browsing History の利用」

`current` が現在の Tab / Window を見ること自体はよい。ただし、移動コマンドの実行前と実行後では「現在」が違う場合がある。

例: Tab A からファイルを開いた結果、Routing によって Tab B が選ばれる。その後に `push` が `ensure-current` を呼ぶと、Tab B の履歴を取得する。そこへ移動元の位置を渡せば、Tab A の位置が Tab B の履歴へ入る。

Window 単位でも、移動によって選択 Window が変わる場合に同じ問題がある。取得関数を分けるだけでは、この問題は解決しない。

**補足案:** 初期構成では Tab 切り替え自体を back / forward の対象にせず、移動元と移動先の履歴を分ける。Tab B の履歴へ Tab A の位置を追加しない。

具体的には、接続側が移動前の History を保持できる形と、移動後に別の History になった場合の処理を決める。公開 `push` が Location だけを受け取る形のままでも、本体の内部操作に History を明示して渡すことはできる。

これは Routing と履歴を直接結合する提案ではない。移動を記録する側で、どの履歴へ書くかを決めるという話。

### 3. back / forward の表示で Routing が再び走る場合

対象: 詳細設計「Routing の再入を防ぐ」「どの移動を記録するか」「Tab Routing と Browsing History は直接つながない」

履歴自身の移動を再記録しない方針は書かれている。一方、履歴の復元に使うファイル表示が Routing の対象だった場合の扱いは未記載。

たとえば、履歴を作った後でルールを並べ替えると、以前の Location を表示する時に別の Tab へ送られる可能性がある。「履歴は Routing を呼ばない」と書くだけでは、表示関数への advice が間接的に動くことを防げない。

**補足案:** 初期構成では back / forward は実行した Tab の選択 Window に復元し、その復元中は新規記録と Routing を行わない。

Browsing History 本体から Routing の関数を呼ぶ必要はない。接続側で履歴復元中の表示を識別するか、Routing を通らない表示経路を選べばよい。

また、Tab 単位で履歴を共有しても Window の配置は復元しない、という範囲を明記するとよい。Location には Window の情報がないため。

### 4. 戻り先を復元できない場合

対象: 履歴設計「データ構造」「テスト」

marker を優先し、使えなければ file + position を使う方針は妥当。ただし、次の場合の結果が決まっていない。

- buffer を閉じ、marker が位置を指さなくなった。
- ファイルが削除・移動されている。
- 内容が短くなり、保存した位置が末尾を超えている。
- file を持たない buffer の marker が使えなくなった。

**補足案:** 読めるファイルは開き直し、位置は有効な範囲へ収める。削除されたファイルを履歴復元のために新規作成しない。復元できなければ理由を表示し、`idx` は成功時だけ変更する。

`position` をいつ保存・更新するかも必要。marker は編集に追従するが、別に保存した整数の `position` は自動更新されない。「file + position では保存時点の位置へ戻る」でもよいので、保証する範囲を決める。

file なしの Location を初期実装で記録するかも、ここで明記したい。

## 接続する段階で決めればよい点

以下は、ルーティングの判定部分まで止める理由ではない。該当する機能をつなぐ直前に決め、少数の統合 ERT で確認すればよい。

| 項目 | 曖昧さ・確認したいこと | 小さな進め方 |
| --- | --- | --- |
| 最初の表示経路 | 「普通に current window へ file を開く」だけでは、対象の関数と入口が決まらない。 | 最初に対応するコマンドを1つ指定し、other-window / other-frame / バックグラウンドの読み込みは後へ回す。実際の呼び出し経路を確認して接続箇所を選ぶ。 |
| file / buffer の入力 | 説明は file / buffer 対象だが、ルーティング関数の例は file だけ。file なしの buffer をどこで判断するか不明。 | 最初は file を受け取る関数に統一し、buffer の入口で file の有無を判定する、など引数の約束を1つ決める。 |
| 再入と preview | 「最小限に防ぐ」という方針だけでは、どの表示が同じ処理の重複かを判断できない。履歴を抑制しても Routing が preview に反応する可能性は別に残る。 | 1経路で重複がないことを確認し、Consult 接続時に確定・取消・preview を分けて確認する。 |
| Bufferlo への成功通知 | 通知名、渡す情報、対象 Tab / buffer、通知回数が未定。 | 最初の1経路では、表示した buffer と対象 Tab を確認して、新規 Tab の成功時に1回だけ初期化する。一般的な通知基盤は不要。 |
| Tab / History の保存 | Tab は切り替え時に内部データが作り直されるが、独自項目を引き継ぐ処理はある。古い Tab データを保持し続ける方法には注意が必要。 | 取得・保存時に現在の Tab を取り直し、A → B → A で ID と History が残ることを確認する。 |
| Window 単位の保存 | window parameter に置くだけで、Window 配置の保存・復元でも残るとは限らない。 | `window-persistent-parameters` の扱いを決め、Tab 切り替え後の復元と Window 分割を確認する。marker を含む値をセッション間保存へ混ぜない。 |
| Tab の複製・閉じる・undo-close | 履歴設計では複製の扱いを後回しにしている一方、詳細設計では独立性の確認を求めている。Tab ID が重複する場合の扱いも必要。 | 複製 Tab は履歴を空にする、独立したコピーにする、など最低限の方針を決める。閉じた履歴を即時に壊すと undo-close と両立しない点にも注意する。 |
| Project Context | directory 明示時は尊重する方針でよい。既存の `project-current-directory-override` と、root が無効な場合の優先順は未定。 | 明示 directory・既存 override を優先し、Tab root が有効な場合だけ補助する形を検討する。無効時の通常判定への復帰も決める。 |
| ID とパス | ID の比較方法、Project root の末尾 /、相対パスや別名パスの扱いが未定。 | ID は `equal` で比較し、root の表記を揃える案が自然。シンボリックリンクと TRAMP の扱いは採用するルールで決める。 |

Bufferlo が分けるのは buffer の一覧であり、同じファイルの内容や buffer オブジェクトを Tab ごとに複製するわけではない。また、すべての buffer 選択画面が自動的に絞り込まれるとは限らない。利用する切り替えコマンドや tab-line への接続で確認する。

## 読みやすさ

基本設計は読みやすい。目的、例、理由の順で説明されていて、細かい関数名を覚えなくても方針を思い出せる。用語表も、会話上の言い換えを勝手に設計概念へ昇格させないために役立っている。

改善は次の範囲で十分。

1. **詳細設計に操作の期待結果を足す。** 「分離する」「後からつなぐ」という方針の繰り返しを増やすより、上の履歴例や Tab をまたぐ例が役立つ。
2. **「渡された履歴」と公開操作の説明を揃える。** 基本・詳細設計では History を渡して操作するように読める一方、履歴設計では `push` に Location を渡し、現在の History を取得する形。内部操作と利用側の操作の違いを1〜2文で説明すればよい。
3. **似た名前の Tab を短く区別する。** 初めに「この設計の Tab は tab-bar の Tab。tab-line の buffer タブではない」と書くと迷いにくい。
4. **用語は増やさず、身近な説明を添える。** `marker` は「編集で位置がずれても追従する目印」、`scope` は「履歴を分ける単位」と説明できる。
5. **4文書の読む順番を示す。** 基本設計 → 必要に応じて用語表 → 詳細設計 → 履歴設計。履歴の細部は履歴設計だけに置く。

実装順の細かい差は、実装不能になる矛盾ではない。ただし、履歴本体と現在の History の取得を別段階で作ることを明示すると、手順1と後半の Tab 接続の関係がわかりやすくなる。

設計書全体を厳密な仕様書へ書き換える必要はない。

## 実装への進み方

1. 履歴設計へ「最初の移動・端・重複・件数上限・復元失敗」の動作を補足し、履歴本体と ERT を作る。
2. ルーティング関数の順番、Destination、Misc、Tab ID の判定を作る。この部分は現在の方針で着手できる。
3. 最初に接続する表示経路を1つ決め、相対パス、重複実行、取消・失敗、成功通知を確認する。
4. Tab 単位の History を接続する前に、記録先と back / forward 中の Routing の扱いを決める。
5. Bufferlo、Project Context、記録対象コマンドを一つずつつなぐ。Window 単位は、その保存・復元を確認してから対応する。

追加したい ERT は、最初の移動からの back / forward、端で循環しないこと、失敗時に履歴位置が変わらないこと、Tab をまたいでも履歴が混ざらないこと、履歴復元が再 Routing・再記録されないこと。preview と Window 配置の見た目は実際の操作でも確認する。

## 確認した根拠

Emacs の参照先は開発版ソース。利用環境に入っている版との一致は未確認なので、実装時には対象版で確認する。以下は今回読んだソースの参照先であり、実動作の証明ではない。

- [Emacs: ring.el](https://github.com/emacs-mirror/emacs/blob/8899f65f39219410d8b3eb84611071e48348e8bf/lisp/emacs-lisp/ring.el) — `ring-ref` の0は最新。範囲外の添字は循環する。容量を超えると最古の要素を捨てる。
- [Emacs: tab-bar.el](https://github.com/emacs-mirror/emacs/blob/8899f65f39219410d8b3eb84611071e48348e8bf/lisp/tab-bar.el) — Tab 切り替え、独自パラメータの引き継ぎ、新規作成、複製、undo-close の処理を確認。
- [Emacs Lisp Manual: Window Parameters の原稿](https://github.com/emacs-mirror/emacs/blob/8899f65f39219410d8b3eb84611071e48348e8bf/doc/lispref/windows.texi) — 独自 window parameter の保存・復元は `window-persistent-parameters` の指定に依存する。
- [Emacs Lisp Manual: Markers の原稿](https://github.com/emacs-mirror/emacs/blob/8899f65f39219410d8b3eb84611071e48348e8bf/doc/lispref/markers.texi) — marker と整数の保存位置は別のもの。不要な marker の解除にも言及がある。
- [Emacs: project.el](https://github.com/emacs-mirror/emacs/blob/8899f65f39219410d8b3eb84611071e48348e8bf/lisp/progmodes/project.el) — `project-current` は明示 directory を使い、省略時に override または `default-directory` を使う。
- [Bufferlo: bufferlo.el](https://github.com/florommel/bufferlo/blob/1ab597c021ee33511fdaad942cc6dd5ac064f6ba/bufferlo.el) — `bufferlo-clear` は現在の buffer を残して一覧を初期化する。
- [参考指定された旧 my-navigation.el](https://github.com/takashit16833/.emacs.d-cli/blob/main/lisp/my-navigation.el) — 移動成功後に移動元を Better Jumper へ記録する接続を確認。新しい履歴本体への移植時には意味を合わせ直す必要がある。
