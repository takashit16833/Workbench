# タブルーティング / Browsing History 基本設計

## このノートについて

これは厳密な仕様書ではなく、

> 何を作ろうとしていたんだっけ？

をあとからすぐ思い出すためのノート。

細かい API 名より、**何をしたいか / なぜそうするか**を優先する。

この設計でいう Tab は `tab-bar` の Tab。
`tab-line` に表示する buffer のタブとは別物。

読む順番は、

```text
基本設計
  ↓
必要なら用語
  ↓
詳細設計
  ↓
Browsing History の細部
```

くらいでよい。

設計で名前を付けて使う言葉は、
[タブルーティング-用語.md](./タブルーティング-用語.md)
にまとめてある。

## まずやりたいこと

今回やりたいのは、

> **Emacs の Tab を、それぞれ独立した作業スペースのように使う**

こと。

ただし、

```text
Tab ≠ Project
Tab ≠ Repository
```

ここは大事。

どの Tab に入るかはルーティング関数が決める。

たとえば `.org` をまとめるルールなら、

```text
Org Tab
├─ repo-a/docs/foo.org
├─ repo-b/notes/bar.org
└─ ~/memo.org
```

のように、1つの Tab に複数 Repository のファイルが入ってよい。

リポジトリや `project.el` を使った判定も、ルーティング方法の1つにすぎない。

## Tab ごとに分けたいもの

まず分けたいのはこのあたり。

```text
Tab A
├─ 表示する buffer のまとまり
├─ 戻る / 進むの履歴
└─ Window の並び

Tab B
├─ 表示する buffer のまとまり
├─ 戻る / 進むの履歴
└─ Window の並び
```

使えそうなものはなるべく標準機能や既存パッケージに任せる。

| やりたいこと | 第一候補 |
| --- | --- |
| Tab ごとの buffer | Bufferlo |
| 戻る / 進むの履歴 | 自作 Browsing History |
| Window の並び | tab-bar |
| リポジトリなどの所属先判定 | project.el |

足りない接着部分だけ自作する。

## Tab Routing

Tab Routing の仕事はシンプル。

> この file / buffer は、どの Tab で表示する？

を決める。

ルーティング関数は自由に追加・削除・並べ替えできる。

```text
file
 ↓
ルーティング関数 A → マッチしない
 ↓
ルーティング関数 B → マッチした
 ↓
その行き先を使う
```

最初にマッチしたものを採用する。

旧設定では Tasks / Org / Project などのルールを使っていたが、これはあくまで当時の設定例。

今回の仕組みが Tasks / Org / Project に固定されるわけではない。

### Destination

ルーティング関数が返す「行き先」を Destination と呼ぶ。

たとえば、

```elisp
(:id org
 :name "Org")
```

なら Org Tab が行き先。

リポジトリ単位のルールなら、

```elisp
(:id (repo . "/work/foo/")
 :name "foo"
 :directory "/work/foo/")
```

のように、`/work/foo/` を基準ディレクトリとして持たせることもできる。

`:directory` は任意で、基準ディレクトリを持たない Tab なら指定しない。

Destination は「どこへ行くか」と、その Tab に必要な最小限の情報を表す。
実際の Tab 操作は別で行う。

## Misc

file がどのルーティング関数にもマッチしなかったら Misc へ送る。

```text
fileあり
  ↓
どのルーティング関数にもマッチしない
  ↓
Misc
```

Misc は通常のルーティング関数というより、最後の受け皿。

一方で、`*Messages*` などの file を持たない buffer は、何にもマッチしなかったからといって Misc へ送らない。

```text
fileあり + マッチなし  → Misc
fileなし + マッチなし  → 今のTabのまま
```

## Tab ID

Tab の表示名とは別に、プログラム用の ID を持たせる。

```text
表示名: Org
Tab ID: org
```

リポジトリ単位のルールなら、

```elisp
(repo . "/work/foo/")
```

のように root を含む ID も使える。

Tab Router は ID の中身に特別な意味を持たせず、同じ Tab かどうかの判定にだけ使う。

同じ ID の Tab があればそこへ移動し、なければ新しく作る。

同じ名前でも ID が違えば別 Tab として扱う。

## 基準ディレクトリ

Tab は、必要な場合だけ基準ディレクトリを持てるようにする。

たとえばリポジトリ単位の Tab なら、

```text
foo Tab
└─ 基準ディレクトリ: /work/foo/
```

とする。

この基準ディレクトリは buffer の `default-directory` とは別物。
Tab を切り替えるたびに buffer の `default-directory` を書き換えたりはしない。

基準ディレクトリがある Tab では、現在の buffer が `*scratch*` のような共有 buffer でも、

```text
project.el
Magit
vterm
```

などをそのディレクトリ基準で動かせるよう、利用側で接続する。

一方、Org Tab のように1つのディレクトリへ固定できない Tab は、基準ディレクトリを持たなくてよい。

```text
Org Tab
├─ repo-a/foo.org
└─ repo-b/bar.org

基準ディレクトリ: なし
```

その場合は各機能の通常動作に任せ、現在の buffer の `default-directory` などを使う。

`project.el` は基準ディレクトリを利用する機能の1つであって、Tab 自体を Project として扱うわけではない。

## Bufferlo

Bufferlo は今回かなり相性がよい。

やりたいのは、

```text
Tab A → Aで使っているbufferだけ見える
Tab B → Bで使っているbufferだけ見える
```

という状態。

新しい Tab を作った時だけ注意が必要で、

```text
新しいTabを作る
 ↓
目的のfileを表示する
 ↓
表示できた
 ↓
Bufferloをそのbufferから始める
```

という順番にする。

Tab を作った直後に `bufferlo-clear` すると、まだ `*scratch*` しか表示されていない可能性があるため。

## Browsing History

「戻る / 進む」は、自作の Browsing History を使う。

Browsing History 自体は Tab Routing を知らない汎用機能として作る。

今回の Tab 構成では、

```text
Tab A → Browsing History A
Tab B → Browsing History B
```

のように、各 Tab がそれぞれ1つの Browsing History を利用する。

同じ Tab に Window が複数あっても、使う Browsing History は同じ。

Browsing History の構造や振る舞いは、
[Browsing-History-設計.md](./Browsing-History-設計.md)
に分けてまとめる。

## Routing と Browsing History の関係

この2つは別機能として考える。

```text
Tab Routing
  → どのTabで表示するか

Browsing History
  → 現在使う History に対して記録 / 戻る / 進む
```

Browsing History は Tab Routing を呼ばない。

初期実装では Tab をまたぐ移動を1つの Browsing History としてつながない。
back / forward も現在の Tab の中だけで行う。

Tab 固有の使い方は利用側で決める。

## Misc を隠すのは後で

まず Routing を正しく動かす。

Misc を画面上から隠したくなったら、その時に見た目だけ調整する。

`tab-bar-tabs-function` から Misc を除外する方法は使わない。これは表示だけでなく実際の Tab 操作にも影響するため。

## パッケージと個人設定の分け方

Browsing History と Tab Routing は、それぞれ独立した Emacs Lisp パッケージとして作る。

```text
emacs-browsing-history
  → 戻る / 進むの仕組み

emacs-tab-router
  → どの Tab へ表示するか
  → Tab ID と任意の基準ディレクトリを扱う

.emacs.d
  → 自分専用のルール、接続、キー、見た目
  → project.el / Magit / vterm との接続
```

2つのパッケージは互いを必須依存にしない。

たとえば、

```text
.org は Org Tab
Consult の移動を履歴へ入れる
s-[ で back
```

のような「自分の使い方」はパッケージへ入れず、`.emacs.d` に置く。

## コードの作り方

基本は、

```text
Emacsの状態を見る
 ↓
小さい関数で判断する
 ↓
必要な操作をする
```

という形にする。

純粋にできる判断は純粋関数にする。

ただし、純粋関数にするためだけに大きなデータ構造や抽象化を増やさない。

個人用 Emacs 設定なので、分かりやすさを優先する。

## テスト

ERT は、壊れた時に原因を見つけやすいところへ置く。

特に確認したいのは、

- ルーティング関数の順番
- 同じ Tab ID の再利用
- マッチしない file が Misc へ行くこと
- file のない buffer は勝手に Misc へ行かないこと
- Bufferlo の buffer が Tab ごとに分かれること
- 基準ディレクトリを持つ Tab から正しく取得できること
- 基準ディレクトリを持たない Tab では nil になること
- Tab A / Tab B が別の Browsing History を使うこと
- 同じ Tab の複数 Window では同じ Browsing History を使うこと
- 相対パスを開いても、Tab 切り替えのせいで別 file を開かないこと
- 設定を再読込しても advice / hook が二重にならないこと

全部を ERT に押し込まず、UI は実際に触って確認する。

## 実装する順番

一気に作らない。

```text
1. Browsing History 本体を小さく実装 + ERT
2. ルーティング関数の仕組みを作る
3. Destination と Tab ID を使って Tab を選ぶ
4. 普通の file を開く経路へつなぐ
5. Misc を入れる
6. Bufferlo とつなぐ
7. 必要な Tab に基準ディレクトリを持たせる
8. .emacs.d 側で project.el / Magit / vterm とつなぐ
9. Tab ごとに Browsing History を持たせる
10. 記録対象の移動を少しずつ増やす
11. 最後に必要なら Misc の見た目を調整する
```

## まとめ

今回の中心は、

> **Tab をそれぞれ独立した作業スペースのように見せる**

こと。

でも、

```text
Tab ≠ Project
Tab ≠ Repository
```

どの Tab に入るかは自由なルーティング関数で決める。

Tab ごとの buffer は Bufferlo、戻る / 進むは自作 Browsing History、Window は tab-bar に任せる。

必要な Tab だけ基準ディレクトリを持ち、project.el / Magit / vterm などは利用側でその情報を使う。

なるべく Emacs 標準と既存パッケージを使う。ただし Browsing History は今回の使い方に合わせて小さく自作する。
