## 4. すでに実装済みで、基盤として利用できる部分

### private sublibrary

共通ログ基盤`ragscope-logging`は、同一Cabal package内のprivate sublibraryとして分離済み。

大まかな依存方向は、

```text
executable
    ↓
main library
    ↓
private ragscope-logging
```

であり、logging sublibraryからmain libraryへ逆依存しない。

### 用途別Facade

private sublibraryでは、現在次のFacadeが公開されている。

```text
RAGScope.Logging
RAGScope.Logging.EventSpec
RAGScope.Logging.Setup
RAGScope.Logging.Testing
```

ただし`RAGScope.Logging.Setup`は公開枠だけ存在し、実装はまだ空である。

### EventSpecと失敗イベントの不変条件

通常イベント用の生成経路と失敗イベント用の生成経路が分離されている。

特に`failedEventSpec`では、

```text
event = failed
level = error
error 必須
```

という不変条件を同じ生成経路で保証する設計になっている。

### Runtime

現在の`emit`は概ね、

```text
機能固有イベント
  ↓
ToEventSpec
  ↓
最低ログレベル判定
  ↓
event_id / timestamp / component / context 付加
  ↓
LogEvent
  ↓
Sink
```

という責務分離になっている。

最低ログレベル未満の場合は、ID・時刻生成もSink呼び出しも行わず成功として扱う。

### Sink失敗

現在のSink境界は、

```haskell
LogEvent -> IO (Either LoggingFailure ())
```

である。

失敗するSinkを使ったRuntimeテストがあり、`LoggingSinkFailure`が呼び出し元へ返ることを確認している。

失敗したSinkへ同じログ経路で再帰的にログを書き込む処理はない。

### JSON stderr Backend

`RAGScope.Logging.Backend.AesonStderr`には、

- `encodeLogEvent`
    
- AesonによるJSON変換
    
- stderrへの1イベント1行出力
    
- `IOException`から`LoggingSinkFailure`への変換
    

が実装されている。

### Testing Facade

Runtime検査用として、

- 固定EventId
    
- 固定ExecutionId
    
- 固定Clock
    
- memory Sink
    
- failure Sink
    
- テスト用閉じたイベント
    

などが用意されている。

### 現在のRuntimeテスト

現在のtest-suiteは`RuntimeSpec`のみを読み込んでおり、主なテストは3件。

1. 出力対象イベントから`LogEvent`を組み立てる
    
2. 最低ログレベル未満を出力しない
    
3. Sink失敗時に`Left LoggingSinkFailure`を返す

## 5. 現在残っている未完了事項

ここからが次スレッドで対応する本体。

### A. 共通エラー型が未完成

現在の、

```text
ragscope-app/src/RAGScope/Error/Types.hs
```

には`ErrorCategory`しかない。

一方、`エラー設計.md`ではコード内部の共通エラーについて、次の5項目の意味を定義している。

```text
category
code
message
context
cause
```

また、正常結果と失敗結果を型または明示的な結果によって区別することを要求している。

logging側の`LogError`は、構造化ログへ安全に投影するための表現であり、アプリケーション内部の共通エラーそのものではない。

したがって、まず現在設計に従って、

- RAGScopeアプリケーション内部の共通エラー表現
    
- category
    
- code
    
- message
    
- context
    
- cause
    
- 正常/失敗を明示する境界
    

を必要最小限で実装する必要がある。

具体的な機能固有error codeは後続機能の責務なので、RS-0015で先行実装しない。

---

### B. `RAGScope.Logging.Setup`が未実装

現在の`Setup.hs`は実質、

```haskell
module RAGScope.Logging.Setup () where
```

だけである。

一方、現在の`構造化ログ設計.md`では、`RAGScope.Logging.Setup`をcomposition root向けFacadeとし、

- context
    
- minimum log level
    
- EventId生成
    
- Clock
    
- stderr Backend
    

などを組み合わせて実運用用`Logger`を初期化する責務を持たせている。

`Runtime.mkLogger`と`AesonStderr`は内部モジュールなので、このままではcomposition rootが正規の公開Facadeだけを通して本番Loggerを構築できない。

RS-0015完了前に実装が必要。

- optional fieldの省略

これらを自動テストへ追加する必要がある。

#### 固定UUIDの既知問題

JSON Schemaは`event_id`とexecution contextの`execution_id`へUUID v4を要求する。

一方、現在のTesting Facadeは固定値を`UUID.fromWords`で構築しており、現在の値はSchemaのUUID v4パターンへ適合することを確認していない。

Schema適合テスト追加時に、固定EventIdとExecutionIdを**明示的に有効なUUID v4**へ修正し、Schemaで実際に検証すること。

### D. JSON encodingの失敗設計が未確定

`構造化ログ設計.md`には現在も、

> JSON変換に回復可能な失敗経路を設けるか

が「実装で解消する未決定事項」として残っている。

現在のコードでは、

```haskell
encodeLogEvent :: LogEvent -> Value
```

という純粋な変換になっており、各ADTを網羅的にAeson `Value`へ変換している。

一方、Runtimeの`LoggingFailure`には、

```haskell
LoggingEncodingFailure
LoggingSinkFailure
```

の2つがあり、`LoggingEncodingFailure`は現在の実行経路で使用されていない。

現在実装からは、

```text
コード内部の閉じたLogEvent
        ↓
totalな純粋JSON変換
```

とする設計が有力に見えるが、推測で確定しない。

少なくとも、

- `encodeLogEvent`以下に部分関数がないか
    
- すべてのADTを網羅しているか
    
- Aeson APIが回復可能な失敗を返すか
    
- 例外が現実的に発生し得るか
    
- Schema検証と実行時検証の責務が重複しないか
    

を確認したうえで決定する。

もしtotalな純粋変換を採用するなら、少なくとも、

- `LoggingEncodingFailure`の削除
    
- `構造化ログ設計.md`の未決定事項を現在設計へ変更
    
- 失敗時規則の整合
    
- 関連テストの整合
    

を同じ変更で行う。
