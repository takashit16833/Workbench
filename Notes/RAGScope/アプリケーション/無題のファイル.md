### 用語集の配置

`project-docs/RAGScope用語集.md` が一番自然です。

```text
project-docs/
├─ RAGScope概要.md
├─ RAGScope要求定義.md
├─ RAGScope用語集.md
└─ design/
```

`design/`には置きません。用語集は要求・概要・設計のすべてから参照する**RAGScope全体の共通語彙の正本**であり、システム設計そのものではないからです。

現在の文書管理規約では`project-docs/`直下を概要・要求定義としているため、Subtask 2で規約も「概要・要求定義・用語集」へ更新します。

Frontmatterは新しい種類を増やさず、

```yaml
---
note_type: reference
---
```

でよいです。既存の`reference`は「規約、テンプレート、参照資料」に使えるため、用語集にもそのまま適用できます。

### 用語集が正本にするもの

用語集は、

> **RAGScopeで使う正式な名称、その意味、似た概念との違い、基本的な関係**

だけを担当します。

例えば、

```text
評価データ
= 1件の質問、参照回答、回答可能性、正解根拠をまとめたもの
```

までは用語集。

一方、

```text
evaluation_data.id UUID PRIMARY KEY ...
```

のような保存構造は、後続のデータモデル設計・migrationが正本です。

これはSubtask 2自身の完了条件とも一致しています。

## 今回ここで正式化する主要語

まずこの構成で用語集を作るのがよさそうです。

### システム

**RAGScopeアプリケーション**
文書、検索、回答生成、評価、実験の流れを制御するHaskellアプリケーション。

**AI推論サービス**
モデルとTokenizerに依存する計算を提供するPythonサービス。

**RAGScope API**
RAGScopeアプリケーションを外部から利用するためのAPI。

**RAGScope CLI**
RAGScopeアプリケーションをコマンドラインから利用するインターフェース。

ここではPostgreSQLを「コンポーネント」に含めません。現在のアーキテクチャはそう分類していますが、**後続の「システムアーキテクチャを概念モデルと整合させる」Subtaskで修正します**。

---

### 文書

**文書集合**
検索や実験の対象としてまとめて扱う文書の集まり。

**文書**
RAGScopeへ取り込む1件の技術文書。

**文書バージョン**
ある文書の特定時点の内容。同じ文書が更新された場合に、更新前後を区別するための概念。

**分割条件**
文書を文書チャンクへ分割するときに使用した条件。

**文書チャンク**
文書を検索やEmbedding生成に使う単位へ分割したもの。

**検索用データ**
文書チャンクを各検索方式で検索できるようにするため、文書チャンクから生成・保持するデータの総称。

正確な文書集合と文書の関連、ID、保存単位、テーブル構造は**後続のデータモデル設計で決定します**。要求上は文書・文書集合・文書バージョン等の識別が必要です。

---

### 検索と回答生成

**検索**
質問に関係する文書チャンクを取得する処理。

**検索結果**
検索によって得られた順位付きの文書チャンク。

**全文検索**
文書中の語に基づいて文書チャンクを検索する処理。

**dense検索**
質問Embeddingと文書チャンクのEmbeddingの近さを使って検索する処理。

**hybrid検索**
全文検索とdense検索の結果を統合する処理。

**reranking**
検索候補を別の基準またはモデルで再評価して並べ替える処理。

そして、ここは今回変更したいです。

現在の

```text
context
context選択
```

は正式用語にしません。

代わりに、

**回答生成用文書チャンク**
検索候補の中から選ばれ、実際に回答生成モデルへ渡す文書チャンク。

**回答生成用文書チャンク選択**
検索候補から回答生成用文書チャンクを選ぶ処理。

とします。

これなら`ErrorContext`やログの`context`との衝突自体をなくせます。現在の`context`の意味も「実際に回答生成モデルへ渡す文書チャンク」なので、概念は維持したまま名前だけ明確にできます。

**回答生成用プロンプト**
質問、回答生成用文書チャンク、回答生成条件などを組み合わせて作る、回答生成モデルへの入力。

**回答生成用プロンプト構築**
回答生成用プロンプトを作る処理。

**回答**
回答生成モデルが質問に対して生成した回答。

**引用**
回答が根拠として使用した文書を示す構造化された参照。

---

### 評価データ

**評価データセット**
実験・評価に使用する評価データの集まり。

**評価データ**
1件の質問と、その評価に必要な参照回答、回答可能性、正解根拠をまとめたもの。

**質問**
RAGScopeが検索・回答生成・評価の対象とする問い。

**参照回答**
生成した回答を評価する際の基準として評価データが保持する回答。

**回答可能性**
対象文書からその質問へ回答できるかどうかを示す情報。

**正解根拠**
その質問へ正しく回答する根拠として評価データが保持する、元文書内の範囲。

`dev` / `test`の正確な保存方法は**後続のデータモデル設計で決定**します。

---

### 実験

**実験**
指定した文書・評価データ・検索・回答生成・評価などの条件を使ってRAG処理を実行し、その結果を保存・比較する単位。

**実験条件**
1つの実験で使用する文書分割、検索、`reranking`、回答生成、評価などの条件。

**評価データごとの実行結果**
1件の評価データを1つの実験条件で処理した結果。

これは今回、正式名称として確定です。

概念的には、

```text
評価データごとの実行結果
├─ 各検索段階の結果
├─ 回答生成用文書チャンク
├─ 回答生成用プロンプト
├─ 回答
├─ 引用
├─ 評価結果
├─ 処理時間
├─ 状態
└─ エラー
```

です。現在の要求も、1問ごとの検索段階・プロンプト・回答・引用・評価結果・処理時間・状態・エラーを追跡し、詳細結果を保存することを要求しています。

**評価結果**
評価データごとの実行結果を評価した結果。

**実験全体の集計結果**
複数の評価データごとの評価結果を、実験単位で集計したもの。

**実験レポート**
保存済みの実験結果や比較結果を、人が確認できるMarkdown / CSVなどへ出力した成果物。

## 正式用語にしない語

ここも用語集で明確にしたいです。

| 語                    | 扱い                                           |
| -------------------- | -------------------------------------------- |
| `context`            | 使用しない。`回答生成用文書チャンク`を使う                       |
| `source`             | 単独では正式用語にしない。文書、引用、正解根拠など実際の概念名を使う           |
| `実行`                 | 単独では正式用語にしない。`実験`、`評価データごとの実行結果`など対象を明示する    |
| `評価問題`               | 使用せず`評価データ`を使う                               |
| `コーパス`               | 正式名称にはせず`文書集合`を使う                            |
| `ExecutionOutcome`   | Haskell内部型なので用語集へ入れない                        |
| `execution_id`       | 用語集へ入れない。後続の論理契約再設計で存続自体を再検討                 |
| `TraceId` / `SpanId` | 一般仕様の識別子。後続の論理契約再設計でOpenTelemetry採用と追跡単位を再検討 |
| ドメイン参照               | 後続の論理契約再設計で必要性から再検討                          |

これで、Subtask 2の骨格はかなり固まりました。
