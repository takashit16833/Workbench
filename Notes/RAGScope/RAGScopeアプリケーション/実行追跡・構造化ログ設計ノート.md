# 実行追跡・構造化ログ設計ノート

このノートは、実行追跡・構造化ログ設計のうち、比較的変わりにくい前提、責務、用語、Cabal境界を扱う。

実行フロー、Effectの具体化、Applicationでの組み立て、Runtimeの具体形、未確定事項は [[実行追跡・構造化ログ実行設計ノート]] を参照する。全体像は [[RAGScope実行追跡・構造化ログ基盤.canvas]]、静的依存関係は [[実行追跡・構造化ログ静的依存.canvas]]、設計判断の経緯は [[実行追跡・構造化ログ設計日誌]] を参照する。

## 設計前提

- 既存Haskell実装との互換性や既存module構成の維持は設計制約にしない。
- 現在のRAGScope正本の設計・契約を基準とし、Workbenchは実装設計の作業台として使う。
- OpenTelemetryの都合からRAGScopeの公開APIを決めない。
- **1 trace = 利用インターフェースが受け付けた1回のトップレベルな利用者操作**とする。プロセス生存期間やUseCase実行そのものをtrace単位にしない。
- root spanはrouting / command判定、入力変換・検証より前の操作固有処理開始から、利用者操作の結果を確定して操作固有処理から外側へ戻るまでを覆う。
- UseCaseを呼び出した場合、その実行はroot span配下の子spanとする。UseCaseを呼び出さず入力処理等で終了する操作も存在する。
- アプリケーションやサービスの起動・終了など、特定の利用者操作へ属さないライフサイクルは個別traceへ含めない。
- 構造化ログはtraceより広い概念とし、trace外のライフサイクルeventも同じLogging基盤で扱う。
- trace内ログは`TraceId`と`SpanId`を組で持ち、trace外ログは両方を持たない。片方だけの状態を作らない。
- spanの開始・終了を管理する処理と、eventをログとして記録する処理は分ける。
- Feature / UseCaseは`TraceId` / `SpanId`、Logger、OpenTelemetry、Sink、外部出力形式を直接扱わない。
- ObservabilityはLoggingの中間表現を作らない。Feature / Interface / Lifecycle eventから`LogSpec`への変換と`LogRecord`の生成・出力はLogging側の責務とする。
- 複数のlibraryやRuntimeをRAGScope本番環境として接続する処理は、個々のlibraryへ押し込まず`RAGScope.Application.*`側のcompositionへ置く。
- Cabal package / library / moduleの依存関係に循環を作らない。
- Portはmodule名のsuffixではなく設計上の役割を表す語として使う。呼び出し側が必要とする抽象操作を定義し、具体実装を境界の向こう側で差し替える箇所をPortと呼ぶ。

## 利用者操作・UseCase・ライフサイクルの境界

1回の利用者操作全体は、UseCaseを必要な場合だけ内包する。結果の意味も同じ包含関係で扱う。

```text
Process lifecycle
├─ startup / started / stopping / stopped ...
│    └─ 利用者操作外。OperationResultには含めない
│
└─ User Operation × 0..N
     ├─ pre-UseCase processing
     ├─ UseCase（必要な場合）
     │    └─ UseCaseResult
     │         ├─ UseCaseSuccess
     │         └─ UseCaseFailure
     ├─ post-UseCase processing
     └─ OperationResult
          ├─ OperationSuccess
          └─ OperationFailure
```

`UseCaseResult = UseCaseSuccess | UseCaseFailure`は、UseCase実行結果の区分を示す概念表記である。Haskell境界では`Either failure result`を使い、`Right result`を`UseCaseSuccess`、`Left failure`を`UseCaseFailure`として表す。

`UseCaseFailure`は結果区分であり、具体的なfailure型ではない。たとえば`DenseSearchFailure`はdense検索UseCaseが`UseCaseFailure`となった具体的な理由を表す型である。具体的なfailure型は、そのUseCaseを所有するFeatureの`RAGScope.<Feature>.Failure`に置く。Featureはfailure型・event・UseCaseなどの所有単位であり、一般的な結果区分を`FeatureFailure` / `FeatureResult`とは呼ばない。

`OperationResult = OperationSuccess | OperationFailure`は、1回の利用者操作全体の結果区分を示す概念表記である。UseCaseを実行して`UseCaseFailure`となった場合は`OperationFailure`となる。`UseCaseSuccess`だけでは`OperationSuccess`は確定せず、UseCase前後を含む操作固有処理が完了して利用者が依頼した結果が成立したときに`OperationSuccess`となる。UseCaseを呼び出さず、routing / validation等で`OperationFailure`となる場合もある。

Haskellの利用者操作境界は`Either OperationFailure result`で表す。`OperationFailure`はApplication側の共通型であり、`ToErrorType` instanceを持つ具体的なfailure値を1つ保持する。

```haskell
data OperationFailure where
  OperationFailure
    :: ToErrorType failure
    => failure
    -> OperationFailure
```

- UseCaseが`Left failure`を返した場合は、その具体的なfailure値をApplicationで受け取り、UseCase span、失敗ログ、利用者向け結果など必要な処理を行った後、利用者操作も失敗として終了するなら`Left (OperationFailure failure)`を返す。
- routing / command判定 / 入力変換・検証 / UseCase後の結果処理の通常failureもUseCase固有failureへ変換せず、具体型を必要とする処理を終えた後に`OperationFailure failure`として返す。
- `ToErrorType OperationFailure`は`OperationFailure failure`から中のfailure値を取り出して`toErrorType failure`を実行する。
- 利用者操作ごとのfailure ADTや、Input / UseCase / Outputなど処理段階ごとの`OperationFailure` constructorは作らない。
- `OperationFailure`の定義はFeature固有failure型をimportしない。`ragscope-application`は`ToErrorType`のために`RAGScope.ErrorType`をimportし、`ragscope-error`へ直接依存する。
- 同期Exception、非同期Exception、Logging自身のfailureを`OperationResult`へどう反映するかは実行・失敗境界の設計で決める。

## eventの所有とLoggingへの変換

具体的なeventは、その出来事を意味として所有する側が定義する。

```text
Application lifecycle event
  → Application側

CLI / API固有event
  → 各利用インターフェース側

Feature event
  → 各Feature側
```

Logging共通基盤は具体的なevent名、属性、`error_type`を決めない。各eventは`ToLogSpec`によって共通`LogSpec`へ変換する。

```text
owned event
  ↓ ToLogSpec
LogSpec
  ↓ 実行時情報を付加
LogRecord
  ↓
Sink / JSON / SQLite
```

`LogSpec`はevent名、level、message、attributesなどイベントの意味を持つ。timestamp、component、Trace Contextなど実行時に決まる情報は`LogRecord`完成時に加える。

Trace Contextはログ1件に対して「ある / ない」を1つのまとまりとして扱う。Haskell内部型でも独立した`Maybe TraceId`と`Maybe SpanId`で不正な片方だけの状態を作らない方向とする。正確な型定義は実装コードで確定する。

## `ErrorType`とUseCase固有failure

- `ErrorType`と`ToErrorType`は共通local package `ragscope-error`の`RAGScope.ErrorType`に置く。
- 各UseCaseが失敗した具体的な理由を表すfailure型は、そのUseCaseを所有するFeatureの`RAGScope.<Feature>.Failure`に置く。
- `ToErrorType <UseCaseFailureType>` instanceも同じmoduleへ置き、orphanにしない。
- `ToErrorType`はfailure値だけから`ErrorType`を得る純粋な変換であり、LoggingやTracingのContextを要求しない。
- failure型自身には`ToLogSpec`を要求しない。失敗をログへ出す場合は、その失敗を表すFeature eventを使う。
- ユースケース失敗eventはUseCase spanへ関連付ける。同じ具体failureを`OperationFailure failure`として返しただけでは同じ失敗ログをroot側へ重複記録しない。
- `OperationFailure`自身の`ToErrorType` instanceは中のfailure値に`toErrorType`を適用するため、同じ具体failureをUseCase spanとroot spanで観測した場合に同じ`ErrorType`を得る。

## Cabal package構成

現在は次の5 packageを基準にする。

```text
ragscope-app/
  cabal.project

  ragscope/
  ragscope-error/
  ragscope-observability/
  ragscope-logging/
  ragscope-tracing/
```

### `ragscope`

Feature / UseCaseとRAGScope本番用compositionを置く。Feature側とApplication側は依存集合が異なるためprivate libraryを分ける。

```text
ragscope
├─ private: ragscope-features
│  ├─ RAGScope.<Feature>.Event
│  ├─ RAGScope.<Feature>.Failure
│  └─ RAGScope.<Feature>.UseCase
│
└─ private: ragscope-application
   ├─ RAGScope.<Feature>.Logging
   ├─ RAGScope.Application.Execution
   ├─ RAGScope.Application.Observability
   └─ RAGScope.Application.LoggingInstances
```

`ragscope-features`はUseCase固有failureの`ToErrorType` instanceを定義するため`ragscope-error`へ依存する。`ragscope-application`も共通`OperationFailure`のconstructor制約と`ToErrorType OperationFailure` instanceで`RAGScope.ErrorType`を使うため、`ragscope-error`へ直接依存する。

Application lifecycle eventの正確なmodule配置、CLI / API固有処理をどのHaskell componentへ置くか、`OperationFailure`の正確なmodule名は、実際のApplication / interface構成と合わせて確定する。

### `ragscope-error`

```text
ragscope-error
└─ public: main
   └─ RAGScope.ErrorType
      ├─ ErrorType
      └─ ToErrorType
```

Logging、Tracing、Observability、UseCase固有failure、`OperationFailure`のいずれにも所有させない。

### `ragscope-observability`

実行追跡の公開API、Application向けRunner、current spanとspan lifecycleの内部実装を分ける。

```text
ragscope-observability
├─ public: main
│  └─ RAGScope.Observability
├─ public: runtime
│  └─ RAGScope.Observability.Runner
└─ private: internal
   └─ RAGScope.Observability.Internal.*
```

旧案の「RunnerがUseCase呼び出しをroot spanとして包む」という前提は破棄する。Operation root spanを利用インターフェース境界から開始でき、UseCase spanをその子として開始できるAPI構成へ見直す。正確なAPIは [[実行追跡・構造化ログ実行設計ノート]] で詰める。

### `ragscope-logging`

```text
ragscope-logging
├─ public: core
│  └─ RAGScope.Logging
│     └─ ToLogSpec / LogSpec / LogRecord / LogValue
├─ public: main
│  └─ RAGScope.Logging.Write
└─ private: internal
   ├─ RAGScope.Logging.Runtime
   ├─ RAGScope.Logging.Sink
   ├─ RAGScope.Logging.JSON
   └─ RAGScope.Logging.SQLite
```

`RAGScope.Logging.Write`はtrace内外のeventを同じlogging基盤へ渡せる公開入口とする。Trace Contextを引数として必須にする旧候補は見直す。

### `ragscope-tracing`

```text
ragscope-tracing
├─ public: core
│  └─ RAGScope.Tracing.Context
├─ public: main
│  └─ RAGScope.Tracing
│     └─ Tracing Port
└─ public: otel
   └─ RAGScope.Tracing.OpenTelemetry
```

Tracing Portはspan開始・終了・状態更新などの抽象操作をRAGScopeの型で表し、OpenTelemetry固有型を公開境界へ出さない。

## 引き継がない旧前提

- `ExecutionId`でUseCase実行を識別する。
- `1 UseCase = 1 trace`。
- ApplicationがUseCaseを呼ぶ時点でroot spanを開始する。
- UseCase終了後のrouting / response / output処理をtrace外へ置く。
- すべての構造化ログにTrace Contextを必須とする。
- `EventContext`、`OperationName`、通常/失敗イベント直和を共通Loggingの前提にする。
- `Observation`の「全機能結果へ必須ログ1件」を前提にする。
- Feature / UseCaseへLoggerや`TraceId` / `SpanId`を明示的に渡す。
- UseCase実行結果の一般概念を`FeatureResult` / `FeatureFailure`と呼び、Featureという所有単位と結果区分を混在させる。
- 利用者操作ごとに具体failureを列挙した`<Operation>OperationFailure`型を定義する。

## 実行設計で詰める内容

以下は [[実行追跡・構造化ログ実行設計ノート]] で扱う。

- Operation root spanの開始・終了をHaskell APIでどう表すか。
- UseCase spanの開始・終了とFeature内部spanとの親子関係。
- Interface / Application / FeatureからObservability APIをどう利用するか。
- `OperationFailure`の正確なmodule名とconstructor構文。
- 同期Exception / 非同期Exceptionと通常の`OperationFailure`の関係。
- Trace Contextなしのeventを`Logging.Write`へ渡す正確なAPI。
- `LogSpec`から`LogRecord`を完成するRuntime API。
- Logging自身のfailureと`OperationResult`の組み合わせ。
- `Observation`、`Result`、`AppError`を維持・変更・削除するか。
- 各Cabal libraryの`exposed-modules` / `other-modules`と正確な`build-depends`。
