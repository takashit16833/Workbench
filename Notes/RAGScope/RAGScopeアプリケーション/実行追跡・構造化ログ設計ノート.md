## 現在の実装構成候補

Workbenchでは、実装候補を次の5 packageで検討している。これは実装前の候補であり、最終的なpackage / library / module構成はCabal設定とコードで確定する。OpenTelemetry Adapterの所属と公開範囲は正本Ticketで決定済みであり、以下の候補でもその境界を固定する。

```text
ragscope
ragscope-error
ragscope-observability
ragscope-logging
ragscope-tracing
```

`ragscope`ではFeature、Application、OpenTelemetry Adapterで必要な依存が異なるため、private libraryを分ける。

```text
ragscope
├─ ragscope-features
├─ ragscope-application
└─ ragscope-tracing-otel
```

- `ragscope-features`: Featureのevent / failure / UseCaseと`RAGScope.<Feature>.Logging`を置く。`RAGScope.<Feature>.Logging`はFeature eventに対する`ToLogSpec` instanceを定義するためLoggingの公開契約へ依存する。UseCase / Event / FailureはLogging moduleをimportしない。
- `ragscope-application`: 利用インターフェース、Operation実行、本番構成の組み立て、`RAGScope.Application.LoggingInstances`を置く。`LoggingInstances`は本番で必要なFeatureのinstance moduleを読み込み、Feature固有eventから`LogSpec`への変換規則自体はApplicationに置かない。OpenTelemetry SDKへは直接依存せず、`ragscope-tracing-otel`から本番用のTracing Port実装を受け取る。
- `ragscope-tracing-otel`: `RAGScope.Application.Tracing.OpenTelemetry`を置くprivate library。`RAGScope.Tracing`、`RAGScope.Tracing.Context`、OpenTelemetry SDKへ依存してTracing Portを実装する。OpenTelemetry SDKへ直接依存するのはこのlibraryだけとする。
- `ragscope-error`: `RAGScope.ErrorType`を公開する。
- `ragscope-observability`: 利用側が使うObservability API、Operation / child spanを実行するRunner、span lifecycleの内部実装を分ける。
- `ragscope-logging`: 共通のログ型、公開`write` API、Runtime / Sink / JSON / SQLiteを分ける。
- `ragscope-tracing`: `RAGScope.Tracing.Context`を持つpublic `core` libraryと、Tracing Port `RAGScope.Tracing`を持つpublic main libraryだけを公開する。OpenTelemetry具体実装とOpenTelemetry SDK依存は持たない。

正確な依存方向は静的依存図で管理する。同じ依存をこのノートへ一覧として複製しない。

## 実装時の値の流れ

現在検討している共通Logging側の流れは次のとおり。

```text
Feature / Interface / Lifecycle のevent
  ↓ ToLogSpec
LogSpec
  + 実行時情報
  + 任意のTraceContext
  ↓
LogRecord
  ↓
Sink / JSON / SQLite
```

`RAGScope.<Feature>.UseCase`はLogger、TraceId / SpanId、OpenTelemetry SDK、JSON / SQLite表現を直接扱わない。Feature側でLoggingへ依存する`RAGScope.<Feature>.Logging`も、`ToLogSpec` / `LogSpec`の公開契約だけを使い、Logging Runtime、Sink、JSON / SQLite実装へは依存しない。本番環境でObservability / Logging / Tracingを接続する処理はApplication側へ置く。OpenTelemetry SDKを使う具体実装はprivate `ragscope-tracing-otel`へ閉じる。

## 現在の検討地点

正本では、UseCaseとOperationは自身の成功・失敗を結果として返し、観測用表現やログ表現への実変換を必須責務にしない。変換元の型を所有する側は、必要な変換型クラスのinstanceとして変換規則を提供できるが、`toErrorType`や`toLogSpec`などの変換関数を実際に適用するのは、その変換後の表現を必要とする処理である。

Span Statusは公開API設計で引き続き具体化する。現時点の最有力候補は、UseCase境界の`Either failure result`とOperation境界の`Either OperationFailure result`をObservability側が観測し、`Left`を`Error`、`Right`を`Unset`として直接解釈する方法である。現在契約では具体的なfailureやresultの種類ごとにSpan Statusの判定規則を変える必要がないため、`ToSpanStatus`のような専用型クラスは現時点では導入しない。結果型固有の判定が必要になった場合に再検討する。

## 現在未確定の実装事項

次は、正本で実装詳細が確定していないか、コードへ落とす段階で具体化が必要な項目である。

1. `OperationFailure`の正確なmodule名とconstructorの構文。
2. 同期`Exception`をどこで`catch`するか。どの`Exception`型をどの条件で、型で表現したfailureへ変換し、変換しないものをどこで`rethrow`するか。
3. 非同期`Exception`を受けたとき、各spanのscopeでどの後始末を行い、その後どう`rethrow`するか。
4. Operationのroot span / UseCase spanを開始・終了し、各結果をSpan Statusへ反映するObservability公開APIの正確な型とmodule分割。
5. Feature内部spanを開始するAPIと、Feature向けEffectの分割。
6. 現在の`TraceContext`をどこに保持し、並行実行時にどう伝播するか。
7. traceに属するeventと、traceに属さないeventを`RAGScope.Logging.Write`へ渡す公開API。`Maybe TraceContext`を1つのAPIで受けるか、traceあり / traceなしでAPIを分けるか。
8. `LogSpec`から`LogRecord`を構築してSinkへ渡すRuntime APIと、`timestamp` / `component`をどこで付加するか。
9. 利用インターフェース固有eventとApplication lifecycle eventの`ToLogSpec` instanceを置く正確なCabal componentと、それを有効にするimport経路。Feature eventのinstanceは`ragscope-features`の`RAGScope.<Feature>.Logging`へ置くことを正本で確定済み。
10. Logging自身のfailureをOperationの最終結果へどう反映するか。Operation failureと同時に起きた場合に何を返すか。
11. 旧`Observation` / `Result` / `AppError` / `ExecutionFailure`相当を維持・変更・削除する範囲。
12. SQLite投影を置くCabal library、使用するSQLite library、migrationの配置、transaction境界、復元API、往復テスト。

`ErrorType`の具体的な内部表現・値が実装で必要になった場合は、正本と既存コードを確認して別途確定する。

## 次の作業

現在実行中のSubtaskは`RS-0022 subtask logging全体像を設計して公開APIと中核型を実装する`である。このSubtaskでは、上記候補をコードとCabal設定へ落とせるところまで具体化し、Logging / Observability / Tracingの公開APIとLoggingの中核型を実装する。

```text

```
