## 現在の実装構成

全体設計で採用した責務境界は次の5 packageを基本とする。正確なCabal stanzaと実装ファイルは後続実装Subtaskでコード・Cabal設定へ落とす。

```text
ragscope
ragscope-error
ragscope-observability
ragscope-logging
ragscope-tracing
```

`ragscope`ではUseCase、Application、OpenTelemetry Adapterで必要な依存が異なるため、private libraryを分ける。

```text
ragscope
├─ ragscope-use-cases
├─ ragscope-application
└─ ragscope-tracing-otel
```

- `ragscope-use-cases`: UseCase本体・event・failure・ErrorClassification・依存record・`RAGScope.<UseCase>.Logging`を置く。`RAGScope.<UseCase>.Failure`は`ErrorType`へ依存せず、`RAGScope.<UseCase>.ErrorClassification`がfailure型と`RAGScope.ErrorType`を参照して名前付き`ErrorClassifier <UseCase>Failure`を定義する。UseCase本体はClassifierを直接扱わない。
- `ragscope-application`: 利用インターフェースのhandler、Application側の薄い`withOperation`、本番構成の組み立て、共通`OperationFailure`、`operationFailureErrorClassifier`を置く。composition rootはTracingとfailure型ごとのClassifierからObservabilityを作り、`Logger m LogSpec`とUseCase固有の純粋変換を`contramap`で合成してUseCase別Loggerを作る。UseCase依存recordをUseCase実行関数へ適用して依存を閉じ、handlerへ必要な能力だけを渡す。
- `ragscope-tracing-otel`: `RAGScope.Application.Tracing.OpenTelemetry`を置くprivate library。Tracing Port、Trace Context、OpenTelemetry SDKへ依存してTracing Portを実装する。OpenTelemetry SDKへ直接依存するのはこのlibraryだけとする。
- `ragscope-error`: `RAGScope.ErrorType`で`ErrorType`と`ErrorClassifier (..)`を公開する。
- `ragscope-observability`: public main libraryの`RAGScope.Observability`と、composition rootが利用するpublic `runtime` libraryの`RAGScope.Observability.Runtime`だけを持つ。mainはfailure型へ特殊化した`Observability m failure`を公開し、runtimeが`Tracing m`と`ErrorClassifier failure`から値を組み立てる。
- `ragscope-logging`: 公開`Logger m event` / `record` / `Contravariant` instance、共通ログ型、Runtime / Sink / JSON / SQLiteを分ける。Runtime / Sink / 外部表現の正確なmodule名とlibrary内配置はまだ確定していない。
- `ragscope-tracing`: `RAGScope.Tracing.Context`を持つpublic `core` libraryと、`SpanName`・`SpanOutcome`・Tracing Portを持つpublic main libraryを公開する。`Either`、具体failure、Classifier、OpenTelemetry具体実装を持たない。

正確な依存方向は静的依存図で管理する。同じ依存をこのノートへ一覧として複製しない。

## failure・Observability・Tracingの値の流れ

`ToErrorType`型クラスは採用しない。具体failureから`ErrorType`への分類は、failure所有側が名前付き`ErrorClassifier failure`値として提供する。

```text
具体failure
  ├─ 詳細値を保持したままeventへ渡せる
  │    ↓
  │  event -> LogSpec
  │    └─ error_type以外のattributes
  │
  └─ ErrorClassifier failure
       ↓
     ErrorType
```

Classifierで`ErrorType`を得ても、元のfailure値を置き換えない。たとえばfailureが`Int`を保持していれば、その値は具体failureまたは失敗eventからログ属性へ利用できる。

Operation全体では次の組を保持する。

```text
OperationFailure
  ├─ 具体failure値
  └─ ErrorClassifier failure
```

root span用の`operationFailureErrorClassifier`は、保存されたClassifierを保存された同じfailure値へ適用する。

Observability RuntimeがApplication / UseCaseの`Either failure result`を解釈する。

```text
Either failure result
        ↓ Observability Runtime
Right _ ───────────────→ SpanSucceeded
Left failure
  + ErrorClassifier failure
        ↓
SpanFailed ErrorType
        ↓
      Tracing
```

Tracingは`SpanOutcome`だけを扱い、`Either`、具体failure、`OperationFailure`、Classifierを知らない。

## Loggingの値の流れ

```text
UseCase / Interface / Lifecycle のevent
  ↓ Logger m event の record
event -> LogSpec
  ↓
Logger m LogSpec
  ↓ minimumLevel filter
  + timestamp / component
  + current Trace Context（任意）
  ↓
LogRecord
  ↓
Sink / JSON / SQLite
```

採用済みの中核型は、`LogSpec = EventName + LogLevel + Maybe Text + Attributes`、`LogRecord = Timestamp + Component + Maybe TraceContext + LogSpec`とする。`Attributes`は`Map AttributeName AttributeValue`で、`AttributeValue`は`Text` / `Scientific` / `Bool` / array / objectの再帰型とし、`null`相当は持たない。top-level attributesが0件の場合は空`Map`で表し、JSON投影時だけ`attributes` propertyを省略する。

Logging Runtimeはminimum level、`Component`、時刻取得action、current Trace Context取得action、Sinkから`Logger m LogSpec`を作る。`LogLevel`は`Debug < Info < Warn < Error < Fatal`の順で`Ord`を利用し、minimum level未満なら時刻・Trace Contextを取得せずSinkも呼ばない。Application composition rootは`Tracing m`全体ではなく`currentTraceContext` actionだけをRuntimeへ渡し、所有側の`event -> LogSpec`純粋関数を`contramap`で合成してUseCase別`Logger m event`を作る。Sinkは完成済み`LogRecord`だけを受け取り、`m (Either LoggingFailure ())`で具体的な出力・保存境界の成否をRuntimeへ返す。`Left LoggingFailure`は通常Logger / Sinkとは独立した`LoggingFailureReporter`へ1回だけ渡し、本番の最初のReporterはbest-effortにstderrへ直接診断情報を出す。Reporterは診断出力を完遂できなかったことを新たな`LoggingFailure`として同じReporterへ再通知しない。Reporter実行中の同期・非同期Exceptionの扱いはException境界で未決定とする。logging failureの蓄積・保持は現在要件としない。

失敗eventで`error_type`が必要な場合は、`RAGScope.<UseCase>.Logging`が`RAGScope.<UseCase>.ErrorClassification`の同じ名前付きClassifierを利用する。failureの詳細値を他のattributesへ出す処理とは分離する。

`ToLogSpec`型クラス、UseCase eventのorphan instance、`RAGScope.Application.LoggingInstances`、instance読み込み専用の`import ... ()`、Loggingで任意eventを受けるための`RankNTypes`は使用しない。

## 現在の検討地点

以下は正本へ反映済みであり、このSubtask内では採用済み設計として扱う。

- `ErrorClassifier failure`による明示的なfailure分類と、`ToErrorType`型クラスの廃止。
- `RAGScope.ErrorType`は`ErrorClassifier (..)`を公開し、専用の生成関数を設けない。
- UseCase failureとErrorClassification moduleの分離。
- `OperationFailure = 具体failure値 + 対応Classifier`と`operationFailureErrorClassifier`。
- failure詳細値を先に`ErrorType`へ潰さず、失敗eventのattributesへ利用可能な状態を保つ境界。
- `SpanOutcome`と`observeOutcome`によってTracingから`Either`・具体failure・Classifierを除く境界。
- `Observability m failure`と`makeObservability :: Tracing m -> ErrorClassifier failure -> Observability m failure`。
- Loggingの`Logger m event`、`Contravariant`、名前付き`event -> LogSpec`変換。
- UseCase所有の依存recordへ必要な能力だけを渡し、Application全体の`AppEnv`をUseCaseへ渡さない境界。
- Operationは機能固有Application Serviceではなく、1回の利用者操作全体という意味上の境界とする。利用インターフェースのhandlerが操作固有処理を担当し、Application側の薄い`withOperation`がOperation用Observabilityの`withTrace`へその全体を委譲する。
- composition rootはUseCase依存recordをUseCase実行関数へ適用して依存を閉じ、その関数、Operation用Observability、Interface Loggerをhandlerへ必要な能力として渡す。機能固有Operation module、Operation固有依存record、共通Operation Runnerは導入せず、現在は`AppEnv`も導入しない。
- Logging中核型として`EventName`、5値の`LogLevel`、`AttributeName`、再帰的`AttributeValue`、`Attributes`、`Timestamp`、`Component`、`LogSpec`、`LogRecord`の型構造を確定。`Attributes`は空`Map`を許可し`Maybe`にせず、`LogRecord`は`Maybe TraceContext`を一体で保持する。
- Logging Runtimeは`LogLevel`の`Ord`を使うminimum level filterを最初に適用し、通過した`LogSpec`だけへtimestamp / component / current Trace Contextを付加して`LogRecord`を完成する。`Tracing m`全体ではなく`m (Maybe TraceContext)` actionだけを受け取る。
- Sinkは完成済み`LogRecord`だけを受け取り、`m (Either LoggingFailure ())`で具体的な出力・保存境界の成否をRuntimeへ返す。`Left LoggingFailure`は通常Logger / Sinkとは独立した`LoggingFailureReporter`へ1回だけ渡し、本番の最初のReporterはbest-effortにstderrへ直接診断情報を出す。Reporterは診断出力を完遂できなかったことを新たな`LoggingFailure`として同じReporterへ再通知しない。Reporter実行中の同期・非同期Exceptionの扱いはException境界で未決定とする。logging failureの蓄積・保持は現在要件としない。RuntimeはJSON / SQLite固有表現を知らず、SinkはRuntime共通情報を付加しない。
- logging failureを`OperationResult`から分離し、`record`からtyped resultとして返さない境界。

Sink / Logging Runtimeのlogging failureは、独立した`LoggingFailureReporter`へ1回通知し、本番の最初の実装ではbest-effortにstderrへ直接診断する設計まで確定した。現在残っている主要判断は、同期・非同期Exceptionをどの境界で捕捉・変換・再throwするかである。

## 現在未確定の実装事項

1. `OperationFailure`を配置する正確なmodule名。保持構造とClassifierの責務は確定済み。
2. 同期`Exception`をどこで`catch`するか。どの`Exception`型をどの条件でtyped failureへ変換し、変換しないものをどこで`rethrow`するか。
3. 非同期`Exception`を受けたとき、各spanのscopeでどの後始末を行い、その後どう`rethrow`するか。
4. UseCase所有の依存recordの正確な型名・field・module名。UseCaseへApplication全体の`AppEnv`を渡さず、必要な能力だけをこのrecordで受け取る方針は確定済み。
5. `withOperation`を配置する正確なmodule名。公開する意味、型、Operation用Observabilityの`withTrace`へ委譲する責務は確定済み。
6. `EventName`、`AttributeName`、`Component`などのconstructor公開範囲と、文字列表現を検証する構築APIを設けるか。保持する型構造は確定済み。
7. `Logger m LogSpec`を組み立てる正確な関数名・module境界、`minimumLevel`の設定元・既定値。Runtimeの責務と必要な入力能力は確定済み。
8. 利用インターフェース固有eventとApplication lifecycle eventの`event -> LogSpec`純粋関数・必要なClassifierを置く正確なCabal component。
9. `Sink` / `LoggingFailureReporter` / `LoggingFailure`の正確なmodule境界・export範囲と、`LoggingFailure`のconstructor・保持する詳細値。Sinkの型構造、独立Reporter、best-effort direct stderrという診断経路は確定済み。
10. 旧`Observation` / `Result` / `AppError` / `ExecutionFailure`相当を維持・変更・削除する範囲。
11. SQLite投影を置くCabal library、使用するSQLite library、migrationの配置、transaction境界、復元API、往復テスト。
