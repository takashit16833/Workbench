## 現在の実装構成候補

Workbenchでは、実装候補を次の5 packageで検討している。これは実装前の候補であり、最終的なpackage / library / module構成はCabal設定とコードで確定する。OpenTelemetry Adapterの所属と公開範囲は正本Ticketで決定済みであり、以下の候補でもその境界を固定する。

```text
ragscope
ragscope-error
ragscope-observability
ragscope-logging
ragscope-tracing
```

`ragscope`ではFeature、Application、OpenTelemetry Adapterで必要な依存が異なるため、private libraryを分ける。

```text
ragscope
├─ ragscope-features
├─ ragscope-application
└─ ragscope-tracing-otel
```

- `ragscope-features`: Featureのevent / failure / UseCaseと`RAGScope.<Feature>.Logging`を置く。記録箇所は`Logger m <FeatureEvent>`と`record`を利用し、`RAGScope.<Feature>.Logging`はFeature eventから`LogSpec`への名前付き純粋変換を定義する。Logging Runtime、Sink、JSON / SQLite実装はimportしない。
- `ragscope-application`: 利用インターフェース、Operation実行、本番構成の組み立てを置く。composition rootは`Logger m LogSpec`とFeature固有の純粋変換を`contramap`で合成し、Feature別Loggerを組み立てる。`RAGScope.Application.LoggingInstances`は置かない。OpenTelemetry SDKへは直接依存せず、`ragscope-tracing-otel`から本番用のTracing Port実装を受け取る。
- `ragscope-tracing-otel`: `RAGScope.Application.Tracing.OpenTelemetry`を置くprivate library。`RAGScope.Tracing`、`RAGScope.Tracing.Context`、OpenTelemetry SDKへ依存してTracing Portを実装する。OpenTelemetry SDKへ直接依存するのはこのlibraryだけとする。
- `ragscope-error`: `RAGScope.ErrorType`を公開する。
- `ragscope-observability`: public main libraryの`RAGScope.Observability`と、composition rootが利用するpublic `runtime` libraryの`RAGScope.Observability.Runtime`だけを持つ。`internal` libraryや`RAGScope.Observability.Runner`は置かない。
- `ragscope-logging`: 公開`Logger m event` / `record` / `Contravariant` instance、共通ログ型、Runtime / Sink / JSON / SQLiteを分ける。Runtime / Sink / 外部表現の正確なmodule名とlibrary内配置はまだ候補として扱う。
- `ragscope-tracing`: `RAGScope.Tracing.Context`を持つpublic `core` libraryと、Tracing Port `RAGScope.Tracing`を持つpublic main libraryだけを公開する。OpenTelemetry具体実装とOpenTelemetry SDK依存は持たない。

正確な依存方向は静的依存図で管理する。同じ依存をこのノートへ一覧として複製しない。

## 実装時の値の流れ

正本へ反映した共通Logging側の流れは次のとおり。

```text
Feature / Interface / Lifecycle のevent
  ↓ Logger m event の record
event -> LogSpec
  ↓
Logger m LogSpec
  + timestamp / component
  + current Trace Context（任意）
  ↓
LogRecord
  ↓
Sink / JSON / SQLite
```

Logging Runtimeは`Logger m LogSpec`を作る。Application composition rootは、所有側の`event -> LogSpec`純粋関数を`contramap`で合成し、利用側へ`Logger m event`を渡す。利用側は`record logger event`だけを呼び、`LogSpec`、`LogRecord`、Logging Runtime、Sink、JSON / SQLite実装を直接扱わない。

`ToLogSpec`型クラス、Feature eventのorphan instance、`RAGScope.Application.LoggingInstances`、instance読み込み専用の`import ... ()`、Loggingで任意eventを受けるための`RankNTypes`は使用しない。

## 現在の検討地点

Tracing / Observabilityの公開API、Span Statusへの結果反映、current Trace Contextの管理責務、OpenTelemetry Adapterの配置は正本で確定済みであり、このノートでは再検討対象としない。

logging failureは`OperationResult`から分離し、`record`からOperation / Featureへtyped resultとして返さないことを正本へ反映済みである。利用者操作本体が成功していればlogging failureが発生しても`OperationSuccess`を維持し、利用者操作本体が失敗していればloggingの成否にかかわらず操作本体の`OperationFailure`を返す。

現在の全体設計Subtaskで残っている主な判断は、Feature別`Logger m event`の受け渡し方法、`LogSpec` / `LogRecord`の正確な型、Logging Runtime / Sink境界、logging failureをどのLogging内部境界へ通知・保持するかである。

## 現在未確定の実装事項

次は、正本で実装詳細が確定していないか、コードへ落とす段階で具体化が必要な項目である。

1. `OperationFailure`の正確なmodule名とconstructorの構文。
2. 同期`Exception`をどこで`catch`するか。どの`Exception`型をどの条件で、型で表現したfailureへ変換し、変換しないものをどこで`rethrow`するか。
3. 非同期`Exception`を受けたとき、各spanのscopeでどの後始末を行い、その後どう`rethrow`するか。
4. Feature別の`Logger m event`を`AppEnv`へ直接持たせるか、Feature単位の依存recordへまとめるか。
5. `Logger m LogSpec`を組み立て、`LogSpec`から`LogRecord`を構築してSinkへ渡すRuntime APIと、`timestamp` / `component`を付加する正確なmodule境界。
6. 利用インターフェース固有eventとApplication lifecycle eventの`event -> LogSpec`純粋関数を置く正確なCabal component。
7. Sink / Logging Runtimeで発生したlogging failureを、どのLogging内部境界へ通知・保持するか。順序は他の設計依存で前後してよいが、この全体設計Subtaskの完了前に必ず確定する。
8. 旧`Observation` / `Result` / `AppError` / `ExecutionFailure`相当を維持・変更・削除する範囲。
9. SQLite投影を置くCabal library、使用するSQLite library、migrationの配置、transaction境界、復元API、往復テスト。

`ErrorType`の具体的な内部表現・値が実装で必要になった場合は、正本と既存コードを確認して別途確定する。

## 次の作業

現在実行中のSubtaskは`RS-0022 subtask 実行追跡・構造化ログの全体設計を確定する`である。

次は、Feature別Loggerを`AppEnv`へ直接持たせるかFeature単位の依存recordへまとめるかを決める。その後、`LogSpec` / `LogRecord`の正確な型、Logging Runtime / Sink境界を具体化する。logging failureの内部通知・保持先は、それらの境界との依存関係を確認しながら適切な順序で決めるが、このSubtaskを完了する前に必ず確定する。
