## 現在の実装構成候補

現在のWorkBench上の実装候補は、次の5 packageを基準にしている。これは実装前の候補であり、正確なpackage / library / module構成はCabal設定とコードで確定する。

```text
ragscope
ragscope-error
ragscope-observability
ragscope-logging
ragscope-tracing
```

`ragscope`ではFeatureとApplicationで依存集合が異なるため、private libraryを分ける候補としている。

```text
ragscope
├─ ragscope-features
└─ ragscope-application
```

- `ragscope-features`: Feature event / failure / UseCase。Logging / Tracingの具体APIへ依存させない。
- `ragscope-application`: 利用インターフェース、Operation実行、本番composition、Feature eventとLoggingの接続を置く。
- `ragscope-error`: `RAGScope.ErrorType`を公開する。
- `ragscope-observability`: 利用側のObservability API、Operation / child spanを実行するRunner、span lifecycle内部実装を分ける。
- `ragscope-logging`: 共通logging型、公開write API、Runtime / Sink / JSON / SQLiteを分ける。
- `ragscope-tracing`: Trace Context、Tracing Port、OpenTelemetry Adapterを分ける。

正確な依存方向は静的依存図で管理する。同じ依存をこのノートへ一覧として複製しない。

## 実装時の値の流れ

現在検討している共通logging側の流れは次である。

```text
Feature / Interface / Lifecycle event
  ↓ ToLogSpec
LogSpec
  + runtime information
  + optional TraceContext
  ↓
LogRecord
  ↓
Sink / JSON / SQLite
```

Feature / UseCaseはLogger、TraceId / SpanId、OpenTelemetry SDK、JSON / SQLite表現を直接扱わない。本番環境でObservability / Logging / Tracingを接続する処理はApplication側へ置く。

## 現在未確定の実装事項

次は正本で実装詳細が確定していない、またはコードへ落とす必要がある項目である。

1. `OperationFailure`の正確なmodule名とconstructor構文。
2. 同期Exceptionをcatchする場所、typed failureへ変換する具体的なException型・条件、変換しないExceptionの再throw。
3. 非同期Exceptionを受けた各span scopeのcleanupと再throw。
4. Operation root span / UseCase spanを開始・終了するObservability公開APIの正確な型とmodule分割。
5. Feature内部spanを開始するAPIとFeature向けEffectの分割。
6. current Trace Contextの保持方法とconcurrency時の伝播方法。
7. trace内eventとtrace外eventを`RAGScope.Logging.Write`へ渡す公開API。`Maybe TraceContext`を受けるか、traced / untraced APIを分けるか。
8. `LogSpec`から`LogRecord`を構築しSinkへ渡すRuntime APIと、timestamp / componentを付加する場所。
9. `ToLogSpec` orphan instanceを置く正確なCabal componentとimport chain。
10. Logging自身のfailureをOperationの最終結果へどう反映するか。Operation failureと同時に起きた場合に何を返すか。
11. 旧`Observation` / `Result` / `AppError` / `ExecutionFailure`相当を維持・変更・削除する範囲。
12. SQLite投影を実装するlibrary、SQLite library選定、migration配置、transaction境界、復元APIと往復テスト。

`ErrorType`の具体的な内部表現・値が実装で必要になった場合は、正本と既存コードを確認して別途確定する。

## 次の作業

現在実行中のSubtaskは`RS-0022 subtask logging全体像を設計して公開APIと中核型を実装する`である。このSubtaskでは、上記候補をコード・Cabal設定へ落とせる粒度まで確定し、Logging / Observability / Tracingの公開APIとlogging中核型を実装する。

その後の既存Subtaskは次の依存関係で進む。

```text
logging全体像・公開API・中核型
├─ trace・span実装
│    └─ Application実行・失敗境界
└─ JSON・Sink・Schema

Application実行・失敗境界 + JSON・Sink・Schema
└─ 最終整合性
```

正本TicketはSQLite投影・migration・復元・往復検証も完了条件としているが、現在のWorkbenchにはSQLite実装を担当する独立Subtaskがない。SQLite実装へ着手する前に、既存Subtaskへ含めるのか独立Subtaskへ分けるのかを決め、Taskと実branchを一致させる。
