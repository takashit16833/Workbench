## 現在の実装構成

全体設計で採用した責務境界は次の5 packageを基本とする。正確なCabal stanzaと実装ファイルは後続実装Subtaskでコード・Cabal設定へ落とす。

```text
ragscope
ragscope-error
ragscope-observability
ragscope-logging
ragscope-tracing
```

`ragscope`ではUseCase、Application、OpenTelemetry Adapterで必要な依存が異なるため、private libraryを分ける。

```text
ragscope
├─ ragscope-use-cases
├─ ragscope-application
└─ ragscope-tracing-otel
```

- `ragscope-use-cases`: UseCase本体・event・failure・ErrorClassification・依存record・`RAGScope.<UseCase>.Logging`を置く。`RAGScope.<UseCase>.Failure`は`ErrorType`へ依存せず、`RAGScope.<UseCase>.ErrorClassification`がfailure型と`RAGScope.ErrorType`を参照して名前付き`ErrorClassifier <UseCase>Failure`を定義する。UseCase本体はClassifierを直接扱わない。
- `ragscope-application`: 利用インターフェース、Operation実行、本番構成の組み立て、共通`OperationFailure`、`operationFailureErrorClassifier`を置く。composition rootはTracingとfailure型ごとのClassifierからObservabilityを作り、`Logger m LogSpec`とUseCase固有の純粋変換を`contramap`で合成してUseCase別Loggerを作る。
- `ragscope-tracing-otel`: `RAGScope.Application.Tracing.OpenTelemetry`を置くprivate library。Tracing Port、Trace Context、OpenTelemetry SDKへ依存してTracing Portを実装する。OpenTelemetry SDKへ直接依存するのはこのlibraryだけとする。
- `ragscope-error`: `RAGScope.ErrorType`で`ErrorType`と`ErrorClassifier failure`を公開する。
- `ragscope-observability`: public main libraryの`RAGScope.Observability`と、composition rootが利用するpublic `runtime` libraryの`RAGScope.Observability.Runtime`だけを持つ。mainはfailure型へ特殊化した`Observability m failure`を公開し、runtimeが`Tracing m`と`ErrorClassifier failure`から値を組み立てる。
- `ragscope-logging`: 公開`Logger m event` / `record` / `Contravariant` instance、共通ログ型、Runtime / Sink / JSON / SQLiteを分ける。Runtime / Sink / 外部表現の正確なmodule名とlibrary内配置はまだ確定していない。
- `ragscope-tracing`: `RAGScope.Tracing.Context`を持つpublic `core` libraryと、`SpanName`・`SpanOutcome`・Tracing Portを持つpublic main libraryを公開する。`Either`、具体failure、Classifier、OpenTelemetry具体実装を持たない。

正確な依存方向は静的依存図で管理する。同じ依存をこのノートへ一覧として複製しない。

## failure・Observability・Tracingの値の流れ

`ToErrorType`型クラスは採用しない。具体failureから`ErrorType`への分類は、failure所有側が名前付き`ErrorClassifier failure`値として提供する。

```text
具体failure
  ├─ 詳細値を保持したままeventへ渡せる
  │    ↓
  │  event -> LogSpec
  │    └─ error_type以外のattributes
  │
  └─ ErrorClassifier failure
       ↓
     ErrorType
```

Classifierで`ErrorType`を得ても、元のfailure値を置き換えない。たとえばfailureが`Int`を保持していれば、その値は具体failureまたは失敗eventからログ属性へ利用できる。

Operation全体では次の組を保持する。

```text
OperationFailure
  ├─ 具体failure値
  └─ ErrorClassifier failure
```

root span用の`operationFailureErrorClassifier`は、保存されたClassifierを保存された同じfailure値へ適用する。

Observability RuntimeがApplication / UseCaseの`Either failure result`を解釈する。

```text
Either failure result
        ↓ Observability Runtime
Right _ ───────────────→ SpanSucceeded
Left failure
  + ErrorClassifier failure
        ↓
SpanFailed ErrorType
        ↓
      Tracing
```

Tracingは`SpanOutcome`だけを扱い、`Either`、具体failure、`OperationFailure`、Classifierを知らない。

## Loggingの値の流れ

```text
UseCase / Interface / Lifecycle のevent
  ↓ Logger m event の record
event -> LogSpec
  ↓
Logger m LogSpec
  + timestamp / component
  + current Trace Context（任意）
  ↓
LogRecord
  ↓
Sink / JSON / SQLite
```

Logging Runtimeは`Logger m LogSpec`を作る。Application composition rootは、所有側の`event -> LogSpec`純粋関数を`contramap`で合成してUseCase別`Logger m event`を作り、UseCase向け`Observability m failure`や他の能力とともにUseCase所有の依存recordへまとめて渡す。

失敗eventで`error_type`が必要な場合は、`RAGScope.<UseCase>.Logging`が`RAGScope.<UseCase>.ErrorClassification`の同じ名前付きClassifierを利用する。failureの詳細値を他のattributesへ出す処理とは分離する。

`ToLogSpec`型クラス、UseCase eventのorphan instance、`RAGScope.Application.LoggingInstances`、instance読み込み専用の`import ... ()`、Loggingで任意eventを受けるための`RankNTypes`は使用しない。

## 現在の検討地点

以下は正本へ反映済みであり、このSubtask内では採用済み設計として扱う。

- `ErrorClassifier failure`による明示的なfailure分類と、`ToErrorType`型クラスの廃止。
- UseCase failureとErrorClassification moduleの分離。
- `OperationFailure = 具体failure値 + 対応Classifier`と`operationFailureErrorClassifier`。
- failure詳細値を先に`ErrorType`へ潰さず、失敗eventのattributesへ利用可能な状態を保つ境界。
- `SpanOutcome`と`observeOutcome`によってTracingから`Either`・具体failure・Classifierを除く境界。
- `Observability m failure`と`makeObservability :: Tracing m -> ErrorClassifier failure -> Observability m failure`。
- Loggingの`Logger m event`、`Contravariant`、名前付き`event -> LogSpec`変換。
- UseCase所有の依存recordへ必要な能力だけを渡し、Application全体の`AppEnv`をUseCaseへ渡さない境界。
- logging failureを`OperationResult`から分離し、`record`からtyped resultとして返さない境界。

現在の全体設計Subtaskで残っている主な判断は、Operation側の依存をどの型でまとめるか、`LogSpec` / `LogRecord`の正確な型、Logging Runtime / Sink境界、logging failureをどのLogging内部境界へ通知・保持するかである。

## 現在未確定の実装事項

1. `OperationFailure`を配置する正確なmodule名。保持構造とClassifierの責務は確定済み。
2. 同期`Exception`をどこで`catch`するか。どの`Exception`型をどの条件でtyped failureへ変換し、変換しないものをどこで`rethrow`するか。
3. 非同期`Exception`を受けたとき、各spanのscopeでどの後始末を行い、その後どう`rethrow`するか。
4. UseCase所有の依存recordの正確な型名・field・module名。UseCaseへApplication全体の`AppEnv`を渡さず、必要な能力だけをこのrecordで受け取る方針は確定済み。
5. Operation側で必要な依存を個別引数、Operation単位の依存record、その他のどの形で表すか。Application全体の長寿命環境として`AppEnv`を導入するかどうかも、この論点と実際のApplication実行構造を確認して判断する。
6. `Logger m LogSpec`を組み立て、`LogSpec`から`LogRecord`を構築してSinkへ渡すRuntime APIと、`timestamp` / `component`を付加する正確なmodule境界。
7. 利用インターフェース固有eventとApplication lifecycle eventの`event -> LogSpec`純粋関数・必要なClassifierを置く正確なCabal component。
8. Sink / Logging Runtimeで発生したlogging failureを、どのLogging内部境界へ通知・保持するか。
9. 旧`Observation` / `Result` / `AppError` / `ExecutionFailure`相当を維持・変更・削除する範囲。
10. SQLite投影を置くCabal library、使用するSQLite library、migrationの配置、transaction境界、復元API、往復テスト。

## 次の作業
