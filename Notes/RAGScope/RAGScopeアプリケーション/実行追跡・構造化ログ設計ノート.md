# 実行追跡・構造化ログ設計ノート

このノートは、実行追跡・構造化ログ設計のうち、比較的変わりにくい前提、責務、用語、Cabal境界を扱う。

実行フロー、Effectの具体化、Applicationでの組み立て、Runtimeの具体形、未確定事項は [[実行追跡・構造化ログ実行設計ノート]] を参照する。Cabal package / library / module同士の静的依存関係は [[実行追跡・構造化ログ静的依存.canvas]] を参照する。設計中に見つかった問題と判断の経緯は [[実行追跡・構造化ログ設計日誌]] に残す。

## 設計前提

- 既存Haskell実装との互換性や既存module構成の維持は設計制約にしない。
- 現在の設計・契約を正として、実装はほぼゼロから組み直す。
- 旧実装は設計アイデアの参照元として扱う。
- OpenTelemetryの都合からRAGScopeの公開APIを決めない。
- `trace` / `span`は、現在どの処理の中にいるかを表す実行コンテキストとして扱う。
- spanの開始・終了を管理する処理と、eventをログとして記録する処理は分ける。
- Feature / UseCaseは`TraceId` / `SpanId`、Logger、OpenTelemetry、Sink、外部出力形式を直接扱わない。
- ObservabilityはLoggingの中間表現を作らない。`LogSpec`への変換と`LogRecord`の生成・出力はLogging側の責務とする。
- 複数のlibraryやRuntimeをRAGScope本番環境として接続する処理は、個々のlibraryへ押し込まず`RAGScope.Application.*`へ置く。
- Cabal package / library / moduleの依存関係に循環を作らない。
- moduleの責務とFacade / Port / Adapterの境界を先に決め、そのうえで禁止依存をCabal componentの`build-depends`で機械的に制約する。
- Portはmodule名のsuffixではなく設計上の役割を表す語として使う。呼び出し側が必要とする抽象操作を定義し、具体実装を境界の向こう側で差し替える箇所をPortと呼ぶ。単なる公開APIを一律にPortとは呼ばない。
- packageは大きな責務のまとまりとして使い、同じpackage内で依存集合や公開範囲が異なる部分はpublic / private libraryへ分ける。
- packageを分ける前に、同じ禁止依存をlibrary境界だけで表現できないか確認する。
- 「このmoduleからは使わない」という運用上の注意だけで守れる状態を最終形にせず、依存禁止に設計上の意味がある場合は可能な限りimport自体を不可能にする。

## Cabal package構成

現在は次の5 packageを基準にする。

```text
ragscope-app/
  cabal.project

  ragscope/
    ragscope.cabal

  ragscope-error/
    ragscope-error.cabal

  ragscope-observability/
    ragscope-observability.cabal

  ragscope-logging/
    ragscope-logging.cabal

  ragscope-tracing/
    ragscope-tracing.cabal
```

packageごとの役割は次のとおりである。

- **`ragscope`**: Feature / UseCaseとRAGScope本番用の組み立てを置く。Feature側とApplication側は依存集合が異なるため、2つのprivate libraryへ分ける。
- **`ragscope-error`**: RAGScope全体で共有する失敗理由`ErrorType`と、失敗値から`ErrorType`へ変換する純粋契約`ToErrorType`を置く。Feature failure、Logging、Tracing、Observabilityのいずれにも所有させない。
- **`ragscope-observability`**: Feature向けObservability API、Application向けRunner、current spanとspan lifecycleの内部実装をまとめる。API / Runner / Internalは別libraryにする。
- **`ragscope-logging`**: Logging契約、公開入口、Logging Runtime / Sink / JSON / SQLiteをまとめる。契約と公開入口はpublic library、内部実装はprivate libraryにする。
- **`ragscope-tracing`**: `TraceContext`などの純粋型、Tracing Port、OpenTelemetry Adapterをまとめる。3つは依存集合が異なるため別public libraryにする。

この分割は別repository化やHackageへの外部公開を意味しない。1つの`cabal.project`から5つのlocal packageとしてまとめて開発・buildする。

package数を増やすこと自体は目的にしない。packageはApplication本体、共通失敗理由、Observability、Logging、Tracingという大きな責務の境界に使い、その内側の依存制約はlibrary単位の`build-depends`で表す。

## package / library / module境界

Cabal上の境界は次の3段階で考える。

```text
Cabal package
└─ library
   └─ Haskell module
```

- **package境界**: 大きな責務のまとまりを分ける。
- **library境界**: componentごとに`build-depends`とpublic / privateを分け、許可するimportを制約する。
- **module境界**: Facade / Port / Adapter / Internalなどの責務を表し、`exposed-modules` / `other-modules`で利用側へ見せるmoduleを制約する。

静的依存Canvasでは、packageを外側のgroup、libraryをその内側のgroup、moduleをnodeとして表す。

### ragscope

DAG最上位の`ragscope`は他packageから依存されないためpublic libraryを持たず、2つのprivate named libraryへ分ける。

```text
ragscope
├─ private: ragscope-features
│  ├─ RAGScope.<Feature>.Event
│  ├─ RAGScope.<Feature>.Failure
│  └─ RAGScope.<Feature>.UseCase
│
└─ private: ragscope-application
   ├─ RAGScope.<Feature>.Logging
   ├─ RAGScope.Application.Execution
   ├─ RAGScope.Application.Observability
   └─ RAGScope.Application.LoggingInstances
```

`RAGScope.<Feature>.Failure`はFeature固有のUseCase failure型を定義し、その型に対する`ToErrorType` instanceも同じmoduleへ置く。instanceをfailure型の定義moduleへ置くことでorphanにしない。

`ragscope-features`はFeature / UseCaseが必要とする依存だけを持つ。`RAGScope.<Feature>.Failure`のため`ragscope-error`へ、Observabilityのため`ragscope-observability`のmain libraryへ依存する。Observability runtime、Logging、Tracingのlibraryへは依存させない。

`ragscope-application`は`ragscope-features`へ依存し、本番用の組み立てに必要な次のpublic libraryを利用できる。

```text
ragscope-observability
ragscope-observability:runtime
ragscope-logging
ragscope-logging:core
ragscope-tracing
ragscope-tracing:core
ragscope-tracing:otel
```

`RAGScope.<Feature>.Logging`はFeature event型と`ToLogSpec`の両方を使うため`ragscope-application`へ置き、Logging依存を`ragscope-features`へ持ち込まない。ユースケース失敗ログもFeature固有eventとして表し、他のFeature eventと同じ`ToLogSpec <FeatureEvent>`の経路で`LogSpec`へ変換する。具体的な失敗event constructorと保持値はFeature設計・実装で確定する。

### ragscope-error

`ragscope-error`は共有失敗理由の純粋契約だけを公開する。

```text
ragscope-error
└─ public: main
   └─ RAGScope.ErrorType
      ├─ ErrorType
      └─ ToErrorType
```

`ErrorType`は構造化ログの`error_type`とspanに関連付ける同じ失敗理由をHaskellで表す値である。`ToErrorType`は失敗値だけから対応する`ErrorType`を一意に得る純粋な変換契約であり、Logging、Tracing、Observability、Applicationの実行Contextを要求しない。

`ragscope-error`にはFeature固有failure、例外処理、Logging、Tracing、Runtimeを置かない。`ErrorType`の内部表現は未確定である。

### ragscope-observability

ObservabilityはFeature向けAPI、Application向けRunner、内部Runtimeを同一packageの別libraryへ分ける。

```text
ragscope-observability
├─ public: main
│  └─ RAGScope.Observability
│     └─ Feature向けEffect API
│
├─ public: runtime
│  └─ RAGScope.Observability.Runner
│     └─ Application向けFacade
│
└─ private: internal
   └─ RAGScope.Observability.Internal.*
      └─ current span保持、root / child span lifecycle
```

`ragscope-features`はmainだけへ依存するため、RunnerやInternalをimportできない。

`ragscope-application`はmainと`runtime`へ依存する。`internal`はprivateなので別packageのApplicationから直接依存できない。

`runtime`は`internal`を使い、Runnerに必要な操作だけを公開する。Runnerが`TraceContext`を公開型として使うため`ragscope-tracing:core`へ、`ToErrorType failure => failure`を受け取る失敗反映境界を持つため`ragscope-error`へ依存する。

`internal`はObservability main、Tracing Port、Tracing core、`ragscope-error`へ依存する。Runnerで変換済みの`ErrorType`とcurrent spanを組み合わせてTracing Portへspan状態更新を要求する。LoggingとOpenTelemetry Adapterには依存しない。

### ragscope-logging

Loggingは契約、公開入口、内部Runtimeを同一packageの別libraryへ分ける。

```text
ragscope-logging
├─ public: core
│  └─ RAGScope.Logging
│     └─ ToLogSpec / LogSpec / LogRecord / LogValue
│
├─ public: main
│  └─ RAGScope.Logging.Write
│     └─ event + TraceContextを受け取る公開入口
│
└─ private: internal
   ├─ RAGScope.Logging.Runtime
   ├─ RAGScope.Logging.Sink
   ├─ RAGScope.Logging.JSON
   └─ RAGScope.Logging.SQLite
```

`core`はIO / JSON / SQLiteへ依存しない。`LogRecord`が追跡情報を持つため`ragscope-tracing:core`へ依存する。ユースケース失敗eventの`error_type`をどの値から`ToLogSpec`で得るかはまだ未確定であり、Logging側のどのCabal componentが`ragscope-error`へ直接依存するかも、その具体形と合わせて確定する。

mainは`core`とprivate `internal`を使う。`RAGScope.Logging.Write`が`toLogSpec`を呼び、`LogSpec`をInternal Runtimeへ渡す。

`internal`はLogging coreとTracing coreへ依存し、JSON / SQLite Adapterのために`aeson`とSQLite libraryを利用する。ApplicationからInternal moduleを直接使わせない。

JSON / SQLiteだけをさらに別private libraryへ分けて外部依存を狭める必要があるかは、Logging Runtimeの具体的な組み立てを決める段階で再確認する。

### ragscope-tracing

Tracingは純粋型、Port、OpenTelemetry Adapterを同一packageの別public libraryへ分ける。

```text
ragscope-tracing
├─ public: core
│  └─ RAGScope.Tracing.Context
│     └─ TraceId / SpanId / TraceContext
│
├─ public: main
│  └─ RAGScope.Tracing
│     └─ Tracing Port
│
└─ public: otel
   └─ RAGScope.Tracing.OpenTelemetry
      └─ production Adapter
         ↓
      OpenTelemetry SDK
```

mainは`core`と`ragscope-error`へ依存する。Tracing Portはspan開始・終了・状態更新などの抽象操作をRAGScopeの型で表し、spanへ失敗理由を設定する操作では`ErrorType`を受け取る。

`otel`はmainと`core`へ依存し、OpenTelemetry SDKを利用する。Observability Internalはmainと`core`だけへ依存するため、OpenTelemetry SDKを直接importできない。

`otel`は`ragscope-application`から本番用Adapterとして使うためpublic libraryにする。

## 採用する概念と責務

- **Observability Effect API**: `RAGScope.Observability`。Feature / UseCaseから見える観測能力。`emit`はFeature eventが起きたことの宣言として扱い、Logging固有の制約やRuntime APIを出さない。単なる公開APIを広くPortと呼ばない方針に合わせ、Observability Portとは呼ばない。
- **Observability Runner**: `RAGScope.Observability.Runner`。ApplicationからObservability Runtimeを使うためのFacade。root span付き実行、current `TraceContext`取得、current spanへの状態反映などApplicationに必要な操作だけを公開する。失敗値からspanへ失敗理由を反映する公開境界では`ToErrorType failure => failure`を受け取り、Runner内で`toErrorType`を適用して下位層へ`ErrorType`を渡す。
- **Observability Internal Runtime**: `RAGScope.Observability.Internal.*`。current span保持、root / child spanのlifecycle、親spanへの復元を実装し、Tracing Portへspan操作を要求する。LoggingとOpenTelemetry Adapterは知らない。
- **Application Observability**: `RAGScope.Application.Observability`。本番でObservability / Logging / Tracingをつなぐ。productionの`MonadObservability` instanceを持ち、Runnerから現在の`TraceContext`を取得してeventとともにLoggingの公開入口へ渡す。本番用Tracing Adapterもここで選ぶ。
- **Tracing Port**: `RAGScope.Tracing`。Observability Internal Runtimeが要求できるspan操作をRAGScopeの型で定義する。具体的なOpenTelemetry APIは公開契約へ出さず、`RAGScope.Tracing.OpenTelemetry`から実装を差し替えられる境界なのでPortと呼ぶ。`Port`はmodule suffixにはしない。
- **OpenTelemetry Tracing Adapter**: `RAGScope.Tracing.OpenTelemetry`。Tracing PortをOpenTelemetryで実装する。
- **Tracing Core**: `RAGScope.Tracing.Context`。`TraceId` / `SpanId` / `TraceContext`などの純粋な追跡値を定義する。
- **ErrorType**: `RAGScope.ErrorType`。LoggingとTracingで共有するRAGScopeの失敗理由を表す値。Logging専用型でもTracing専用型でもない。
- **Feature event**: Feature / UseCaseで「何が起きたか」を表す機能固有の値。`emit`へ渡す。これ自体はログ1件ではない。UseCaseの失敗を表すログもFeature eventの値として表す。
- **UseCase failure**: 各UseCaseが失敗時に返す理由を表す機能固有の型。UseCase境界では`Either <UseCaseFailure> <Result>`の`Left`として返す。dense検索では`DenseSearchFailure`を使う。各constructorはその失敗をApplicationが扱うために必要な情報だけを保持できる。型と`ToErrorType` instanceは`RAGScope.<Feature>.Failure`へ置く。
- **ToErrorType**: `RAGScope.ErrorType`で定義する、失敗値だけから共通`ErrorType`を一意に得る型クラス。`toErrorType`は失敗値だけを受け取り、Applicationの実行状況など追加Contextを要求しない。UseCase failureは対応するinstanceを必ず持つ。UseCase外のfailureも、そのfailureを扱う境界で`ErrorType`が必要と決まった場合に同じ契約を利用できる。`ToErrorType`を適用すること自体は、そのfailureを構造化ログへ記録することや`trace` / `span`で追跡することを意味しない。
- **Feature Logging**: Feature eventを構造化ログへ記録する意味へ写す。`ToLogSpec <FeatureEvent>`を定義する。Cabal上は`ragscope-application`へ置く。
- **Application Logging Instances**: `RAGScope.Application.LoggingInstances`。productionで使用するFeature Logging moduleを`import ... ()`で集め、Feature固有の`ToLogSpec` instanceへimport chainを作る。
- **LogSpec**: event名、level、message、attributesなど、Feature側で意味を確定した共通表現。timestamp、component、`TraceId` / `SpanId`など実行時情報はまだ持たない。
- **LogRecord**: `LogSpec`へ実行時情報を加えた、完成済みの構造化ログ1件。
- **Logging Write**: `RAGScope.Logging.Write`。`ToLogSpec a`を満たす値と現在の`TraceContext`を受け取り、`toLogSpec`で`LogSpec`へ変換した後、Logging Runtimeへ渡す。Logging subsystemの公開APIであり、現在設計ではLogging Portとは呼ばない。
- **Logging Runtime**: `LogSpec`へtimestamp、component、`TraceId` / `SpanId`などを加えて`LogRecord`を完成し、Sinkへ渡す。
- **Sink**: 完成した`LogRecord`の出力先・保持先を表す差し替え可能な境界。
- **JSON Encoder**: `LogRecord`を外部出力用JSONへ変換する部分。
- **SQLite Projection**: `LogRecord`をSQLite表現へ投影し、SQLiteから同じ論理情報へ復元する部分。

Observability Effectのevent発生操作は次の形を採用する。

```haskell
class Monad m => MonadObservability event m where
  emit :: event -> m ()
```

UseCaseは例えば`MonadObservability SearchEvent m`だけを要求し、`ToLogSpec SearchEvent`は要求しない。productionでは`RAGScope.Application.Observability`に置く具体的な`m`のinstanceが`ToLogSpec event`を追加制約として要求する。ただし、そのinstance自身は`toLogSpec`を呼ばず、Observability Runnerから現在の`TraceContext`を取得してeventとともに`RAGScope.Logging.Write`へ渡す。

testではLoggingへ渡さずFeature eventそのものを保持するinstanceを持てる。

`withSpan`も`RAGScope.Observability`からUseCaseへ提供するが、`MonadObservability`の同じclassへ含めるか、正確な引数型をどうするかは実行設計で詰める。

## eventからLogRecordまでの意味

基本のデータモデルは次のとおり。

```text
Feature event
  ↓ production MonadObservability instance
event + 現在のTraceContext
  ↓ RAGScope.Logging.Write
ToLogSpecでLogSpecへ変換
  ↓
LogSpec
  ↓ Logging Runtimeで実行時情報を加える
LogRecord
  ↓
Sink / 外部表現
```

- **1 `LogRecord` = 1件の構造化ログ**。
- 1 `LogRecord`は1つのeventが起きた事実を記録する。
- Feature固有のevent名、level、message、attributesはFeature Loggingの`ToLogSpec` instanceで決める。
- UseCaseの失敗を表すログもFeature固有eventとしてこの経路へ流す。検索機能なら`SearchEvent`のユースケース失敗を表すconstructorを使う。
- 共通Loggingは具体的なFeature event型を知らず、`ToLogSpec`を満たす値として受け取る。
- `LogSpec`はLogging側で生成し、Observabilityへ渡さない。
- `LogRecord`自体はJSON / SQLiteなどの外部形式に依存しない。

## 外部表現

`LogRecord`はRAGScope内部で扱うログ1件の共通表現であり、外部へ出すときに各形式へ変換する。

```text
LogRecord
  ├─ JSON
  └─ SQLite
```

JSON / SQLiteの正確な形式は正本リポジトリの各Contract / Schema / 設計書を正とする。

RS-0022ではHaskellのJSON変換とstderr出力に加え、SQLiteへの投影・復元も実装する。同じ`LogRecord`から性質の異なる2つの外部表現を実装し、JSONまたはSQLite固有の都合が共通モデルへ出ていないことを検証する。SQLiteを本番Sinkとして採用するためのdatabase file配置、rotation、保持期間、同時書き込み、index、bufferingなどの運用設計は対象外とする。

## 旧実装から採用する考え方

- 1 `LogRecord` = 1イベント。
- Feature側がFeature event型を定義する。
- Feature固有の意味から共通logging表現への変換内容はFeature側で定義する。
- `ToLogSpec`を使う処理自体はLogging側に置き、Observabilityに`LogSpec`を扱わせない。
- UseCaseの`emit`はログ出力命令ではなく、event発生の宣言として扱う。
- `LogRecord`を組み立てる処理と、出力・保持するSinkを分ける。
- 本番Sink、memory Sink、失敗を再現するSinkなどを差し替えられるようにする。
- 共通Loggingの中核型はIOやJSON / SQLite形式に依存させない。
- 内部実装はpackage / library / module境界で利用側から隠し、必要なAPIだけを公開する。

旧コード互換のためではなく、現在契約にも自然に適合する場合だけ採用する。

## 引き継がない前提

- `ExecutionId`: UseCase実行の識別はTraceIdが担う。
- `EventId`: 現在契約から必要性を説明できなければ持たない。
- `EventContext`: ログイベント専用Contextを前提にせず、現在の実行コンテキストからtrace / spanへ関連付ける。
- `OperationName`: 処理単位はspan側で扱い、eventは起きた出来事へ集中する。
- `EventSpec`: 新設計では`LogSpec`を使う。
- `LogEvent`: 完成したログ1件には`LogRecord`を使う。
- 通常イベント用と失敗イベント用で別々の仕組みを持つことを前提にしない。
- `LogError`というLogging専用の失敗型が必要だとは前提にしない。
- `Observation`の「全機能結果へ必須ログ1件」を前提にしない。
- Feature / UseCaseへLoggerや`TraceId` / `SpanId`を明示的に渡す設計は採用しない。
- Observability Runtimeが`event`を`LogSpec`へ変換したり、`LogSpec`をLogging Runtimeへ中継したりする設計は採用しない。
- Observability InternalからOpenTelemetry Adapterを直接importする設計は採用しない。

## 設計中の内容

以下は [[実行追跡・構造化ログ実行設計ノート]] で管理する。

- `main` → `Application.Execution` → `Application.Observability` → `Observability.Runner` → Internal Runtime → UseCaseの実行構成
- root / child spanの開始・終了と現在spanの切り替え
- `withSpan`の正確なtypeclass配置・API
- `RAGScope.Observability.Runner`の正確な公開APIと`Internal.*`の具体module分割
- `RAGScope.Tracing` Portの具体形と`RAGScope.Tracing.OpenTelemetry` Adapterの注入方法
- production / test Runtimeと具体的な`m`の組み立て
- `Application.Observability`と`Application.LoggingInstances`の正確な公開範囲・API
- `RAGScope.Logging.Write`とLogging Runtimeの正確な関数分割・型
- `ErrorType`の内部表現
- ユースケース失敗を表すFeature eventの正確なconstructorと保持値、およびLogging側で`ErrorType`を必要とする具体的なcomponent / 依存方向
- Loggingの`internal`をJSON / SQLite Adapterごとに追加library分割する必要があるか
- その他の未確定事項
