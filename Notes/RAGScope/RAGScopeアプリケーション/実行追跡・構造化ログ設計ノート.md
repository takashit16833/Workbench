## 現在の実装構成候補

Workbenchでは、実装候補を次の5 packageで検討している。これは実装前の候補であり、最終的なpackage / library / module構成はCabal設定とコードで確定する。OpenTelemetry Adapterの所属と公開範囲は正本Ticketで決定済みであり、以下の候補でもその境界を固定する。

```text
ragscope
ragscope-error
ragscope-observability
ragscope-logging
ragscope-tracing
```

`ragscope`ではFeature、Application、OpenTelemetry Adapterで必要な依存が異なるため、private libraryを分ける。

```text
ragscope
├─ ragscope-features
├─ ragscope-application
└─ ragscope-tracing-otel
```

- `ragscope-features`: Featureのevent / failure / UseCaseと`RAGScope.<Feature>.Logging`を置く。記録箇所は`Logger m <FeatureEvent>`と`record`を利用し、`RAGScope.<Feature>.Logging`はFeature eventから`LogSpec`への名前付き純粋変換を定義する。Logging Runtime、Sink、JSON / SQLite実装はimportしない。
- `ragscope-application`: 利用インターフェース、Operation実行、本番構成の組み立てを置く。composition rootは`Logger m LogSpec`とFeature固有の純粋変換を`contramap`で合成し、Feature別Loggerを組み立てる。`RAGScope.Application.LoggingInstances`は置かない。OpenTelemetry SDKへは直接依存せず、`ragscope-tracing-otel`から本番用のTracing Port実装を受け取る。
- `ragscope-tracing-otel`: `RAGScope.Application.Tracing.OpenTelemetry`を置くprivate library。`RAGScope.Tracing`、`RAGScope.Tracing.Context`、OpenTelemetry SDKへ依存してTracing Portを実装する。OpenTelemetry SDKへ直接依存するのはこのlibraryだけとする。
- `ragscope-error`: `RAGScope.ErrorType`を公開する。
- `ragscope-observability`: 利用側が使うObservability API、Operation / child spanを実行するRunner、span lifecycleの内部実装を分ける。
- `ragscope-logging`: 公開`Logger m event` / `record` / `Contravariant` instance、共通ログ型、Runtime / Sink / JSON / SQLiteを分ける。
- `ragscope-tracing`: `RAGScope.Tracing.Context`を持つpublic `core` libraryと、Tracing Port `RAGScope.Tracing`を持つpublic main libraryだけを公開する。OpenTelemetry具体実装とOpenTelemetry SDK依存は持たない。

正確な依存方向は静的依存図で管理する。同じ依存をこのノートへ一覧として複製しない。

## 実装時の値の流れ

正本へ反映した共通Logging側の流れは次のとおり。

```text
Feature / Interface / Lifecycle のevent
  ↓ Logger m event の record
event -> LogSpec
  ↓
Logger m LogSpec
  + timestamp / component
  + current Trace Context（任意）
  ↓
LogRecord
  ↓
Sink / JSON / SQLite
```

Logging Runtimeは`Logger m LogSpec`を作る。Application composition rootは、所有側の`event -> LogSpec`純粋関数を`contramap`で合成し、利用側へ`Logger m event`を渡す。利用側は`record logger event`だけを呼び、`LogSpec`、`LogRecord`、Logging Runtime、Sink、JSON / SQLite実装を直接扱わない。

`ToLogSpec`型クラス、Feature eventのorphan instance、`RAGScope.Application.LoggingInstances`、instance読み込み専用の`import ... ()`、Loggingで任意eventを受けるための`RankNTypes`は使用しない。

## 現在の検討地点

正本では、UseCaseとOperationは自身の成功・失敗を結果として返し、観測用表現やログ表現への実変換を必須責務にしない。failure型の所有側は`ToErrorType` instanceを、event所有側は`event -> LogSpec`の名前付き純粋関数を提供する。`toErrorType`は観測用`ErrorType`を必要とする処理が適用し、event変換はcomposition rootが`contramap`でLoggerへ組み込む。

Span Statusは公開API設計で引き続き具体化する。現時点の最有力候補は、UseCase境界の`Either failure result`とOperation境界の`Either OperationFailure result`をObservability側が観測し、`Left`を`Error`、`Right`を`Unset`として直接解釈する方法である。現在契約では具体的なfailureやresultの種類ごとにSpan Statusの判定規則を変える必要がないため、`ToSpanStatus`のような専用型クラスは現時点では導入しない。結果型固有の判定が必要になった場合に再検討する。

Observabilityの利用側では、新しいトップレベルな利用者操作の`trace`を開始するscopeと、開始済み`trace`内へ`span`を追加するscopeを分ける。現時点では前者を`withTrace`、後者を`withSpan`と呼ぶ。Operation境界が`withTrace`を使い、その内側のApplication / Featureは`withSpan`を使う。`withSpan`は開始済み`trace`の中で使い、現在の`trace`がない場合に暗黙に新しいroot `span`を開始しない。

利用側は`TraceId`や`SpanId`を受け取ったり`withSpan`へ渡したりしない。現在のtrace / span状態はTracingの具体実装側が管理し、`withSpan`で作るspanの親はそのcurrent spanから決定する。`withTrace` / `withSpan`の正確な型・module分割と、それらを実現するTracing Portの最小APIは引き続き設計する。

## 現在未確定の実装事項

次は、正本で実装詳細が確定していないか、コードへ落とす段階で具体化が必要な項目である。

1. `OperationFailure`の正確なmodule名とconstructorの構文。
2. 同期`Exception`をどこで`catch`するか。どの`Exception`型をどの条件で、型で表現したfailureへ変換し、変換しないものをどこで`rethrow`するか。
3. 非同期`Exception`を受けたとき、各spanのscopeでどの後始末を行い、その後どう`rethrow`するか。
4. `withTrace` / `withSpan`の正確な型とmodule分割、およびOperation / UseCaseの結果をSpan Statusへ反映するObservability APIの構成。
5. `withSpan`をFeature向けEffectとしてどう公開し、開始済み`trace`がない不正な利用を実装上どう扱うか。
6. Observabilityの`withTrace` / `withSpan`を実現するためにTracing Portへ要求する最小API。
7. 現在の`TraceContext`をどこに保持し、並行実行時にどう伝播するか。
8. Feature別の`Logger m event`を`AppEnv`へ直接持たせるか、Feature単位の依存recordへまとめるか。
9. `Logger m LogSpec`を組み立て、`LogSpec`から`LogRecord`を構築してSinkへ渡すRuntime APIと、`timestamp` / `component`を付加する正確なmodule境界。
10. 利用インターフェース固有eventとApplication lifecycle eventの`event -> LogSpec`純粋関数を置く正確なCabal component。
11. Logging自身のfailureをOperationの最終結果へどう反映するか。Operation failureと同時に起きた場合に何を返すか。
12. 旧`Observation` / `Result` / `AppError` / `ExecutionFailure`相当を維持・変更・削除する範囲。
13. SQLite投影を置くCabal library、使用するSQLite library、migrationの配置、transaction境界、復元API、往復テスト。

`ErrorType`の具体的な内部表現・値が実装で必要になった場合は、正本と既存コードを確認して別途確定する。

## 次の作業

現在実行中のSubtaskは`RS-0022 subtask 実行追跡・構造化ログの全体設計を確定する`である。

次は、Feature別Loggerを`AppEnv`へ直接持たせるかFeature単位の依存recordへまとめるかを決める。その後、`LogSpec` / `LogRecord`の正確な型、Logging Runtime / Sink境界、logging failureの通知とOperation結果との関係を確定し、後続実装Subtaskが追加の全体設計判断なしで着手できる状態にする。

正本Ticketは、SQLiteへの投影、migration、復元、往復検証も完了条件としている。一方、現在のWorkbenchにはSQLite実装を担当する独立Subtaskがない。SQLite実装へ着手する前に、既存Subtaskへ含めるのか独立Subtaskへ分けるのかを決め、Taskと実branchを一致させる。
