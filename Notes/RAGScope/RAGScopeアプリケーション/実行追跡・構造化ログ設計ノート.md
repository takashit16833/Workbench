## 現在の実装構成候補

Workbenchでは、実装候補を次の5 packageで検討している。これは実装前の候補であり、最終的なpackage / library / module構成はCabal設定とコードで確定する。

```text
ragscope
ragscope-error
ragscope-observability
ragscope-logging
ragscope-tracing
```

`ragscope`ではFeatureとApplicationで必要な依存が異なるため、private libraryを分ける候補としている。

```text
ragscope
├─ ragscope-features
└─ ragscope-application
```

- `ragscope-features`: Featureのevent / failure / UseCaseを置く。Logging / Tracingの具体APIには依存させない。
- `ragscope-application`: 利用インターフェース、Operation実行、本番構成の組み立て、FeatureのeventとLoggingの接続を置く。
- `ragscope-error`: `RAGScope.ErrorType`を公開する。
- `ragscope-observability`: 利用側が使うObservability API、Operation / child spanを実行するRunner、span lifecycleの内部実装を分ける。
- `ragscope-logging`: 共通のログ型、公開`write` API、Runtime / Sink / JSON / SQLiteを分ける。
- `ragscope-tracing`: `TraceContext`、Tracing Port、OpenTelemetry Adapterを分ける。

正確な依存方向は静的依存図で管理する。同じ依存をこのノートへ一覧として複製しない。

## 実装時の値の流れ

現在検討している共通Logging側の流れは次のとおり。

```text
Feature / Interface / Lifecycle のevent
  ↓ ToLogSpec
LogSpec
  + 実行時情報
  + 任意のTraceContext
  ↓
LogRecord
  ↓
Sink / JSON / SQLite
```

Feature / UseCaseでは、Logger、TraceId / SpanId、OpenTelemetry SDK、JSON / SQLite表現を直接扱わない。本番環境でObservability / Logging / Tracingを接続する処理はApplication側へ置く。

## 現在未確定の実装事項

次は、正本で実装詳細が確定していないか、コードへ落とす段階で具体化が必要な項目である。

1. `OperationFailure`の正確なmodule名とconstructorの構文。
2. 同期`Exception`をどこで`catch`するか。どの`Exception`型をどの条件で、型で表現したfailureへ変換し、変換しないものをどこで`rethrow`するか。
3. 非同期`Exception`を受けたとき、各spanのscopeでどの後始末を行い、その後どう`rethrow`するか。
4. Operationのroot span / UseCase spanを開始・終了するObservability公開APIの正確な型とmodule分割。
5. Feature内部spanを開始するAPIと、Feature向けEffectの分割。
6. 現在の`TraceContext`をどこに保持し、並行実行時にどう伝播するか。
7. traceに属するeventと、traceに属さないeventを`RAGScope.Logging.Write`へ渡す公開API。`Maybe TraceContext`を1つのAPIで受けるか、traceあり / traceなしでAPIを分けるか。
8. `LogSpec`から`LogRecord`を構築してSinkへ渡すRuntime APIと、`timestamp` / `component`をどこで付加するか。
9. `ToLogSpec`のorphan instanceを置く正確なCabal componentと、それを有効にするimport経路。
10. Logging自身のfailureをOperationの最終結果へどう反映するか。Operation failureと同時に起きた場合に何を返すか。
11. 旧`Observation` / `Result` / `AppError` / `ExecutionFailure`相当を維持・変更・削除する範囲。
12. SQLite投影を置くCabal library、使用するSQLite library、migrationの配置、transaction境界、復元API、往復テスト。

`ErrorType`の具体的な内部表現・値が実装で必要になった場合は、正本と既存コードを確認して別途確定する。

## 次の作業

現在実行中のSubtaskは`RS-0022 subtask logging全体像を設計して公開APIと中核型を実装する`である。このSubtaskでは、上記候補をコードとCabal設定へ落とせるところまで具体化し、Logging / Observability / Tracingの公開APIとLoggingの中核型を実装する。

その後の既存Subtaskは次の依存関係で進む。

```text
logging全体像・公開API・中核型
├─ trace・span実装
│    └─ Application実行・失敗境界
└─ JSON・Sink・Schema

Application実行・失敗境界 + JSON・Sink・Schema
└─ 最終整合性
```

正本Ticketは、SQLiteへの投影、migration、復元、往復検証も完了条件としている。一方、現在のWorkbenchにはSQLite実装を担当する独立Subtaskがない。SQLite実装へ着手する前に、既存Subtaskへ含めるのか独立Subtaskへ分けるのかを決め、Taskと実branchを一致させる。
