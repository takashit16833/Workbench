正本を確認したうえで、`ToErrorType` の適用範囲はかなり明確に決められます。結論としては、**UseCase専用ではなく、RAGScopeアプリケーション内で「失敗した処理を `error_type` で観測するための共通変換契約」とする**のが自然です。

branch HEAD は引き継ぎ記載どおり `2a78de873e1ec6ce02d7c2a96b34a1e75fe31849` でした。

## 結論

`ToErrorType` の責務はこう定義するのがよいです。

```text
具体的なfailure値
        ↓ ToErrorType
      ErrorType
        ↓
spanのerror_type / 失敗eventのerror_type
```

つまり、

> **RAGScopeアプリケーションで、ある具体的なfailureを失敗理由として観測境界へ渡し、その理由を`error_type`として記録する場合、そのfailure型に`ToErrorType`を要求する。**

です。

ここでいう観測境界はUseCaseだけではありません。現在の共通契約では、UseCaseを一度も呼ばない入力検証失敗でもroot spanを`Error`として、その理由の`error_type`を付けます。またUseCase後処理の失敗も同様です。

したがって、現在の`ユースケース詳細設計.md`にある「UseCase固有failure → `ToErrorType`」は正しいものの、**契約全体の適用範囲としては狭い**です。現在の文書自身も、`ToErrorType`をUseCase固有failureに対する契約として記述しています。

## 適用対象

私なら次のように確定します。

|failure|`ToErrorType`|理由|
|---|--:|---|
|UseCase固有failure|必須|UseCase spanを`Error`にするとき、その失敗理由が必要|
|routing / command判定failure|必須|UseCaseなしでroot spanが`Error`になり得る|
|input conversion / validation failure|必須|同上|
|post-UseCase processing failure|必須|UseCaseが成功してもroot spanだけ`Error`になり得る|
|Feature内部のfailure|条件付きで必須|内部spanを`Error`として`error_type`を付けるfailureなら必要|
|Application lifecycle failure|条件付きで必須|lifecycle失敗eventへ`error_type`を記録するfailureなら必要|
|捕捉した同期Exceptionを変換した通常failure|必須|**変換後のfailure型**に要求する|
|生の`SomeException`等|対象外|arbitraryなExceptionを直接安定分類しない|
|async Exception|対象外|通常failureへ変換せずcleanup後に再throwする|
|Logging内部failure|原則対象外|通常のlogging経路自身を観測する契約にしない|
|Tracing内部failure|原則対象外|同様に通常のtrace失敗理由と混ぜない|

最後のLogging/Tracingは重要です。

共通契約上、ログ基盤自身の失敗などにも`error_type`という概念自体は使用可能です。ADR-0005も、その具体的な扱いをコンポーネント実装側で決めるとしています。

ただし、

```text
LoggingFailureだから
→ 必ずToErrorType
```

とはしません。

`ToErrorType`の必須条件は「failureであること」ではなく、**通常の観測経路へそのfailureを渡して`error_type`にすること**です。

## `ErrorType`が表す範囲

ここもUseCase専用ではありません。

私は、

> **RAGScope内で処理が成立しなかった理由を、実装固有のfailure型から独立して機械的に識別する共通の観測用失敗分類**

とします。

これは現在の論理契約の`error_type`の意味と一致します。正本では`error_type`を「なぜ処理が成立しなかったか」の安定した名称としており、機能だけでなく利用インターフェース、ライフサイクル、コンポーネント実装固有の失敗まで対象にしています。

したがって、

```text
ErrorType
≠ UseCase failure分類
≠ OperationFailure
≠ Exception
≠ 利用者向けエラー
```

です。

`ErrorType`は**観測用の共通分類**です。

この意味なら、`ragscope-error / RAGScope.ErrorType`が所有するという現在の判断もかなり自然です。RS-0022 TicketでもLogging・Tracing・Observability・Featureのいずれにも所有させないことが既に決まっています。

## Operation側は一段ラップするのがよい

ここは今回かなり重要な設計結果です。

UseCase前後の具体failureを全部`ErrorType`へ早々に潰してしまうのではなく、

```text
InputFailure
DenseSearchFailure
ResponseFailure
      ↓
Operation固有failure
      ↓
OperationFailure
```

という構造で**具体failureを保持したままOperation境界まで運ぶ**のがよいです。

概念例なら、

```haskell
data SearchOperationFailure
    = SearchInputFailure InputFailure
    | SearchUseCaseFailure DenseSearchFailure
    | SearchResponseFailure ResponseFailure
```

のような形です。名前や正確な型はまだ固定する必要はありません。

そして外側にも、

```haskell
instance ToErrorType SearchOperationFailure where
    toErrorType = \case
        SearchInputFailure f    -> toErrorType f
        SearchUseCaseFailure f  -> toErrorType f
        SearchResponseFailure f -> toErrorType f
```

という**委譲だけのinstance**を持たせます。

これがかなりきれいです。

UseCase failureの場合、

```text
DenseSearchFailure
 ├─ UseCase span
 │    └─ toErrorType
 │
 └─ SearchOperationFailureへ持ち上げ
      └─ root span
           └─ toErrorType
```

となり、両方とも同じ`ErrorType`になります。

しかもroot spanのためにUseCase failureを早期に`ErrorType`へ潰す必要がありません。

現在の契約で求めている、

> 同じ失敗をUseCase spanとroot spanへ表す場合は同じ`error_type`

にも自然につながります。

## `ToErrorType`を呼ぶ場所

ここは「Observability APIだけが呼ぶ」と一箇所に限定しない方がよいです。

呼び出し地点は2種類あります。

```text
failure
   │
   ├─ spanへ反映
   │    ↓
   │ Observability Effect API
   │    ↓ toErrorType
   │  ErrorType
   │
   └─ failure event
        ↓
     ToLogSpec instance
        ↓ toErrorType
      LogSpec.attributes.error_type
```

### span

UseCaseやOperationの実行を包むObservability側のAPIが、失敗値を受け取って`toErrorType`を適用します。

その下のTracing Portへは、

```text
具体failure
```

ではなく、

```text
ErrorType
```

だけを渡します。

### 構造化ログ

失敗eventは具体failureを保持したままでよいです。

たとえば概念上、

```haskell
SearchFailed DenseSearchFailure
```

のようなeventをFeatureが所有し、その`ToLogSpec` instanceで、

```haskell
toErrorType failure
```

を使います。

これならLogging Runtimeへ`DenseSearchFailure`は漏れません。

`ToLogSpec`がeventから`LogSpec`だけを作り、timestamp/component/Trace Contextは後からLoggingが付けるという現在設計ともそのまま整合します。

## 同期Exceptionとasync Exception

ここも分けるべきです。

同期Exceptionは、

```text
known synchronous Exception
        ↓ catch boundary
具体的な通常failure
        ↓ ToErrorType
     ErrorType
```

とします。

たとえばDB libraryのExceptionをFeatureが意味のある`DatabaseQueryFailure`へ変換したなら、`ToErrorType`対象は`DatabaseQueryFailure`です。

一方、

```haskell
instance ToErrorType SomeException
```

のようなものは作りません。

そうするとlibrary固有Exceptionや未知のExceptionまで共通分類へ直接入り、分類責務が崩れます。

予期しない同期Exceptionをトップレベルで捕捉する場合も、生の`SomeException`へinstanceを作るのではなく、Application境界で「予期しない内部失敗」を表す専用failureへ変換する方がよいです。元Exceptionは内部原因として保持できますが、`toErrorType`はその中身を解析せず安定した分類を返します。

async Exceptionは別です。

```text
AsyncException
  ↓
cleanup / span終了
  ↓
rethrow
```

通常の`OperationFailure`へ変換せず、`ToErrorType`も要求しません。

これは「失敗理由」ではなく実行中断の制御だからです。

## Logging failureはOperationFailureにしない方がよい

ここは今回、`ToErrorType`とは別ですが一緒に決めてよい部分だと思います。

現在の旧実装は、

```haskell
Right featureResult + Left LoggingFailure
    -> LoggingFailedAfterSuccess
```

として、ログ出力に失敗するとアプリケーション実行自体を失敗にしています。

しかし現在確定した`OperationResult`は、

> 利用者が依頼した結果を成立させられたか

でSuccess/Failureを決めています。

したがって例えば、

```text
検索成功
↓
利用者へ検索結果を返せる状態になった
↓
ログSinkだけ失敗
```

なら、

```text
OperationSuccess
```

のままにするのが整合します。

Logging/Tracingは**OperationResultとは別の観測基盤の実行結果**として扱うべきです。

これは旧`ExecutionOutcome` / `ExecutionFailure`を今後置き換える大きな理由にもなります。現在コードはRS-0015時代の`AppError`、`ExecutionOutcome`、旧Loggingモデルのままで、Cabalにもまだ`ragscope-error`は存在していません。

つまりここは「現在コードを踏襲する」のではなく、RS-0022で置き換える対象です。

## static dependency

この設計なら依存方向もかなり素直です。

```text
                 ragscope-error
                RAGScope.ErrorType
                ErrorType / ToErrorType
                   ▲    ▲    ▲
                   │    │    │
             Feature  Interface  Application
              failure   failure    lifecycle
                   │
                   │ concrete failure
                   ▼
             Observability
                   │ ErrorType
             ┌─────┴─────┐
             ▼           ▼
          Tracing       Logging
```

`ragscope-error`は他のRAGScope内部packageへ依存しません。

failure型を所有するlibraryは`ToErrorType` instanceを書くため`ragscope-error`へ依存します。

Tracingは`ErrorType`をspanへ設定するため、`ragscope-error`へ直接依存させてよいです。

Observabilityも当然`ragscope-error`へ依存します。

Loggingについては、`LogSpec`のattributesをどの正確なHaskell型にするかと合わせて最終決定できます。`ErrorType`を型のままLogging APIへ渡すなら依存するし、`ToLogSpec`側で属性値へ変換済みにするなら直接依存しなくても成立します。**ここだけは`LogSpec`型設計とセットで決めるべきで、現段階で無理に固定しません。**

設計書作業ルールでも、module/package依存は「どのAPIを呼ぶためか・どの値を渡すためか・どのimportが必要か・Cabalでどう制約するか」まで確認することになっているため、この依存理由まで明示して決めるのが適切です。

## 正本配置

ここも結論を出せます。

**`ToErrorType`本体を`ユースケース詳細設計.md`から分離するのを推奨します。**

新しい責務は、

> RAGScopeアプリケーションのHaskell実装において、具体failureから共通`ErrorType`へ変換する契約

です。

Feature、利用インターフェース、Operation、Lifecycleへまたがるので、UseCase詳細の責務ではありません。

配置候補は私は、

```text
project-docs/design/
└─ 失敗理由ErrorType変換設計.md
```

あたりを推します。

`logging/`配下には置きません。

`ErrorType`はLogging自身の概念ではなく、Tracingにも使い、`ragscope-error`もLoggingの所有ではないためです。

分担はこうなります。

```text
実行追跡・構造化ログ契約設計
└─ error_typeの論理的な意味

失敗理由ErrorType変換設計
├─ ErrorType / ToErrorType
├─ 適用対象
├─ 純粋・totalという契約
├─ instance所有規則
└─ package依存

ユースケース詳細設計
└─ UseCase固有failureはToErrorTypeを実装する

利用者操作実行設計
├─ pre / UseCase / post failureを具体値のまま保持
├─ Operation failureへの持ち上げ
└─ root spanでToErrorTypeを使う

構造化ログイベント変換設計
└─ failure eventのToLogSpecからToErrorTypeを利用する
```

これは「現在設計を1つの正本へ置き、他文書には必要な接続だけを書く」という文書管理規約にも合います。 文書作業ルールでも、対象文書の責務外の情報を関連性だけで混ぜないことが求められています。

### 今回の設計結果

なので、この段階で私は次を採用案とします。

> **`ToErrorType`はUseCase専用契約ではない。RAGScopeアプリケーションで、具体的なfailureを`error_type`として観測するfailure型に共通して要求する。具体failureは所有境界を越えても可能な限り保持し、spanまたはLogSpecへ変換する観測境界で`toErrorType`を適用する。Operation固有failureは内包するfailureへ変換を委譲する。同期Exceptionは通常failureへ正規化した後に対象とし、生のExceptionとasync Exceptionには適用しない。Logging/Tracing内部failureには一律には要求せず、OperationResultとも分離する。**

これなら、UseCaseだけに引っ張られず、root span・Feature内部span・trace外Lifecycleまで一つの設計原則で説明できます。

今回は設計確認だけなので、branch上のファイル変更・commit等は行っていません。変更時には指定branchと既存差分を確認し、依頼範囲だけを変更するルールです。 Ticket作業でも正本Ticketと実branchを基準に再開する規則に沿って確認しています。 Workbenchは正本ではなく補助情報という扱いのままです。

次はこの設計を前提に、**`OperationFailure`の具体的なHaskell構造と、root/UseCase spanを包むObservability APIを設計する**のが一番自然です。
