# テストから逆引きする

対象: `RS-0024/exception-event-once` / `9f6517a4dc9c2fbaa70479eea8cf7c1d3a7acc78`

## テストの役割を先に分ける

現在のTelemetry周辺テストは、全部同じ層を見ているわけではない。

```text
OpenTelemetryBehaviorSpec
  = hs-opentelemetry自体の挙動を確認する

OpenTelemetryTraceSpec
  = RAGScope TraceBoundary + Trace Adapterを確認する

OpenTelemetryLogsSpec
  = RAGScope LogsBoundary + Logs Adapterを確認する

OpenTelemetryExceptionEventSpec
  = TraceとLogsを接続したexception統合動作を確認する

OpenTelemetryTestSupport
  = Provider / Exporterなど共通fixtureとassertion
```

この区別をしてから読むと、どこで不具合が起きているかを絞りやすい。

## `OpenTelemetryBehaviorSpec.hs`

ここはRAGScopeのBoundaryを主役にしていない。

`inSpan''`を直接使って、hs-opentelemetryが実際にどう動くかを確認している。

### current Span

```text
Span callback中は、そのSpanがcurrentになるか
```

を確認する。

これがLogsとのTrace correlationの前提になる。

### nested SpanのContext復元

```text
parent current
  ↓
child開始
  ↓
child current
  ↓
child終了
  ↓
parent currentへ戻る
```

を確認する。

### callbackが返した`Left`をSDKが勝手にError扱いしない

これは重要。

```haskell
pure (Left "expected-failure")
```

をcallbackが返しても、hs-opentelemetryから見ればただの正常return。

```text
EitherのLeft
  ≠ Haskell exception
```

であることを確認している。

未採用の`Either CapturedException result`案を考えるときも、このSDK挙動が前提になる。

### default exception handling

SDKデフォルトでは、callbackからexceptionが出ると、

```text
Span Status = Error
exception Span Event = 1件
exceptionは再throw
```

となることを確認している。

### ignore設定

RAGScopeのようにexception typeをignore対象にすると、SDKの自動Span Eventを抑制できる。

ただしexception自体は再throwされ、Context cleanupも行われる。

つまり、

```text
ignore
  = SDKのexception自動記録を抑える

ignore
  ≠ exception propagationを止める
```

と読める。

## `OpenTelemetryTraceSpec.hs`

ここではhs-opentelemetryを直接使うのではなく、

```haskell
withSpan traceBoundary ...
```

を使う。

つまりRAGScopeの公開境界から見た振る舞いを確認している。

### 成功結果を壊さない

```text
action result = 42
    ↓
withSpan
    ↓
result = 42
```

かつSpanは`Unset`。

### application-level failureを壊さない

```text
action result = Left failure
    ↓
classifier = SpanFailed
    ↓
SpanはError
    ↓
元のLeft failureはそのまま返る
```

を確認する。

### 同期exception

```text
TestException
    ↓
Span Error
error.typeあり
SDK exception Span Eventなし
元のTestExceptionを再throw
```

を確認する。

### UserInterrupt

```text
UserInterrupt
    ↓
Span Unset
error.typeなし
Span Eventなし
UserInterruptを再throw
```

を確認する。

今回のexactly-once修正で非同期exception経路まで変えてはいけない理由を、このテストから確認できる。

### actionは1回だけ

Telemetry wrapperがactionを再実行しないことを明示的に確認している。

SDK cleanup失敗時などに「もう一度actionを実行すればよい」とはできないことにも繋がる。

## `OpenTelemetryLogsSpec.hs`

ここではLogs Adapterを確認する。

見るポイントは、

```text
RAGScope LogRecord / EventRecord
    ↓
OpenTelemetry LogRecord
```

への変換。

特にEventRecordでは、

```text
event name
severity
attributes
timestamp
TraceId / SpanId
```

が重要になる。

Logs Adapter自身はSpanを作らない。

emit時のcurrent ContextからTrace情報を受け取る。

## `OpenTelemetryExceptionEventSpec.hs`

今回のSubtaskで一番重要な統合テスト。

Trace ProviderとLogger Providerを両方作り、

```haskell
logsBoundary =
  mkOpenTelemetryLogsBoundary loggerProvider

traceBoundary =
  mkOpenTelemetryTraceBoundary
    tracerProvider
    (emitEventRecord logsBoundary)
```

としてTraceとLogsを接続する。

## ケース1: rootまでexceptionが抜ける

構造は、

```text
root-span
└─ use-case-span
   └─ internal-span
      └─ TestException
```

### 元のexception

```haskell
result `shouldBe` Left TestException
```

Telemetryがexceptionを別の型や別の値へ置き換えていないことを確認する。

### Context復元

rootへ入る前のContextと、全Spanを抜けた後のContextが同じことを確認する。

### 3つのSpanすべて

```haskell
mapM_
  assertTestExceptionSpan
  [ internalSpan
  , useCaseSpan
  , rootSpan
  ]
```

各Spanについて、

```text
Status Description = TestException
error.type = TestException
exception Span Event = 0
```

を確認する。

### EventRecordは1件

`assertSingleExceptionEvent`で、exportされたLogRecordが1件だけであることを要求する。

さらに、そのLogRecordのTraceId / SpanIdが、exception発生時に保存した`internal-span`のContextと一致することを確認する。

つまりこの1つのassertionで、

```text
件数 = 1
owner = internal-span
```

の両方を見ている。

現在失敗しているのは件数。

```text
expected exactly one exported LogRecord, but got 3
```

## ケース2: use-case内でcatchして復旧

```text
root
└─ use-case
   └─ internal
      └─ TestException
         ↓
      internalを抜ける
         ↓
   application codeがcatch
```

期待は、

```text
internal = Error
use-case = Unset
root = Unset
EventRecord = 1件
```

### なぜこのテストが重要か

「子Spanでexceptionが起きた」というだけで、親Spanまで自動的にErrorにしてはいけないことを示している。

親SpanがErrorになる条件は、

```text
exceptionがその親Span自身の境界も外へ抜けた
```

とき。

application codeが途中でcatchして復旧したら、それより外側へはexceptionは伝播しない。

### Logs fixture

### `withTestTraceBoundary`

TracerProviderからOpenTelemetry版TraceBoundaryを作る。

```haskell

```

を渡している。

これによってTrace単体テストとTrace + Logs統合テストを分離している。

件数を見る前に、


する。

```text

```

ことと、

```text

```

ことのタイミング差をテストから排除するため。

## 今回の問題をテストから辿る最短ルート

```text
1. OpenTelemetryExceptionEventSpec
   「1件のはずが3件」を確認

2. markSynchronousException
   各Spanでclaimしていることを確認

3. claimExceptionEvent
   marker判定自体は純粋で単純と確認

4. ではなぜouterでmarkerが見えない？

5. OpenTelemetryBehaviorSpec
   inSpan''がexceptionをcatch / cleanup / rethrowすることを確認

6. hs-opentelemetry inSpanInternal
   SomeExceptionでcatchしてthrowIOしていることを確認

7. GHC Exception SomeException
   toExceptionでExceptionContextを落とすことを確認
```

この順に追うと、`claimExceptionEvent`のロジックを複雑化する問題ではなく、markerを運ぶ経路の問題だと分かる。
