# テストから逆引きする

対象: `RS-0024/exception-event-once` / `e40a998a0352214e4989a0aec5ec6ea1d65d6e8b`

## テストの役割を先に分ける

現在のTelemetry周辺テストは、全部同じ層を見ているわけではない。

```text
OpenTelemetryBehaviorSpec
  = hs-opentelemetry自体の挙動を確認する

OpenTelemetryTraceSpec
  = RAGScope TraceBoundary + Trace Adapterを確認する

OpenTelemetryLogsSpec
  = RAGScope LogsBoundary + Logs Adapterを確認する

OpenTelemetryExceptionEventSpec
  = TraceとLogsを接続したexception統合動作を確認する

OpenTelemetryTestSupport
  = Provider / Exporterなど共通fixtureとassertion
```

## `OpenTelemetryBehaviorSpec.hs`

ここはRAGScopeのBoundaryではなく、`inSpan''`などhs-opentelemetry側の実際の挙動を見る。

重要なのは、callbackが返した`Either`の`Left`はHaskell exceptionではない、という点である。

```haskell
pure (Left "expected-failure")
```

を返しても、SDKから見れば正常returnである。

```text
EitherのLeft
  ≠ Haskell exception
```

現在の`SpanExit`実装は、この性質を利用している。

```text
Left CapturedException
    ↓
inSpan''からは正常return
    ↓
SDKのSomeException catch / throwIO経路へ入らない
```

一方、callbackから本当にHaskell exceptionが出ると、SDKはexception pathへ入り、Span cleanup後に再throwする。

## `OpenTelemetryTraceSpec.hs`

RAGScopeの公開境界、

```haskell
withSpan traceBoundary ...
```

から見た振る舞いを確認する。

主な観点は次の通り。

```text
成功
  → 元の値を返す
  → Span Unset

application-level failure
  → classifierに応じてSpan Error
  → 元のfailure値はそのまま返す

同期exception
  → Span Error
  → error.typeあり
  → SDK exception Span Eventなし
  → 元のexceptionを再throw

UserInterrupt
  → Span Unset
  → error.typeなし
  → Span Eventなし
  → UserInterruptを再throw

実行回数
  → actionは1回だけ
```

現在の`SpanExit`変更でも、これらを壊してはいけない。

## `OpenTelemetryLogsSpec.hs`

Logs Adapterの変換を確認する。

```text
RAGScope LogRecord / EventRecord
    ↓
OpenTelemetry LogRecord
```

EventRecordでは、

```text
event name
severity
attributes
timestamp
TraceId / SpanId
```

を見る。

Logs Adapter自身はSpanを作らず、emit時のcurrent Contextを使ってTraceId / SpanIdを関連付ける。

## `OpenTelemetryExceptionEventSpec.hs`

今回のSubtaskで最も重要な統合テスト。

Trace ProviderとLogger Providerを両方作り、

```haskell
logsBoundary =
  mkOpenTelemetryLogsBoundary loggerProvider

traceBoundary =
  mkOpenTelemetryTraceBoundary
    tracerProvider
    (emitEventRecord logsBoundary)
```

として接続する。

この接続から、現在の依存も読み取れる。

```text
LogsBoundary
    ↓ emitEventRecord
EventRecordEmitter
    ↓
Trace Adapterへ注入
```

Trace AdapterはOpenTelemetry Logs Adapterそのものを呼ばず、SDK非依存のEmitterを受け取る。

## ケース1: rootまでexceptionが抜ける

```text
root-span
└─ use-case-span
   └─ internal-span
      └─ TestException
```

確認したい結果は、

```text
元のTestExceptionが外へ伝播

internal-span = Error + error.type
use-case-span = Error + error.type
root-span = Error + error.type

exception Span Event = 0件
exception EventRecord = 1件
owner = internal-span
```

である。

EventRecordのownerは、exportされたLogRecordのTraceId / SpanIdと、exception発生時のinternal-span Contextを比較して確認する。

## ケース2: use-case内でcatchして復旧

```text
root
└─ use-case
   └─ internal
      └─ TestException
         ↓
      internalを抜ける
         ↓
   application codeがcatch
```

期待は、

```text
internal = Error
use-case = Unset
root = Unset
EventRecord = 1件
```

親SpanがErrorになる条件は「子でexceptionが起きたか」ではなく、exceptionがその親Span自身の境界も外へ抜けたか、である。

## 現在の`SpanExit`変更をテストから追う

production codeでは、同期exceptionが現在次のように流れる。

```text
handleSynchronousException
    ↓
markSynchronousException
    ↓
Left CapturedException
    ↓
inSpan''は正常returnとしてSpan終了
    ↓
either rethrowIO pure
```

この修正によって特に確認したいのは、

```text
1. EventRecordが1件になる
2. ownerがinternal-spanのまま
3. 3 SpanすべてErrorになる
4. exception Span Eventが0件のまま
5. 元のTestExceptionがその型のままcatchできる
6. recoveryケースが壊れない
7. UserInterruptなど非同期exceptionの既存挙動を壊さない
8. application resultのLeftとSpanExitのLeftを混同しない
```

である。

## `OpenTelemetryTestSupport.hs`

Providerの仕組みを見る入口でもある。

Trace側は概ね、

```text
in-memory Span Exporter
    ↓
SpanProcessor
    ↓
createTracerProvider
    ↓
TracerProvider
```

Logs側は、

```text
in-memory LogRecord Exporter
    ↓
LogRecordProcessor
    ↓
createLoggerProvider
    ↓
LoggerProvider
```

と組み立てる。

Trace単体テストではLogsを本当にexportする必要がないため、EventRecordEmitterにno-opを渡せる。このことからも、Trace Adapterが必要としているのがLogs Adapter実装そのものではなく、`EventRecordEmitter`という能力だと分かる。

## 症状からどこを読むか

### SpanのStatusがおかしい

```text
OpenTelemetryTraceSpec
    ↓
applySpanOutcome
markSynchronousException
```

### exception Span Eventが増えた

```text
OpenTelemetryBehaviorSpec
    ↓
tracerExceptionHandlerOptions
ignoreSynchronousException
```

### EventRecordの内容がおかしい

```text
OpenTelemetryExceptionEventSpec
    ↓
emitExceptionEvent
    ↓
OpenTelemetry Logs Adapter
```

### EventRecordのownerがおかしい

```text
assertTracingDetails
    ↓
EventRecordをemitした時点のcurrent Context
    ↓
どのSpan callback内でemitしたか
```

### EventRecordが重複する

現在は次を順に見る。

```text
OpenTelemetryExceptionEventSpec
    ↓
claimExceptionEvent
    ↓
ExceptionEventRecorded marker
    ↓
markSynchronousExceptionがmarker付きCapturedExceptionを返すか
    ↓
handleSynchronousExceptionがLeftへ入れるか
    ↓
inSpan''を正常returnとして抜けるか
    ↓
外側のrethrowIO後もouter handlerでmarkerが見えるか
```

以前の原因調査では、さらに、

```text
inSpan''内部のSomeException catch / throwIO
    ↓
GHC 9.12.4 Exception SomeException
    ↓
ExceptionContext消失
```

まで追った。

現在の実装はそのSDK exception pathを同期exceptionだけ迂回する。
