# 未実装の設計候補

このノートは**現在実装ではない**。現在の静的依存と実moduleは[[07 現在の静的依存マップ]]を見る。

ここには、旧RS-0024設計ノートのうち、現在コードへまだ入っていないが今後の実装判断に残す価値がある内容だけを集約する。採用するときは、その時点のRAGScope正本リポジトリ、実module、`ragscope.cabal`、テストを再確認する。

空moduleを先に作るための一覧ではない。具体的な責務が発生したときだけ実装する。

## 将来も守りたい依存方向

候補として残す基本線は次である。

```text
feature / UseCase
    ↓
telemetry-boundary

opentelemetry-adapter
    ├─ telemetry-boundary
    └─ OpenTelemetry SDK
```

避けたい方向は次。

```text
feature ──X──► opentelemetry-adapter
telemetry-boundary ──X──► OpenTelemetry SDK
opentelemetry-adapter ──X──► 個別featureの失敗型
```

後続のHTTP / DB / GenAI等で標準instrumentation packageを使う場合まで、すべて`opentelemetry-adapter`経由に固定するという意味ではない。その機能の実際のAPIとCabal componentを見て決める。

## Lifecycle候補

`RAGScope.Telemetry.OpenTelemetry.Lifecycle`を作る場合は、Trace / Logs / MetricsのProviderを単に生成するだけでなく、**取得・利用・解放の一続きの責務**として扱う。

候補となる責務:

```text
TracerProvider / LoggerProvider / MeterProviderの構築
Processor / Exporter / Readerの構築・接続
部分初期化失敗時の取得済み資源のcleanup
forceFlush / shutdown
終了処理の一部が失敗しても残りの資源を処理すること
Telemetry失敗を同じTelemetry経路へ再帰記録しないこと
```

旧調査では、当時確認した`hs-opentelemetry`ソースの`initializeOpenTelemetry`について、複数Providerの取得途中で後段が例外になった場合の明示的rollbackがhelper内部に見当たらないことを確認していた。

これは**現在採用APIの確定事項として扱わない**。Lifecycle実装時に、現在利用している正確なpackage version / sourceを再確認して、

```text
SDKの統合helperを使う
vs
各Providerを段階的に取得してcleanupを登録する
```

を比較する。

## production向け構築入口とtest向け低水準入口

productionの`Main`へ`SpanProcessor`、`LogRecordExporter`等のSDK型を直接渡す必要がなければ、高水準のAdapter入口はSDK非依存に保つ候補がある。

一方、Adapterのテストではproductionと同じAdapter実装へin-memoryのProcessor / Exporter / Readerを差し込みたい。

そのため必要になった場合だけ、Adapter内部に狭い低水準構築入口を置く候補を残す。

```text
RAGScope.Telemetry.OpenTelemetry
  = production / Main向け高水準入口

限定されたConstruction入口
  = Adapter test向け
  = SDKのProcessor / Exporter / Reader等を受け取る
```

production用Adapterとtest用Adapterを別実装にすることは避ける。

## Metrics候補

Metricsについては、`telemetry-boundary`に先に万能な、

```text
emitMetric name value attributes
```

のようなAPIを作らない。

理由は、Counter / Histogram等で操作と意味が異なり、単位や属性制約もinstrumentごとに異なるからである。

候補の基本線:

```text
MeterProvider / Reader / ExporterなどのSDK構成
    = Adapter / Lifecycle側

application-facingなMetric操作
    = 実際に手動記録する具体的なMetricが必要になった時点で最小限追加
```

SDKが提供するaggregation、temporality、collection、exportを再実装しない。

また、Metric属性へTraceId / SpanId、Invocation ID、文書IDなど高cardinalityな実行識別子を共通で自動追加しない。

## Context候補

OpenTelemetry Contextと、依存を渡すReader環境は別物として扱う。

```text
Reader環境
  = DB / HTTP / Telemetry操作 / 設定などの依存

OpenTelemetry Context
  = current Span等の実行scope情報
```

RAGScope側に独自TraceId / SpanIdや独自Context stackを作らない。

必要な場合はContext値そのものを業務値として持ち回るより、操作を狭く公開する候補を優先する。

### 同一thread

Span作成時のcurrent Context切り替えと復元は、現在のTrace AdapterのSpan scope内で完結させる。

### child thread

必要になった場合は、

```text
親threadでcurrent Contextをcapture
    ↓
child threadでそのContextを適用
    ↓
action終了後に元Contextへ復元
```

というscopeとして扱う。

### outbound通信

HTTP等へTrace Contextを渡す場合は、送信時点のcurrent ContextをPropagatorでcarrierへinjectする操作を候補とする。

fresh child threadへの伝播、既存workerへの一時適用、outbound carrierへのinjectは同じ操作として雑にまとめない。

## feature固有の失敗型とTelemetry変換

将来feature private libraryを実装するときは、処理ごとの具体的な失敗型を保ち、Telemetry用の分類値へ早い段階で潰さない候補を残す。

```text
具体的な処理失敗
    ├─ 呼び出し側の実行制御へそのまま使う
    └─ 純粋変換
         ↓
       SpanOutcome / EventRecord等の観測表現
```

module配置の候補は、

```text
RAGScope.UseCase.*
RAGScope.UseCase.*.Error
RAGScope.UseCase.*.Telemetry
```

のように、UseCase本体・失敗型・Telemetry変換をcycleしない形へ分けること。ただし具体的なfeatureがないうちに空moduleを作らない。

残したい原則は次。

```text
外部library固有error / 既知の同期例外
  → 外部Adapterで利用側の具体的な処理失敗へ変換

async exception / 意図された中断
  → 通常の処理失敗へ変換しない

Telemetryのerror.type
  → 元の失敗値を置き換えない

telemetry-boundary / OpenTelemetry Adapter
  → 個別featureの失敗型へ逆依存しない
```

巨大な共通`AppError` / `RAGScopeError`や、すべての失敗型へ共通能力を要求する広いtype classは、具体的な必要が出るまで作らない。

## Haskellの抽象化で残す判断基準

### 関数値 / 関数recordを第一候補にする

DIのためだけにOOPのinterfaceをtype classで再現せず、必要な能力を関数値または小さい関数recordとして渡す。

現在の、

```haskell
EventRecordEmitter = EventRecord -> IO ()
SpanRunner = ... -> IO result -> IO result
```

もこの方向に沿っている。

型クラスは、本当に複数型へ同じ多相操作を要求する具体的な処理が現れた場合に、その能力だけを狭く切り出して再検討する。

### Spanは高階操作として扱う

Spanは「start命令」と「end命令」を利用側へ自由に渡すより、対象処理を受け取ってscopeを囲む高階操作として扱う。

```text
action
  ↓
withSpan / SpanRunner
  ↓
同じresultを返す
```

開始・終了漏れ、別SpanへのStatus更新、Context復元漏れを利用側へ持ち込まない。

### 観測用分類は純粋関数にする

具体的なerror値から`error.type`や`SpanOutcome`への変換は、多対一の分類である。

```text
詳細なfailure
    ↓ pure
安定した観測分類
```

分類後の値から元failureを復元しようとしない。元のresultはそのまま保持する。

### 何でもMonoidにしない

Telemetry operationのrecordだからといって、自動的に`Monoid`を与えない。

```text
Logs操作を2つ結合
  → 二重出力になり得る

Span操作を2つ結合
  → Spanが入れ子になり得る
```

合成可能であることと、同じ意味の結合演算を持つことは別である。

### Signalを万能emitへ統合しない

Trace、Logs、Metricsは意味と操作が異なる。

```text
Trace   = 処理範囲・親子関係
Logs    = 出来事の記録
Metrics = 測定値の集約
```

1つの汎用event busや万能`emit`へ揃えない。

## Telemetry失敗の隔離で残す条件

今後の「Telemetry失敗を機能処理から隔離する」実装でも、少なくとも次を守る候補を残す。

```text
Telemetry記録失敗で、成功した機能resultを失敗へ変えない
本体actionを再実行しない
元の同期exceptionをTelemetry側のexceptionで置き換えない
async exception / cancellationを握りつぶさない
Context cleanupを省略しない
```

no-op fallbackのためにactionをもう一度実行する構造は採らない。

## Span lifecycleの代替案

現在のTrace Adapterは`inSpan''`と`SpanExit`で要求を満たし、変更後のテストも成功している。

そのため、

```text
createSpan
attachContext
endSpan
detachContext
```

をAdapter側で直接組み合わせるmanual lifecycleへ切り替える理由は現在ない。

ただし将来、`inSpan''`の具体的な副作用やexception処理が新しい要求を満たせないと実測で分かった場合は、SDKの低水準APIをAdapter内部で安全に合成する案を再検討する。

## 旧ノートから残さないもの

次は設計資産として独立保存しない。

```text
実装前commit時点の詳細な候補比較
すでに現在コードで決着した型名・関数名の候補
現在実装で置き換えられた例外owner方式
現在のTrace.hsを読むだけで確認できる処理の複製
正本ですでに採用済みの要求・設計全文の複製
```

必要な過去経緯はGit履歴から復元できる。ActiveなWorkbenchノートには、現在理解に必要な内容と、まだ生きている設計候補だけを残す。
