### 1. 一番まずいのは「最終失敗」とroot spanです

ここは読み直して、**現在の記述には実際に矛盾があります。**

現在の擬似コードでは、

```haskell
Application.Execution.run useCase =
  Application.Observability.runObserved useCase

Application.Observability.runObserved useCase =
  Observability.Runtime.runObserved useCase

Observability.Runtime.runObserved useCase =
  withRootSpan $ do
    useCase
```

です。つまり `Application.Execution` が結果を受け取る時点では、普通に読めば `withRootSpan` は終了していて、root spanも閉じています。

ところが別の節では、

```text
Application.Execution
  ↓ 最終失敗を確定
Application.Observability
  ├─ root span Errorを反映
  └─ 最終失敗ログを記録
```

としています。

**root spanを閉じた後に、Application.Executionが確定したErrorをroot spanへ設定することはできません。**

これは未確定というより、現在案を修正すべきです。

私は、

```haskell
Application.Execution.run useCase =
  Application.Observability.runObserved $ do
    result <- useCase

    outcome <- determineFinalOutcome result

    Application.Observability.recordOutcome outcome

    pure result
```

のように、

```text
root span開始
↓
UseCase
↓
Application.Executionが最終結果を確定
↓
root span Error / 最終失敗logを反映
↓
root span終了
```

とする方向を推します。

正確な関数分割は後で詰めればいいですが、**最終結果の確定はroot spanの内側で行う**、は先に決めてよいと思います。

### 2. Cabalによる依存制約が、`ragscope`の中だけ効いていません

これはかなり重要です。

現在の設計思想では、

> 許可していない依存を`build-depends`で機械的に失敗させる

ことを狙っています。

ところが現在の `ragscope` は、

```text
ragscope
└─ ragscope-internal
   ├─ Feature.UseCase
   ├─ Feature.Event
   ├─ Feature.Logging
   ├─ Application.Execution
   ├─ Application.Observability
   └─ Application.LoggingInstances
```

と**全部同じprivate library**です。現行Canvasもその構成です。

すると `ragscope-internal` の `build-depends` に、

```text
ragscope-logging-core
ragscope-logging
ragscope-observability
...
```

が入ります。

その瞬間、

```haskell
RAGScope.<Feature>.UseCase
```

からも技術上は、

```haskell
import RAGScope.Logging
import RAGScope.Logging.Write
import RAGScope.Observability.Runtime
```

できてしまいます。

**「UseCaseはLoggingを知らない」が設計規約だけで、Cabalでは守られていない。**

これは今回の設計方針に対して少し弱いです。

私はここで、`ragscope` にprivate libraryを追加する理由ができたと思います。

例えば、

```text
ragscope
├─ library ragscope-features
│   ├─ Feature.Event
│   └─ Feature.UseCase
│
└─ library ragscope-application
    ├─ Feature.Logging
    ├─ Application.Execution
    ├─ Application.Observability
    └─ Application.LoggingInstances
```

です。

依存は、

```text
ragscope-features
  → Observability APIだけ

ragscope-application
  → ragscope-features
  → Logging
  → Observability Runtime
```

にする。

これなら、UseCaseからLoggingへのimportを**本当にbuildで禁止できます**。

さらに厳密にやるなら `ragscope-observability` 自体も、

```text
Observability API
Observability Runtime
```

を別libraryにして、Feature側はAPI libraryだけに依存させたいです。

これは私なら次に設計を詰めるとき、かなり優先します。

### 3. `withSpan` は別classにした方がよいと思います

これはもう私は「どちらでも」ではなく、**分ける方を推します。**

もし、

```haskell
class Monad m => MonadObservability event m where
  emit :: event -> m ()

  withSpan
    :: SpanName
    -> m a
    -> m a
```

とすると、`withSpan`は`event`を一切使いません。

例えば、

```haskell
foo = withSpan "foo" doSomething
```

だけを行う関数では、

> 何の`event`に対する `MonadObservability event m` なのか

を決める材料がありません。

一方 `AppM` はSearchEventもIndexEventも扱いたいので、

```haskell
m -> event
```

と一意に決めることもできません。

なので私は、

```haskell
class Monad m => MonadSpan m where
  withSpan :: SpanName -> m a -> m a

class Monad m => MonadObservability event m where
  emit :: event -> m ()
```

のように分けます。

名前はまだ検討できます。重要なのは、**span操作には不要な`event`型変数を背負わせないこと**です。

### 4. production instanceもorphanになる可能性があります

現在、

```haskell
instance ToLogSpec event
      => MonadObservability event AppM where
```

を `RAGScope.Application.Observability` に置く想定です。

でも、

* `MonadObservability` は `RAGScope.Observability` 定義
* `AppM` はおそらく別moduleで定義

となると、このinstanceもorphanになります。

現在ノートでは、

> orphanは`RAGScope.<Feature>.Logging`だけに限定

という方向なので、ここは整合を取る必要があります。Feature Loggingのorphanについては現行設計で明示されています。

これは `AppM` を決めるときに、

```text
AppMを定義するmodule
production effect instanceを定義するmodule
```

を一緒に設計すれば解消できます。

私は**production用effect instance群をAppMの定義元に寄せる**方をまず検討します。

### 5. Loggingにはまだ実行環境が足りません

今の擬似型は、

```haskell
write
  :: ToLogSpec a
  => TraceContext
  -> a
  -> m ()
```

ですが、実際には `LogRecord` を作るために、

```text
timestamp
component
Sink
```

も必要です。現在ノートでもここは未確定です。

私はtypeclassをさらに増やすより、

```haskell
data LoggingRuntime m = LoggingRuntime
  { now       :: m Timestamp
  , component :: Component
  , writeSink :: LogRecord -> m ()
  }
```

のような**Logging用の実行環境を値として持つ**案を推します。

そして、

```haskell
write
  :: ToLogSpec a
  => LoggingRuntime m
  -> TraceContext
  -> a
  -> m ()
```

あるいは `LoggingRuntime` を `AppM` のReader環境から取る。

これならclockもSinkもテストで簡単に差し替えられます。

### 6. stderr出力の具体moduleが1つ足りないと思います

今は、

```text
Logging.Sink
Logging.JSON
Logging.SQLite
```

があります。設計上、Sinkは「出力先を差し替える境界」、JSONは「LogRecord→JSON変換」です。

しかしRS-0022では**JSONをstderrへ出す**ところまでやります。

つまり実際には、

```text
LogRecord
↓ Logging.JSON
JSON
↓
stderrへwrite
```

する具体実装が必要です。

私は、

```text
RAGScope.Logging.Sink
RAGScope.Logging.Sink.Stderr
```

のように、

```haskell
stderrSink :: Sink m
```

を持つ具体moduleを追加するのが自然だと思います。

これはCanvasにもまだありません。

### 7. 失敗処理は早めに方針を決めたいです

現在「Logging / Tracing自身の失敗をUseCase結果とどう組み合わせるか」が未確定です。

私は次の区別を推します。

```text
起動時にLogging Runtime / Tracing Runtimeを構築できない
→ Application起動失敗にしてよい

実行中にログ1件の書き込みやOTel exportが失敗
→ UseCaseの成功/失敗を上書きしない
```

例えば、

```text
UseCase成功
+
stderr log write失敗
```

を、

```text
UseCase失敗
```

へ変えるのは避けたいです。

Observabilityの失敗は**副次的な失敗として別経路で報告する**のがよいと思います。

そして「Logging失敗を同じLoggingで記録しない」は既に正しい方針です。

### 8. `withSpan` の終了保証

これは実装時にかなり重要です。

```haskell
withSpan "db" action
```

の `action` が、

```text
正常終了
ExceptTでLeft
throwIO
async exception
```

のどれでも、

```text
child spanを終了する
parent spanへcurrent contextを戻す
```

ことを保証する必要があります。

ReaderTの`local`ならcontext復元はかなり自然ですが、span終了処理は `bracket` / `finally` 相当の保証が必要です。

これはテスト項目にも入れるべきです。
