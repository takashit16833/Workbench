はい。**「1利用者操作全体の失敗境界」は、次のException設計に影響します。**
なので、私なら「後続Subtaskで全部決める」にはせず、**意味上の契約だけ今決めてからExceptionへ進みます**。

現行のユースケース詳細設計は、UseCaseの`Either`はUseCase実行結果だけを表し、操作全体の型は固定していません。 一方、後続Workbench SubtaskはまさにApplication全体の最終失敗、`AppError`、logging failureとの組み合わせを再設計する責務を持っています。

なので分け方はこうするのがいいです。

```text
今決める
────────────────────────
1利用者操作全体にも
「正常終了 / 通常の失敗」を表す外側の実行結果境界がある

UseCase Left
→ その外側の失敗へ持ち上げられる

routing / validation / post-processing failure
→ UseCase Leftには入れず、外側の失敗として扱う

Exception
→ この通常失敗チャネルとどう関係するかを次に決める


後続Subtaskで確定する
────────────────────────
正確なHaskell型
constructor
AppErrorを残すか
ExecutionFailure的な型を作るか
logging failureとの最終合成方法
```

つまり、**型名やADTを今決める必要はないが、「外側にも失敗境界が存在する」ことは今決める**。これならException設計を宙ぶらりんにせず、後続Subtaskの責務も奪いません。

## 更新版：実装開始までの設計タスクリスト

### 4. 同期Exception

3を前提に決めます。

ここで「操作全体の失敗境界」が必要になります。

### 5. 非同期Exception
