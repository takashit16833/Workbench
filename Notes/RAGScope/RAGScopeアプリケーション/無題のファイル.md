## 現在地 — 今からやること

RS-0022は、まだ「実装に入る直前の全体設計」を固めている段階です。

すでに決まっている大枠はかなりあります。

* UseCase境界は `Either failure result`
* 通常のUseCase failureとExceptionは別物
* Feature固有failureは `RAGScope.<Feature>.Failure`
* failure → `ErrorType` は `ToErrorType`
* `ErrorType` / `ToErrorType` は `ragscope-error`
* root spanへfailureを反映するときはObservability Runnerが`ToErrorType`を使う
* failure型自身には`ToLogSpec`を持たせない
* failureをログへ出す場合はFeature eventとして表す
* Feature event → `ToLogSpec` → `LogSpec`
* `ToLogSpec`のorphan instanceはFeatureとLoggingの依存を切るため意図的に採用
* Logging / Tracing / Observabilityの責務を分離し、Cabal依存で方向を制約する
* `RAGScope.Logging.Write`はLoggingの公開API
* `RAGScope.Tracing`はTracing Port
* `RAGScope.Observability`はFeature向けObservability API

そして**今まさにやっているのは、`ToErrorType` / `ToLogSpec`を「実装者が設計書を読んで実装できる粒度」まで文書化すること**です。

順番としては、

```text
現在
  ↓
ToErrorType / ToLogSpec の設計書上の説明を確定
  ↓
Exception設計
  ↓
Observability / Logging / Tracing 全体の実装境界を確定
  ↓
logging自身のfailureまで確定
  ↓
実装開始
```

です。

直近ではまず、次の切り分けを確定させます。

**`ユースケース詳細設計.md`**

```text
ToErrorTypeとは何か
failure → ErrorType の契約
誰が使うか
どこでは使わないか

UseCase failure自身はToLogSpecを持たず、
failureを表すFeature eventがToLogSpecの対象
```

**Observability / Logging側**

```text
ToLogSpecとは何か
Feature event → LogSpec
誰がtoLogSpecを呼ぶか
LogSpec → LogRecord
Logging.Writeとの関係
package / module依存
```

**コードを正本**

```text
正確なclass定義
正確な関数signature
instance本体
constructor
LogSpec / LogRecordの正確な型
Cabalの実際のexposed-modules / build-depends
```

ここを片付けたあと、引き継ぎどおりExceptionへ進みます。

# 実装開始までに決めること

順番も含めて整理すると、私は以下で進めるのがよいと思います。

### 1. `ToErrorType` / `ToLogSpec`の設計書上の説明

**今ここです。**

決めること：

* `ToErrorType`の概念的API
* `ToErrorType`の責務
* `toErrorType`を呼ぶ境界
* `ToLogSpec`の概念的API
* `ToLogSpec`の責務
* `toLogSpec`を呼ぶ主体
* Feature event / `LogSpec` / `LogRecord`の関係
* 上記をどの設計書へ置くか

ここでは新しい実装設計を大量に決めるというより、**すでに決まった設計を実装可能な形で文書化する**のが中心です。

---

### 2. `Left failure` が表す失敗範囲

Exceptionへ行く前に、ここを明確にします。

問いはこれだけです。

```text
UseCaseが Left failure を返すのは、
具体的にどの種類の失敗なのか？
```

つまり、

```text
正常系
Right result

仕様として予想されるUseCase失敗
Left failure

実行中に発生したException
別経路
```

の境界を決めます。

ここで同期例外・非同期例外・Logging failureまで一気に混ぜません。

---

### 3. 同期Exception

`Left failure`との境界が決まった後です。

決めること：

* どの同期Exceptionをどこで捕捉するか
* ExceptionをUseCase failureへ変換する場合があるか
* 変換しないExceptionはどこまで伝播させるか
* root spanのStatusをどうするか
* `error_type`をどう得るか
* Exceptionに対応する構造化ログを記録するか
* Applicationへどう制御を戻すか

---

### 4. 非同期Exception

同期Exceptionとは分けて設計します。

決めること：

* `AsyncException`を通常のfailureへ変換しないこと
* cleanupのためにどこで捕捉するか
* 捕捉後に再throwする境界
* root spanを確実に終了できるか
* logging処理中にも非同期Exceptionを遮断しすぎないか

特に、

```text
Ctrl-C
thread cancellation
timeout実装による非同期例外
```

などを通常のUseCase failureと混ぜないことが重要です。

---

### 5. Observability Runnerの公開境界

ここまで決まると、Runnerの役割を具体化できます。

例えば概念的には、

```text
Application
  ↓
Observability Runner
  ├─ root span開始
  ├─ UseCase実行
  ├─ Right / Left処理
  ├─ 必要ならerror_type反映
  ├─ 必要ならFeature event記録
  └─ root span終了
```

決めること：

* Runnerが受け取るもの
* Runnerが返すもの
* `ToErrorType` constraintをどのAPIが持つか
* Feature failure eventを誰が生成するか
* Loggingとの接続方法
* Exception時のcleanup

---

### 6. Feature event → `LogSpec` → `LogRecord`

Logging側の中心です。

決めること：

```text
Feature event
    ↓
ToLogSpec
    ↓
LogSpec
    ↓
TraceContext / timestamp / component等を補う
    ↓
LogRecord
```

特に、

* `LogSpec`が何を持つか
* `LogRecord`が何を追加で持つか
* 時刻を誰が付与するか
* `TraceId` / `SpanId`を誰が付与するか
* 発生元を誰が決めるか
* `Logging.Write`がどこまで担当するか

を確定します。

---

### 7. `ToLogSpec` instanceの配置と依存

orphan採用自体は決定済みなので、再検討対象ではありません。

残るのは具体的配置です。

例えば、

```text
ragscope-features
      ↓

integration library
  ToLogSpec SearchEvent

      ↓
ragscope-logging
```

のように、**どのCabal libraryがFeatureとLoggingの両方をimportするか**を決めます。

ここでは、

* module名
* library名
* import方向
* `build-depends`

まで設計します。

---

### 8. Logging package / library / module構成

RS-0022の中心課題の一つです。

少なくとも役割として、

```text
Logging公開API
Logging共通モデル
Logging Runtime
Sink
JSON Adapter
SQLite Adapter
Testing
```

があります。

決めること：

* `ragscope-logging`をどう分割するか
* public / private library
* `exposed-modules`
* `other-modules`
* JSON / SQLiteを別libraryにするか
* RuntimeとSinkをどこに置くか

---

### 9. Tracing package / module構成

概念上は、

```text
RAGScope.Tracing
    ↓
Tracing Port

RAGScope.Tracing.OpenTelemetry
    ↓
Adapter
```

まで決まっています。

残るのは、

* 公開API
* `TraceId`
* `SpanId`
* `TraceContext`
* span開始 / 終了 / Error反映のAPI
* OpenTelemetry型をどこまで内部へ閉じるか
* Cabal依存

です。

---

### 10. Observability package / module構成

Featureから見えるAPIと、内部Runtimeを分けます。

決めること：

```text
Feature
  ↓
RAGScope.Observability

Application / Runner
  ↓
Observability Internal

Observability Internal
  ├─ Logging
  └─ Tracing
```

の正確な境界です。

特に、

* FeatureがLoggingを直接呼ぶのか
* Observability Effect APIを経由するのか
* RunnerとFeature向けAPIの関係
* current `TraceContext`をどう保持するか

を決めます。

---

### 11. Logging Sink

共通Loggingから外部出力までです。

決めること：

* Sink API
* stderr Sink
* memory Sink
* JSON Sink
* SQLite Sink
* Sink差し替え方法
* RuntimeとSinkの依存方向

JSON / SQLiteは同じ`LogRecord`を受け取り、互いに依存しない構造にします。

---

### 12. Logging自身のfailure

これは後半に回すべき項目です。

決めること：

```text
toLogSpec成功
↓
LogRecord生成成功
↓
serialization失敗
Sink書き込み失敗
SQLite transaction失敗
```

などをどう扱うか。

特に、

* UseCase結果へ影響させるか
* root spanへ影響させるか
* 呼び出し元へ返すか
* 握りつぶす場合があるか
* 別経路で報告するか

そして既決定事項として、

```text
Logging自身のfailureを
失敗した同じLogging経路へ再帰的に記録しない
```

を守ります。

---

### 13. 旧構造の扱い

新設計が完成した段階で、

```text
AppError
Result
Observation
ExecutionId
EventId
EventContext
OperationName
LogErrorCategory
ErrorCode
SafeMessage
ToEventSpec
```

など既存構造を一つずつ確認します。

「既存だから残す」ではなく、

```text
新しい全体設計に役割がある → 残す / 変更
役割がない → 削除
```

で判断します。

---

### 14. テスト境界

実装前に、最低限どこをテスト可能にするか決めます。

* `ToErrorType`
* `ToLogSpec`
* RunnerのRight / Left
* root span Error反映
* Feature event → LogRecord
* Runtime差し替え
* memory Sink
* JSON Schema適合
* SQLite往復
* Logging failure
* Exception時のspan cleanup

この設計ができていれば、実装時に「テストのために構造を作り直す」ことを避けられます。

## 最終的な実装開始条件

かなり圧縮すると、**この図を型・module・Cabal依存まで説明できる状態になったら実装開始**です。

```text
Application
    │
    ▼
Observability Runner
    │
    ├─ UseCase
    │     │
    │     ├─ Right result
    │     └─ Left failure
    │           │
    │           └─ ToErrorType
    │                 ↓
    │              ErrorType
    │
    ├─ Tracing
    │     ↓
    │   root span
    │
    └─ Feature failure event
              │
              ▼
          ToLogSpec
              │
              ▼
           LogSpec
              │
              ▼
        Logging.Write
              │
              ▼
          LogRecord
              │
        ┌─────┴─────┐
        ▼           ▼
      JSON        SQLite
        │           │
        └──── Sink ─┘
```

なので、**次の一手はまだExceptionではなく、今やっている`ToErrorType` / `ToLogSpec`の文書化を完了させること**です。

その後、

**`Left failure`の範囲 → 同期Exception → 非同期Exception**

の順で進める、というのが現在地です。
