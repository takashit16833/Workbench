# 実行追跡・構造化ログ実行設計ノート

このノートは、実行フロー、Observability / Logging / Tracingの具体的な接続、Applicationでの組み立て、Runtime API候補、未確定事項など、設計の進行に応じて変わりやすい部分を扱う。

変わりにくい設計前提、責務、Cabal package / library境界は [[実行追跡・構造化ログ設計ノート]]、全体像は [[RAGScope実行追跡・構造化ログ基盤.canvas]]、静的依存は [[実行追跡・構造化ログ静的依存.canvas]] を参照する。

## 現在の実行単位

現在の正本では、次の3つを分ける。

```text
Process lifecycle
│
├─ lifecycle event
│    └─ trace外の構造化ログ
│
└─ User Operation × 0..N
     └─ 1 Operation = 1 trace
          └─ root span
               ├─ routing / command判定
               ├─ input decode / 変換 / validation
               ├─ UseCase span（呼び出した場合）
               │    └─ Feature内部span
               └─ response / output側の結果処理
```

プロセス起動から終了までを1 traceにはしない。CLIが単発型で結果的に1 process = 1 operationになっても、traceの意味は`1利用者操作`のままとする。APIのように1 processで複数操作を受け付ける場合は、操作ごとに別traceを作る。

## Operation root spanの境界

root spanは、利用インターフェースが1件の操作について操作固有の処理を開始する境界で開始する。routing / command判定や入力validationで失敗した操作も追跡するため、それらの成功後から開始する設計にはしない。

終了は、その操作について成功または失敗の結果を確定し、操作固有処理から外側へ制御を戻す境界とする。

```text
operation entry
  ↓ root span開始
routing / command判定
  ↓
input decode / validation
  ↓
UseCase呼び出し（必要な場合）
  ↓
response / output処理
  ↓
OperationResult確定
  ↓ root span終了
operation exit
```

Web APIではprocessの`main`やserver起動ではなく、各requestの操作固有処理へ入る境界がroot span開始点になる。CLIでもprocess lifecycleそのものではなく、1コマンドの操作固有処理を開始する境界を使う。

## OperationResultとUseCaseResult

1回の利用者操作全体は、UseCaseを必要な場合だけ内包する。結果も同じ包含関係で扱う。

```text
1 User Operation
├─ routing / command判定 / 入力処理
├─ UseCase（必要な場合）
│    └─ UseCaseResult
│         ├─ UseCaseSuccess
│         │    └─ Haskell: Right result
│         └─ UseCaseFailure
│              └─ Haskell: Left failure
├─ UseCase後の結果処理
└─ OperationResult
     ├─ OperationSuccess
     └─ OperationFailure
```

`UseCaseResult = UseCaseSuccess | UseCaseFailure`はUseCase実行結果の概念表記である。Haskellでは専用ADTを追加せず、UseCase境界の`Either failure result`で表す。`Right result`が`UseCaseSuccess`、`Left failure`が`UseCaseFailure`に対応する。

`UseCaseFailure`は結果区分であり、具体的なfailure型ではない。たとえば`DenseSearchFailure`はdense検索UseCaseが`UseCaseFailure`となった理由を表す具体型である。具体型はそのUseCaseを所有するFeatureの`RAGScope.<Feature>.Failure`に置く。Featureは所有単位であり、一般的なUseCase結果を`FeatureFailure` / `FeatureResult`とは呼ばない。

`OperationResult = OperationSuccess | OperationFailure`は1回の利用者操作全体の結果区分を示す概念表記である。UseCaseが`UseCaseFailure`となった場合は`OperationFailure`となる。UseCase前後の通常失敗もUseCase固有failureへ変換せず`OperationFailure`の原因として扱う。`UseCaseSuccess`だけでは`OperationSuccess`は確定せず、操作固有処理全体が完了して利用者が依頼した結果が成立したときに`OperationSuccess`となる。

Application / process lifecycleのstartup・shutdown failureは、利用者操作そのものではないため`OperationResult`へ含めない。

### まだここで固定しないこと

次はOperation境界に影響するが、後続の実行・失敗境界設計で決める。

- `OperationResult`の正確なHaskell型・constructorと、外側のfailure型の正確なADT。
- 同期Exceptionを通常の`OperationFailure`へ変換する条件。
- 非同期Exceptionのcleanupと再throw。
- Logging failureをOperationの最終結果へ反映する条件。
- `UseCaseFailure`とLogging failureが同時発生した場合の返却値。

このため、旧`AppError` / `ExecutionFailure` / `ExecutionOutcome`をそのまま新`OperationResult`へ名前変更することはしない。

## UseCase span

RAGScope ApplicationがUseCaseを呼び出す場合は、その呼び出しからApplicationへ制御が戻るまでをroot span配下の子spanとして追跡する。

```text
operation root span
├─ interface processing
├─ UseCase span
│    ├─ Feature内部span
│    └─ ...
└─ post processing
```

UseCaseが呼ばれない場合はUseCase spanを作らない。

UseCase spanのStatusは`UseCaseResult`から決める。

```text
UseCaseSuccess / Right result
→ UseCase span = Unset

UseCaseFailure / Left failure
→ UseCase span = Error + error_type
```

Operation root spanは`UseCaseResult`だけでは決めず、`OperationResult`から決める。

```text
UseCaseFailure + OperationFailure
→ UseCase span Error
→ root span Error

UseCaseSuccess + post-processing OperationFailure
→ UseCase span Unset
→ root span Error

validation OperationFailure / UseCase未呼び出し
→ UseCase spanなし
→ root span Error

OperationSuccess
→ root span Unset
```

## ユースケース失敗ログ

UseCaseが`UseCaseFailure`となった具体的なfailureは、その失敗を表すFeature固有eventとして記録し、UseCase spanへ関連付ける。

```text
Left failure
  ├─ failure値 → ToErrorType → ErrorType → UseCase span Error
  └─ failureを表すFeature event → ToLogSpec → LogSpec → LogRecord
                                              ↑
                                       UseCase spanのTraceContext
```

ここで`failure`は`DenseSearchFailure`などの具体的なUseCase固有failure値であり、`UseCaseFailure`という結果区分そのものではない。同じ具体failureが`OperationFailure`の原因になったというだけで、root spanへ同じ失敗ログをもう1件記録しない。root spanは自身の`OperationResult`に従ってStatusと必要な`error_type`を持つ。

## Lifecycle event

ApplicationやAI推論サービスの起動・終了など、特定の利用者操作へ属さないeventはtrace外ログとして扱う。

```text
ApplicationLifecycleEvent
  ↓ ToLogSpec
LogSpec
  ↓ TraceContextなし
LogRecord
  ↓
Sink
```

Application lifecycle eventの意味はApplication側、AI推論サービスのlifecycle eventはAI推論サービス側が所有する。CLI / API固有eventは各利用インターフェース側が所有する。

Logging基盤をLifecycle LoggingとOperation Loggingの2系統へ分けない。同じ`ToLogSpec → LogSpec → LogRecord → Sink`を使い、違いはLogRecord完成時にTrace Contextが存在するかどうかとする。

## Trace Contextの表現

論理契約では、ログは次のどちらかだけを取る。

```text
TraceContextあり
  = TraceId + SpanId

TraceContextなし
  = trace_id / span_idともに存在しない
```

Haskellでも`Maybe TraceId`と`Maybe SpanId`を独立させて片方だけの状態を作らない。第一候補は、次のようにTrace Context全体を任意値にする形である。

```haskell
traceContext :: Maybe TraceContext
```

これは実装候補であり、正確なrecord fieldや型名はコードで確定する。

## Observability APIの再設計

旧候補の`withRootSpan :: m a -> m a`を「UseCaseをroot spanで包むAPI」として使う案は破棄する。Operation root spanはInterface境界から開始する必要があるため、Runnerは少なくとも次の2種類のspan境界を表現できる必要がある。

```text
Operation root span
UseCase / Feature child span
```

APIの概念候補は次のようになる。

```haskell
withOperationSpan :: ... -> m a -> m a
withSpan          :: ... -> m a -> m a
currentTraceContext :: m TraceContext
markCurrentSpanError :: ToErrorType failure => failure -> m ()
```

関数名と正確な型は未確定である。重要なのは次である。

- Operation root spanをUseCase呼び出しより外側から開始できる。
- UseCase spanをrootの子として開始できる。
- Feature内部spanはcurrent spanを親にできる。
- current TraceContextはtrace内eventのLoggingで利用できる。
- trace外のLifecycle Loggingはcurrent TraceContextを前提にしない。

`RAGScope.Observability`をFeature専用APIと固定しない。Interface / Application / Featureで必要な操作が異なる場合は、公開moduleやclassを責務ごとに分ける。正確な分割はCabal依存と合わせて決める。

## Featureから見えるObservability Effect

Feature / UseCaseからは引き続き、event発生や内部spanを表す抽象操作だけを見せる。

```haskell
class Monad m => MonadObservability event m where
  emit :: event -> m ()
```

- `emit`は「Feature eventが起きた」という宣言であり、ログ出力命令ではない。
- `emit`の公開型へ`ToLogSpec`を出さない。
- FeatureはLogging、Tracing backend、Trace Contextを直接扱わない。
- `withSpan`を同じclassへ含めるか別classへするかは未確定。

productionではApplication compositionがFeature eventをLoggingへ接続し、testではFeature eventをmemoryへ保持するなど別実装へ差し替えられるようにする。

## eventからLogRecordまで

### trace内event

```text
Feature / Interface event
  ↓
ToLogSpec
  ↓
LogSpec
  + current TraceContext
  + timestamp / component
  ↓
LogRecord
  ↓
Sink
```

### trace外event

```text
Lifecycle event
  ↓
ToLogSpec
  ↓
LogSpec
  + TraceContextなし
  + timestamp / component
  ↓
LogRecord
  ↓
Sink
```

`RAGScope.Logging.Write`がTraceContextを必須引数として受ける旧候補は見直す必要がある。候補は次のどちらかである。

```text
A. write :: Maybe TraceContext -> event -> ...
B. traced / untracedの公開APIを分け、内部で同じRuntimeへ合流する
```

不正な「TraceIdだけ / SpanIdだけ」を型で作れず、呼び出し側がLifecycleとOperationを自然に扱える方を選ぶ。

## Logging Runtime

共通Runtimeは、event種別に関係なく`LogSpec`を`LogRecord`へ完成してSinkへ渡す。

```text
LogSpec
+ timestamp
+ component
+ optional TraceContext
  ↓
completeLogRecord
  ↓
LogRecord
  ↓
writeLogRecord
  ↓
Sink
```

JSON / SQLiteは同じ`LogRecord`から独立して投影する。Trace Contextがないログも同じ外部表現契約へ投影できる。

## ToLogSpec instanceの配置

Feature eventは引き続きFeature型とLogging契約を接続するintegration moduleで`ToLogSpec` instanceを定義する。

```text
RAGScope.<Feature>.Event
        ↓
RAGScope.<Feature>.Logging
        ↓ ToLogSpec
RAGScope.Logging
```

Feature / UseCaseは`RAGScope.<Feature>.Logging`をimportしない。production composition側が必要なorphan instanceへのimport chainを作る。

Lifecycle eventについてもevent定義の所有者とLogging変換を分離する。例えばApplication lifecycle型を`RAGScope.Application.*`が所有する場合、Logging変換の配置はApplication側のintegration責務として決め、Logging共通packageへApplication固有eventを持ち込まない。

## Exception設計へ進む前の確定事項

ここまでで次は決定済みとして扱う。

1. UseCase実行結果は概念上`UseCaseResult = UseCaseSuccess | UseCaseFailure`と表す。
2. HaskellのUseCase境界は`Either failure result`であり、`Right result = UseCaseSuccess`、`Left failure = UseCaseFailure`と対応する。
3. `UseCaseFailure`は結果区分であり、具体failure型は`DenseSearchFailure`などUseCase固有の型としてFeatureが所有する。
4. 利用者操作全体はUseCaseを必要な場合だけ内包し、概念上`OperationResult = OperationSuccess | OperationFailure`と表す。
5. `UseCaseFailure`は`OperationFailure`の原因の1つとなる。`UseCaseSuccess`だけでは`OperationSuccess`は確定しない。
6. routing / validation / post-processing failureも`OperationFailure`側で扱い、UseCase固有failureへ変換しない。
7. lifecycle failureは`OperationResult`へ含めない。
8. 正確な`OperationResult` / Operation failureのHaskell ADTは後続のApplication実行・失敗境界で確定する。

この意味上の境界を前提に同期Exception・非同期Exceptionを設計する。
