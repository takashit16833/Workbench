# 実行追跡・構造化ログ実行設計ノート

このノートは、実行フロー、Effectの具体化、Applicationでの組み立て、Runtimeの具体形、未確定事項など、設計の進行に応じて変わりやすい部分を扱う。

変わりにくい設計前提、Cabal package / library / module境界、用語と責務は [[実行追跡・構造化ログ設計ノート]] を参照する。静的依存関係は [[実行追跡・構造化ログ静的依存.canvas]] を参照する。設計判断の経緯は [[実行追跡・構造化ログ設計日誌]] を参照する。

## ApplicationからUseCaseまで

現在案では、`main`がApplicationを起動し、`RAGScope.Application.Execution`がproduction用の組み立てを`RAGScope.Application.Observability`へ任せる。`Application.Observability`は`RAGScope.Observability.Runner`をApplication向けFacadeとして使い、ApplicationがUseCaseを呼び出す時点からUseCaseが`Either`を返してApplicationへ制御が戻る境界までをroot spanとして追跡する。

Runnerの後ろでは`RAGScope.Observability.Internal.*`がcurrent spanとroot / child span lifecycleを管理する。ApplicationはInternal moduleを直接importしない。

擬似コードでは次のイメージになる。

```haskell
main =
  runApplication

runApplication =
  Application.Execution.run someUseCase

Application.Execution.run useCase = do
  result <- Application.Observability.runObserved useCase
  handleUseCaseResult result

Application.Observability.runObserved useCase =
  Observability.Runner.withRootSpan useCase

someUseCase =
  withSpan "search" $ do
    emit SearchStarted
    search
    emit SearchCompleted
```

`Application.Observability.runObserved`、`handleUseCaseResult`、`Observability.Runner.withRootSpan`などの関数名は現時点の擬似名である。重要なのは、root spanがApplicationによるUseCase呼び出しで開始し、UseCaseが`Right`または`Left`を返してApplicationへ制御が戻る境界で終了することである。UseCase呼び出し終了後にApplicationが行う表示やHTTPレスポンスへの変換などの後続処理はroot spanに含めない。`Left`を返す場合にroot spanのErrorとユースケース失敗eventを境界で反映してからspanを終了するための正確なRunner APIと呼び出し順は未確定である。

流れだけ抜くと次のようになる。

```text
main
 ↓
Application.Execution
 ↓
Application.Observability
 ↓
Observability.Runner
 ↓
Observability.Internal.*
 ↓ root spanを作り現在spanとして保持
UseCase
 ↓ Right / Leftを返す
UseCaseからApplicationへ制御が戻る境界
 ↓ 必要ならユースケースの失敗に必要な観測情報を反映
Observability.Internal.*がroot spanを終了
 ↓
Application.Executionが後続処理を行う
```

`Application.Execution`は「どのUseCaseを実行するか」と、UseCaseから返った`Either`を受け取った後のApplication側の処理を扱う。`Application.Observability`はObservability / Logging / production Tracing Adapterなど複数の部品をRAGScopeのproduction環境として接続し、UseCase呼び出し境界の観測を組み立てる。`Observability.Runner`はApplicationに必要なObservability実行APIだけを公開し、`Observability.Internal.*`がroot / child spanとcurrent spanの具体管理を担当する。

`Application.Execution`自身が`TraceId` / `SpanId`やLoggerをUseCaseへ渡したり、spanを直接管理したりはしない。

## UseCaseから見えるObservability Effect

Feature / UseCaseから見える観測用APIは`RAGScope.Observability`から提供し、event発生の操作はtypeclassで表す。

```haskell
class Monad m => MonadObservability event m where
  emit :: event -> m ()
```

UseCaseは例えば次のように、Feature eventを観測できる能力だけを要求する。

```haskell
search
  :: MonadObservability SearchEvent m
  => m ()
search = do
  emit SearchStarted
  ...
  emit SearchCompleted
```

この型では`SearchEvent`はSearch UseCaseが扱うeventとして固定し、`m`は実行環境に応じて具体化できるよう型変数のまま残す。

- `emit`は「このFeature eventが起きた」という宣言であり、UseCaseにとってログ出力命令ではない。
- `emit`の公開型に`ToLogSpec`を出さない。UseCaseはFeature eventがLoggingへ変換可能かどうかを知らない。
- `MonadObservability event m`は「その`event`をその`m`で観測できる」という能力を表す。
- production / testなど具体的な`m`ごとにinstanceを変えることで、同じUseCaseの`emit`を異なる方法で実行できる。
- `withSpan`も`RAGScope.Observability`から提供する。`MonadObservability`の同じclassへ含めるか、別classへ分けるか、正確な引数型をどうするかはまだ未確定。
- Feature / UseCaseのCabal libraryは`ragscope-error`と`ragscope-observability`のmain libraryへ依存し、`ragscope-observability:runtime`やLogging、Tracingのlibraryへは依存しない。`ragscope-error`はFeature failureとその`ToErrorType` instanceのために使う。
- Effectを表すための専用effect libraryは採用せず、今回のObservability境界はtypeclass方式を採用する。現在spanの保持にReaderT相当の環境と`local`のような仕組みを使うかは別途検討する。

## Application / Observability / Tracing / Loggingの責務分担

現在案では次のように役割を分ける。

```text
Feature / UseCase
  │
  │ withSpan / emit
  ▼
RAGScope.Observability
  │ Feature向けEffect API
  ▼
RAGScope.Application.Observability
  ├─ Observability.RunnerでUseCase呼び出し境界のroot spanを組み立てる
  ├─ production Tracing Adapterを選んでRuntimeへ渡す
  ├─ UseCaseが返したEitherを境界で必要な観測情報へ反映する
  └─ emitでは現在のTraceContextとeventをLoggingへ渡す
        │
        ├─→ RAGScope.Observability.Runner
        │     └─ Internal Runtimeを隠したApplication向けFacade
        │
        └─→ RAGScope.Logging.Write
              └─ ToLogSpecでLogSpecへ変換しLogging Runtimeへ渡す

RAGScope.Observability.Runner
  ↓
RAGScope.Observability.Internal.*
  ↓ span操作を要求
RAGScope.Tracing               -- Tracing Port
  ↑ production実装
RAGScope.Tracing.OpenTelemetry -- Adapter
  ↓
OpenTelemetry SDK
```

責務を具体的に分けると次のとおり。

- **RAGScope.Observability / Observability Effect API**: UseCaseが`withSpan` / `emit`を呼べる公開境界。Logging固有制約、Runner、Runtime、Tracing backendを公開契約へ出さない。単なる公開APIを広くPortと呼ばない方針に合わせ、Observability Portとは呼ばない。
- **RAGScope.Application.Observability**: productionの`MonadObservability` instanceと、productionでObservability Runnerを使うための組み立てを持つ。UseCaseが返した`Either`をApplicationへ引き渡す境界で必要な観測情報へ反映し、`emit`では現在の`TraceContext`を取得して`event`とともにLoggingの公開入口へ渡す。productionのTracing Adapterもcomposition側で選ぶ。
- **RAGScope.Application.LoggingInstances**: productionで使う`RAGScope.<Feature>.Logging`をimportし、Feature固有の`ToLogSpec` orphan instanceへimport chainを作る。
- **RAGScope.Observability.Runner**: Applicationから使うFacade。root span付き実行、current `TraceContext`取得、current spanへのError反映など、Applicationが必要な操作だけを公開する。失敗反映の公開境界では`ToErrorType failure => failure`を受け取り、Runner内で`toErrorType`を適用する。
- **RAGScope.Observability.Internal.***: current spanを保持し、root / child span lifecycleとparent復元を実装する。Runnerから受け取った`ErrorType`とcurrent spanを組み合わせ、Tracing Portへspan状態更新を要求する。LoggingやOpenTelemetry Adapterを知らない。
- **RAGScope.Tracing / Tracing Port**: Observability Internal Runtimeが要求できるspan開始・終了、状態更新などの操作をRAGScopeの抽象契約として定義する。OpenTelemetry SDKには依存しない。Portは「呼び出し側が必要とする抽象操作を定義し、具体実装を差し替える境界」という役割名であり、module suffixではない。
- **RAGScope.Tracing.OpenTelemetry / Adapter**: Tracing PortをOpenTelemetryで実装するproduction Adapter。OpenTelemetry固有型やSDKを他moduleへ漏らさない。
- **Tracing Core**: `TraceId` / `SpanId` / `TraceContext`などの純粋な値を定義する。spanの開始・終了は行わない。
- **RAGScope.Logging.Write**: `ToLogSpec a`を満たす値と`TraceContext`を受け取り、`toLogSpec`で`LogSpec`へ変換してLogging Runtimeへ渡す。Logging subsystemの公開APIであり、現在設計ではLogging Portとは呼ばない。
- **Logging Runtime**: `LogSpec`へ実行時情報を加えて`LogRecord`を完成し、完成した`LogRecord`をSinkへ渡す。

この分担では`Observability Internal -> Logging`と`Observability Internal -> OpenTelemetry Adapter`という静的依存は作らない。

## Observability RunnerとInternal Runtime

`RAGScope.Observability.Runner`はApplication向けFacadeであり、内部状態やTracing backendの具体型をApplicationへ漏らさない。

現在は次のような操作をRunnerから公開することを第一候補とする。

```haskell
withRootSpan :: m a -> m a
currentTraceContext :: m TraceContext
markCurrentSpanError :: ToErrorType failure => failure -> m ()
```

関数名と正確な型全体は未確定である。ただし、失敗をspanへ反映する公開境界では具体的なFeature failure型へ固定せず`ToErrorType failure => failure`を受け取り、Runner内で`toErrorType`を適用して`ErrorType`へ共通化した後にInternal Runtimeへ渡す方針は確定とする。

```text
Feature固有failure
  ↓ Observability.Runner
  ↓ toErrorType
ErrorType
  ↓ Observability.Internal.*
  ↓ current spanと組み合わせる
current span + ErrorType
  ↓ Tracing Port
span状態更新
```

`currentTraceContext`の公開型に`TraceContext`が現れるためRunner moduleは`RAGScope.Tracing.Context`へ、失敗反映APIの制約に`ToErrorType`が現れるため`RAGScope.ErrorType`へ静的に依存する。これらの依存は静的依存Canvasにも明示する。

Internal Runtimeは次を担当する。

```text
- root spanの開始・終了
- current spanの保持
- child spanへの切り替え
- body終了後のparent復元
- Runnerから受け取ったErrorTypeとcurrent spanをTracing Portへ渡す
- Tracing Portへのspan操作要求
```

Internal Runtimeがどの環境型を持つか、current spanをReaderT / local相当で表すかなどは未確定である。

Cabal上は`ragscope-observability:runtime`がprivate `internal` libraryへ依存し、Applicationはpublic `runtime`だけを利用する。

## Tracing PortとOpenTelemetry Adapter

`RAGScope.Tracing`は具体backendを実行するmoduleではなく、Observability Runtimeが要求するTracing Portとする。

PortはHaskell上の特定の構文名ではない。RAGScopeでは「呼び出し側が必要とする抽象操作を定義し、その具体実装を境界の向こう側で差し替えるもの」をPortと呼ぶ。TracingではObservability Runtimeが「spanを開始する」「spanを終了する」「spanへ`ErrorType`を関連付けてErrorへ更新する」といった操作だけを要求し、OpenTelemetry SDKのAPIを直接知らない。

概念上は次の関係になる。

```text
Observability.Internal.*
  │ current span + ErrorTypeなど
  ↓ Tracingの抽象操作を要求
RAGScope.Tracing               -- Tracing Port
  ↑ production実装
RAGScope.Tracing.OpenTelemetry -- Adapter
  ↓ OpenTelemetry固有APIへ変換
OpenTelemetry SDK
```

productionではApplication compositionが`RAGScope.Tracing.OpenTelemetry`からPort実装を作り、Observability Runtimeへ渡す。

Portをtypeclassで表すかrecord of functionsで表すか、span handleをどの型で表すか、AdapterをRuntime環境へどのように注入するかは未確定である。ただし、Observabilityの`internal` libraryは`ragscope-tracing`のmain / `core`だけへ依存し、`ragscope-tracing:otel`へは依存しない。

`RAGScope.Observability`はFeature向けEffect API、`RAGScope.Logging.Write`はLogging subsystemの公開APIとして扱う。これらは公開境界であることだけを理由にPortとは呼ばない。将来Logging Sinkのように抽象操作と差し替え可能な実装の境界を設計する場合は、その役割がPortに相当するかを個別に判断する。

## root span

Observability Internal Runtimeは、ApplicationがUseCaseを呼び出す境界をroot spanとして追跡する。root spanはApplicationがUseCaseを呼び出す時点で開始し、UseCaseが`Right`または`Left`を返してApplicationへ制御が戻る境界で終了する。UseCase呼び出し終了後のApplication固有処理はroot spanに含めない。

1. Internal RuntimeがTracing Portへroot span開始を要求する。
2. root spanをcurrent spanとして保持する。
3. UseCaseを実行する。
4. UseCaseが`Right`または`Left`を返す。
5. `Left`なら、その戻り値をApplicationへ引き渡す境界でroot spanのErrorとユースケース失敗eventに必要な情報を反映する。
6. Internal RuntimeがTracing Portへroot span終了を要求する。
7. Application Executionはroot span終了後に、UseCaseの戻り値に対するApplication固有の後続処理を行う。

この境界を保ったまま、`Left`の`error_type`をroot spanへ設定しユースケース失敗eventを記録してからroot spanを終了するためのRunnerの正確な呼び出し順は未確定である。Observability Internal Runtime自身がUseCase failureの意味を判定する設計にはしない。

1 UseCase実行を1 traceとして扱う。UseCaseはroot spanの`TraceId` / `SpanId`を直接受け取らない。

## child span

Feature / UseCaseが内部処理を独立して観測したい場合は`withSpan`を使う。

```haskell
withSpan "search" $ do
  withSpan "db" $ do
    ...
```

この場合は次のspan treeになる。

```text
root
└─ search
   └─ db
```

一方、順番に実行すれば兄弟spanになる。

```haskell
withSpan "search" $ do
  ...

withSpan "db" $ do
  ...
```

```text
root
├─ search
└─ db
```

productionの`withSpan`実装はRunner / Internal Runtimeへ処理を任せる。Internal Runtimeは現在spanを親としてTracing Portへchild span開始を要求し、そのbodyの間だけchildをcurrent spanにする。body終了後は元の親spanへ戻す。この切り替えと復元の具体実装はInternal Runtimeへ閉じる。

## emitからLogRecordまで

productionで`emit`されたeventを構造化ログへ記録する流れは次のとおり。

```text
UseCase
  │ emit event
  ▼
Application.Observabilityのproduction MonadObservability instance
  │
  ├─ Observability.Runnerから現在のTraceContextを取得
  │
  └─ event + TraceContextをLogging.Writeへ渡す
        │
        │ toLogSpec event
        ▼
      LogSpec
        │
        ▼
      Logging Runtime
        │ 実行時情報を加える
        ▼
      LogRecord
        │
        ▼
      Sink
```

production instanceの概念コードは次の形を第一候補とする。

```haskell
instance ToLogSpec event
      => MonadObservability event AppM where
  emit event = do
    context <- Observability.Runner.currentTraceContext
    Logging.Write.write context event
```

`currentTraceContext`と`write`は責務を示す擬似名であり、正確なAPIは実装設計で確定する。

重要なのは次の4点である。

1. `Application.Observability`は`event`を`LogSpec`へ変換しない。
2. Applicationは`Observability.Internal.*`を直接importしない。
3. Observability Internal Runtimeは`LogSpec`を受け取らず、Logging Runtimeへ中継もしない。
4. `toLogSpec`を呼ぶのはLogging packageの公開入口である。

## ToLogSpecとLoggingの境界

Feature eventから`LogSpec`への変換には`ToLogSpec`を採用する。

```haskell
class ToLogSpec event where
  toLogSpec :: event -> LogSpec
```

Feature側では次の関係とする。

```text
RAGScope.Search.Event
  └─ SearchEventを定義

RAGScope.Search.Logging
  └─ instance ToLogSpec SearchEvent
```

`RAGScope.Logging.Write`は具体的な`SearchEvent`を知る必要がない。

```haskell
write
  :: ToLogSpec a
  => TraceContext
  -> a
  -> m ()
```

概念上は次の処理を行う。

```haskell
write context value = do
  let spec = toLogSpec value
  record <- Runtime.completeLogRecord context spec
  Runtime.writeLogRecord record
```

このコードも責務分割を示す擬似コードである。timestampの取得位置、`completeLogRecord`が純粋関数になるか、Sinkをどのように渡すかなどは未確定である。

`writeLogRecord`という名前を使う場合は、完成した`LogRecord`を受け取ってSinkへ渡す関数に使う。`LogSpec`を受け取る関数へ`writeLogRecord`という名前は付けない。

この構造では、`LogSpec`は`ragscope-logging` packageの中で生成され、Observability側へ出ない。

## Feature固有ToLogSpec instanceの有効化

`RAGScope.<Feature>.Logging`に置く`ToLogSpec <FeatureEvent>`は、`ToLogSpec`のclassも`FeatureEvent`型もそのmodule自身では定義していないためorphan instanceになる。

例えば次の構成である。

```haskell
-- RAGScope.Search.Event
data SearchEvent
  = SearchStarted
  | SearchCompleted
```

```haskell
-- RAGScope.Search.Logging
instance ToLogSpec SearchEvent where
  ...
```

UseCaseは`RAGScope.Search.Logging`をimportしない。

```haskell
search
  :: MonadObservability SearchEvent m
  => m ()
```

productionで`search`を`AppM`として使うと、GHCは次のinstanceを使う。

```haskell
instance ToLogSpec event
      => MonadObservability event AppM
```

このとき`event = SearchEvent`なので、GHCには`ToLogSpec SearchEvent`が必要になる。そのinstanceへimport chainを作るため、production用に次のmoduleを置く。

```haskell
module RAGScope.Application.LoggingInstances () where

import RAGScope.Search.Logging ()
import RAGScope.Index.Logging ()
-- productionで使うFeature Loggingを追加する
```

`RAGScope.Application.Observability`からこのmoduleをimportする。

```haskell
import RAGScope.Application.LoggingInstances ()
```

Haskellでは`import M ()`でも`M`から見えるinstanceはimportされ、importの連鎖上にあるinstanceも利用可能になる。そのため、値や型をApplication側へ持ち込まずにFeature Loggingのinstanceだけをproduction compositionへ含められる。

この構成により次を保つ。

- UseCaseはFeature Loggingをimportしない。
- `ragscope-logging` packageはFeature固有moduleをimportしない。
- productionで使用するFeature Loggingの一覧は`Application.LoggingInstances`から追える。
- 必要な`ToLogSpec <FeatureEvent>`が欠けていればコンパイル時に検出できる。

orphan instanceは無制限に許可せず、Feature eventとLogging契約を接続する`RAGScope.<Feature>.Logging`に限定する。`ToErrorType` instanceはこれと異なり、Feature failure型を定義する`RAGScope.<Feature>.Failure`へ同居させるためorphanにしない。

## Logging Runtime

Logging Runtimeは`LogSpec`を受け取り、`LogRecord`を完成してSinkへ渡す内部処理を担当する。

現在は次の2操作へ分けることを第一候補とする。

```text
LogSpec + TraceContext + その他の実行時情報
  ↓
completeLogRecord
  ↓
LogRecord
  ↓
writeLogRecord
  ↓
Sink
```

- `completeLogRecord`: `LogSpec`へtimestamp、component、`TraceId` / `SpanId`などを加え、`LogRecord`を完成する。
- `writeLogRecord`: 完成した`LogRecord`をSinkへ渡す。

正確な型と、timestampなどをどこで取得して引数へ渡すかは未確定である。

Cabal上は`RAGScope.Logging.Write`を`ragscope-logging` main libraryから公開し、`RAGScope.Logging.Runtime` / `Sink` / `JSON` / `SQLite`はprivate `internal` libraryへ置く。

## ユースケースの失敗

UseCaseが失敗を`Left failure`として返した場合、同じ`error_type`をroot spanとユースケース失敗ログの両方へ関連付ける。`ErrorType`は共有package `ragscope-error`の`RAGScope.ErrorType`で定義し、`failure`からは純粋な`toErrorType`で得る。

Observability Internal Runtime自身がユースケースの失敗の意味を判定したり、ユースケース失敗ログを記録したりはしない。UseCaseが返した`Left failure`をApplicationへ引き渡す境界で、Application Observabilityがroot spanへの失敗反映とユースケース失敗eventの記録を組み立てる。

```text
root span開始
  ↓
UseCase実行
  ↓
Left failureを返す
  ↓ UseCaseからApplicationへ制御が戻る境界
Application.Observability
  ├─ failureをObservability.Runnerの失敗反映APIへ渡す
  │    ↓ RunnerでtoErrorType
  │  ErrorType
  │    ↓ Observability.Internal.*
  │  current span + ErrorType
  │    ↓ Tracing Port
  │  root spanをErrorへ更新
  │
  └─ Feature固有のユースケース失敗eventを作り、現在のTraceContextとLogging.Writeへ渡す
       ↓ ToLogSpec <FeatureEvent>
     LogSpec
       ↓
     ユースケース失敗ログ
  ↓
root span終了
```

ユースケース失敗ログは特別な共通failureログ型ではなくFeature eventとして表す。検索機能なら`SearchEvent`のユースケース失敗を表すconstructorを使い、他の検索eventと同じ`ToLogSpec SearchEvent`で`LogSpec`へ変換する。具体的なconstructor名と、そのeventがFeature failureそのものを保持するか変換済み情報を保持するかはまだ未確定である。

`toErrorType`をApplicationで一度だけ呼んでLogging / Tracingへ配る設計には固定しない。`ErrorType`を必要とする公開境界が`ToErrorType failure => failure`を受け取り、自分の変換境界で`toErrorType`を適用して、その下位層へ`ErrorType`だけを渡す。root spanの失敗反映ではObservability Runnerがこの役割を持つ。Logging側はFeature eventから`ToLogSpec`で`LogSpec`へ変換する責務を保ち、ユースケース失敗eventの`error_type`をどの値から得るかはeventの具体形と合わせて確定する。

Logging自身の失敗は、失敗した同じLogging経路へ再帰的に記録しない。

## テスト時の差し替え

UseCaseの型はproduction / testで共通にする。

```haskell
search
  :: MonadObservability SearchEvent m
  => m ()
```

productionでは`m`が`AppM`などの実行型へ具体化され、`Application.Observability`に置いたproduction用`MonadObservability` instanceが選ばれる。

testでは別の`m`とinstanceを用意できる。例えば`SearchEvent`をそのままmemoryへ保持する実装なら、`ToLogSpec SearchEvent`を要求する必要はない。

```text
同じsearch
  ├─ production m → Logging.Write → LogRecord → Sink
  └─ test m       → Feature eventをmemory保持
```

これにより、Feature / UseCaseのテストでOpenTelemetryやstderr出力、`LogSpec`への変換を必須にしない。

Tracing側もPortとAdapterを別libraryにするため、Observability Internal RuntimeのテストではOpenTelemetry Adapterを使わず、テスト用Tracing実装へ差し替えられる構造を目指す。
