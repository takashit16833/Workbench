# 実行追跡・構造化ログ設計日誌

実行追跡・構造化ログ設計で、途中の判断、見つかった問題、設計レビューで得た観点を残す。

現在採用している設計は [[実行追跡・構造化ログ設計ノート]]、静的依存は [[実行追跡・構造化ログ静的依存図]] を参照する。

## 2026-09-03 Featureを独立概念から外しUseCaseへ統合する

### 変更前

UseCaseとは別に`Feature`を設計・実装上の所有単位として置き、UseCase本体、failure、event、依存record、Logging変換をFeatureが所有する構造としていた。Cabalでは`ragscope-features`をUseCase側のprivate library候補としていた。

### 問題

UseCaseはすでに、利用者の目的を実現する1回の実行境界と、その結果を`Either failure result`で返す境界として定義されている。一方、FeatureはUseCaseとその周辺型・依存をまとめる所有単位として使われており、UseCaseとは別にFeatureを置くことで新しい実行境界、型安全性、静的依存制約が増えるわけではなかった。

そのため、`Feature`と`UseCase`のどちらがfailure、event、依存record、Logging変換を所有するのかを言い分ける必要が生じ、同じ責務を二つの概念で説明する状態になっていた。

### 採用した設計

`Feature`を独立した設計・実装概念としては使用せず、UseCaseを所有単位とする。

UseCaseはUseCase本体に加えて、そのUseCase固有のfailure、event、依存record、`event -> LogSpec`のLogging変換を所有する。Cabalのprivate library候補は`ragscope-features`から`ragscope-use-cases`へ変更し、module候補も`RAGScope.<UseCase>.*`へ統一する。

文書上の`design/features/`階層も削除し、UseCase内部処理である`文書処理設計.md`は`design/`直下へ置く。Embedding生成や文書チャンク化など、UseCaseを構成する処理はUseCaseとは別のトップレベルUseCaseへ昇格させず、UseCase内部処理として扱う。

### 履歴の扱い

この日誌の過去エントリでは、その時点で実際に検討していた`Feature`、`ragscope-features`、`RAGScope.<Feature>.*`などの名称をそのまま残す。現在採用している名称へ過去記録を遡及的に書き換えない。

この判断以降の現在設計はUseCaseを所有単位として扱い、最新状態は設計ノートと静的依存図を参照する。

## 2026-09-03 型付きLoggerと明示的な純粋変換を採用する

### 変更前

所有者定義eventから`LogSpec`への変換を`ToLogSpec`型クラスで表し、Feature eventのorphan instanceを`RAGScope.<Feature>.Logging`へ置いていた。本番構成では`RAGScope.Application.LoggingInstances`がinstance moduleを`import ... ()`で読み込む案だった。

### 採用した設計

Loggingの公開能力は`Logger m event`と`record`で表す。`Logger m`には`Contravariant` instanceを定義する。Logging Runtimeは`Logger m LogSpec`を作り、event所有側は`event -> LogSpec`の名前付き純粋関数を提供する。Application composition rootが両者を`contramap`で合成し、利用側ごとのLoggerを作る。

Feature / Operationは`record logger event`だけを呼び、`LogSpec`、`LogRecord`、Runtime、Sinkを扱わない。trace内eventとtrace外eventで公開操作を分けず、Runtimeが記録時のcurrent Trace Contextから判定する。

### 削除する構造

- `ToLogSpec`型クラスとFeature eventのorphan instance
- `RAGScope.Application.LoggingInstances`とinstance読み込み専用`import ... ()`
- Loggingで任意eventを受けるための`RankNTypes`
- `RAGScope.Logging.Write`

### 依存への影響

`ragscope-features`は記録箇所で`Logger` / `record`を、`RAGScope.<Feature>.Logging`で`LogSpec`を利用する。Application composition rootはLogging Runtime、Feature固有変換、`Logger`、`contramap`を利用する。`RAGScope.Logging`を公開するlibraryとcomposition rootは`contravariant` packageへ直接依存する。

### 継続する論点

Feature別Loggerを`AppEnv`へ直接持たせるかFeature単位の依存recordへまとめるか、Sink failureをどの内部経路で通知・保持するか、logging failureをOperation結果へどう反映するかは、この判断では確定していない。

## 2026-09-02 OpenTelemetry AdapterをApplication側のprivate libraryへ移す

### 変更前

`ragscope-tracing` package内にpublic `otel` libraryを置き、`RAGScope.Tracing.OpenTelemetry`がTracing Portを実装する案にしていた。

```text
ragscope-tracing
├─ public: core
├─ public: main
└─ public: otel
     └─ RAGScope.Tracing.OpenTelemetry
          → OpenTelemetry SDK
```

Applicationは別packageからこのAdapterを使うため、具体実装である`otel` libraryとmoduleをpackage外へ公開する必要があった。

### 問題

`RAGScope.Tracing`はObservability Runtimeが要求する抽象操作を定義するPortであり、OpenTelemetryはそのPortをRAGScopeアプリケーションの本番環境で実装する具体手段である。

具体AdapterをPortと同じpackageへ置くと、`ragscope-tracing` package自体がOpenTelemetry SDKへ依存し、Applicationから具体Adapterを取得するためだけにAdapterをpublicにする必要がある。Portを利用するObservability RuntimeにはOpenTelemetry SDKもAdapterの公開moduleも必要ない。

### 採用した設計

`ragscope-tracing`はPortとTrace Context契約だけを公開する。

```text
ragscope-tracing
├─ public: core
│   └─ RAGScope.Tracing.Context
└─ public: main
    └─ RAGScope.Tracing
```

OpenTelemetry具体実装は`ragscope` package内のprivate libraryへ移す。

```text
ragscope
├─ private: ragscope-features
├─ private: ragscope-application
└─ private: ragscope-tracing-otel
     └─ RAGScope.Application.Tracing.OpenTelemetry
          ├─→ RAGScope.Tracing
          ├─→ RAGScope.Tracing.Context
          └─→ OpenTelemetry SDK
```

`ragscope-application`は`ragscope-tracing-otel`を使って本番用の`RAGScope.Tracing`実装を組み立てる。OpenTelemetry SDKへ直接依存するのは`ragscope-tracing-otel`だけとし、Feature、Observability Runtime、`ragscope-tracing` packageからSDKをimportできない構造にする。

### 静的依存図への影響

全体図では、`ragscope-tracing`から`otel` libraryを削除し、`ragscope` packageにprivate `ragscope-tracing-otel`を追加する。

module依存は依存元moduleが属する詳細図に1回だけ載せるため、`RAGScope.Application.Tracing.OpenTelemetry`を依存元とするTracing Port / Trace Context / OpenTelemetry SDKへの矢印はApplication・Feature図へ置く。Observability・Tracing図にはObservability / Tracing packageを依存元とする矢印だけを残す。

2026-08-29の「package境界を8 packageから4 packageへ整理する」にある`ragscope-tracing`のpublic `otel` libraryは、この判断で置き換えられた。

## 2026-09-01 Operation固有のfailure ADTを共通`OperationFailure`へ置き換える

### 変更前

利用者操作ごとに、その操作で発生し得る具体的なfailureを列挙した型を定義していた。

```haskell
data DenseSearchOperationFailure
  = DenseSearchInputFailure InputFailure
  | DenseSearchUseCaseFailure DenseSearchFailure
  | DenseSearchOutputFailure OutputFailure
```

Operation境界は`Either operationFailure result`とし、Operation固有のfailure型ごとに`ToErrorType` instanceを定義していた。instanceではconstructorをpattern matchし、中のfailure値を`toErrorType`へ渡していた。

### 確認したこと

Operation内では、UseCase、入力変換・検証、結果処理がfailureを返した時点で、具体的なfailure値をそのまま扱える。そこでUseCase span、失敗ログ、利用者向け結果など、具体的なfailure値を必要とする処理を実行できる。

一方、Operation全体の結果を確定してOperation境界の外側へ返したあとに必要なのは、操作全体が失敗したことと、その失敗理由に対応する`ErrorType`を取得できることである。Operation境界の外側で`DenseSearchFailure`や`InputFailure`などの具体型へ戻して分岐する設計要求は正本にない。

そのため、`DenseSearchUseCaseFailure`などのconstructorは、中のfailure値を取り出して`toErrorType`を呼ぶためだけに残っていた。

### 採用した設計

すべてのトップレベルな利用者操作で、同じ`OperationFailure`型を使う。

```haskell
data OperationFailure where
  OperationFailure
    :: ToErrorType failure
    => failure
    -> OperationFailure
```

UseCaseが`Left failure`を返した場合、Applicationはその具体的なfailure値を受け取った場所で必要な処理を行う。そのあと、利用者操作自体も失敗として終了する場合は次を返す。

```haskell
Left (OperationFailure failure)
```

UseCase呼び出し前後に発生した通常のfailureも同じ形で返す。具体的なfailureを先に`ErrorType`へ変換しない。

`OperationFailure`自身の`ToErrorType` instanceでは、中のfailure値に`toErrorType`を適用する。

```haskell
instance ToErrorType OperationFailure where
  toErrorType (OperationFailure failure) =
    toErrorType failure
```

利用者操作ごとの`<Operation>OperationFailure`型や、Input / UseCase / Outputなどの処理段階を表す`OperationFailure` constructorは作らない。

### 依存への影響

`OperationFailure`はApplication側の共通型として`ragscope-application`が所有する。`OperationFailure`の定義から`DenseSearchFailure`などFeature固有のfailure型はimportしない。

`OperationFailure`のconstructorには`ToErrorType failure`制約があり、`ToErrorType OperationFailure` instanceも定義する。そのため、`ragscope-application`は`RAGScope.ErrorType`をimportする。静的依存には次を追加する。

```text
ragscope-application
  → ragscope-error
```

個々のOperation実装はUseCaseの`Either failure result`を受け取るためFeature側の型を参照する。ただし、共通`OperationFailure`型そのものからFeature固有のfailure型への依存は作らない。

## 2026-08-29 package境界を8 packageから4 packageへ整理する

### 変更前

Observability Port / Runtime、Logging Core / Runtime、Tracing Core / Port / OpenTelemetry Adapterを、それぞれ別のCabal packageとして分けていた。

```text
ragscope
ragscope-observability
ragscope-observability-runtime
ragscope-logging-core
ragscope-logging
ragscope-tracing-core
ragscope-tracing
ragscope-tracing-otel
```

この構成では、責務や依存先が異なる単位を見つけるたびにpackageを分けていた。

### 問題

依存方向をCabalで機械的に制限できることは必要だが、`build-depends`はlibrary component単位にも設定できる。

そのため、

```text
責務が違う
↓
packageを分ける
```

とそのまま対応させると、packageとlibraryの役割が重なり、1 packageにpublic main libraryが1つだけある境界が増える。

特にObservability RuntimeやTracing Core / Adapterは、別packageにしなくても、同じ責務を持つpackage内でlibraryを分ければ依存先を制限できる。

### 採用した方向

packageは大きな責務の単位に使い、その内側をpublic / private libraryへ分ける。

```text
ragscope
├─ private: ragscope-features
└─ private: ragscope-application

ragscope-observability
├─ public: main
├─ public: runtime
└─ private: internal

ragscope-logging
├─ public: core
├─ public: main
└─ private: internal

ragscope-tracing
├─ public: core
├─ public: main
└─ public: otel
```

moduleの責務は変更しない。変更するのは、Cabal package / libraryへの割り当てである。

### 依存禁止の維持

packageを4つへ減らしても、library単位の`build-depends`で次の依存制限を維持する。

- `ragscope-features`はObservability mainだけに依存し、Runner / Logging / Tracingへは依存できない。
- ApplicationはObservabilityのpublic `runtime`へ依存できるが、private `internal`へは依存できない。
- Observability `internal`はTracing main / `core`だけに依存し、`otel`へは依存しない。
- Tracing `otel`だけがOpenTelemetry SDKへ依存する。
- Logging `core`はJSON / SQLiteへ依存しない。
- LoggingのRuntime / Sink / Adapterはprivate `internal`へ置き、Applicationから直接使わせない。

Logging `internal`の中でJSON / SQLite Adapterをさらに別のprivate libraryへ分け、Runtimeから外部形式への依存をCabalで遮断する必要があるかは、Runtimeの具体的な組み立てを決める段階で再確認する。

### RunnerからTraceContextへの依存

`RAGScope.Observability.Runner`の候補APIには次がある。

```haskell
currentTraceContext :: m TraceContext
```

このため、Runner moduleは`RAGScope.Tracing.Context`を直接必要とする。

従来の静的依存Canvasではこのmodule依存が抜けていたため、4 packageへの再配置と同時に次を追加する。

```text
RAGScope.Observability.Runner
  → RAGScope.Tracing.Context
```

module数は18のまま変わらない。詳細図のmodule依存はApplication / Feature 14本、Observability / Tracing 10本、Logging 12本の計36本になる。

### 今後の判断基準

新しい境界を追加するときは、次の順番で判断する。

1. moduleの責務を分ける必要があるか。
2. componentごとに依存先や公開範囲を変える必要があるか。
3. 2が必要ならlibrary境界で表現できるか。
4. packageとして独立させる追加理由がある場合だけpackageを分ける。

package数やlibrary数そのものを設計目的にしない。

## 2026-08-29 Observability RuntimeからLoggingを外す

### 変更前

本番用の`MonadObservability` instanceでFeatureのeventを`LogSpec`へ変換し、その`LogSpec`をObservability Runtimeへ渡す案を検討していた。

```haskell
instance ToLogSpec event
      => MonadObservability event AppM where
  emit event =
    Observability.Runtime.emitLogSpec (toLogSpec event)
```

その結果、静的依存図には次の依存があった。

```text
Observability.Runtime
  ├─→ RAGScope.Logging
  └─→ RAGScope.Logging.Runtime
```

Observability Runtimeは`LogSpec`を受け取り、Logging Runtimeへ渡すところまで担当していた。

### 問題

`LogSpec`を必要とするのはLoggingであり、Observability Runtime自身は`LogSpec`を使って判断や状態管理をしない。

Observability Runtimeが行っていた処理は次の2つだけだった。

1. 本番用のinstanceで作られた`LogSpec`を受け取る。
2. 現在の`TraceContext`を付けてLogging Runtimeへ渡す。

つまり、Observability Runtimeは`LogSpec`を別moduleへ中継していた。この構造では、Loggingが所有する中間表現`LogSpec`がObservabilityへ漏れ、Observability RuntimeにLoggingとの接続責務まで集まる。

### 採用した方向

`event -> LogSpec`の変換はLogging package内で行う。

Logging側は具体的なFeature event型を知らず、`ToLogSpec`を満たす値として受け取る。

```haskell
write
  :: ToLogSpec a
  => TraceContext
  -> a
  -> m ()
```

本番用の`MonadObservability` instanceは`event`を変換せず、現在の`TraceContext`と一緒にLoggingへ渡す。

```haskell
instance ToLogSpec event
      => MonadObservability event AppM where
  emit event = do
    context <- Observability.Runtime.currentTraceContext
    Logging.Write.write context event
```

`RAGScope.Logging.Write`が`toLogSpec`を呼び、`LogSpec`をLogging Runtimeへ渡す。

```text
event + TraceContext
  ↓ Logging.Write
toLogSpec
  ↓
LogSpec
  ↓ Logging Runtime
LogRecord
  ↓
Sink
```

### Application.Observability

ObservabilityとLoggingを本番環境でどう接続するかは、Observability library自身ではなくRAGScope Application側で決める。

そのため、`RAGScope.Application.Observability`を置く。

このmoduleは次を担当する。

- 本番用の`MonadObservability` instanceを定義する。
- Observability Runtimeを使ってUseCaseを実行する。
- `emit`時に現在の`TraceContext`を取得する。
- `event + TraceContext`をLoggingの公開入口へ渡す。

これにより、Observability RuntimeからLoggingへの静的依存を削除できる。

### Loggingの公開入口とRuntime

`ragscope-logging`では、別packageから呼び出す公開入口と、その後ろで動くRuntimeを分ける。

現在の第一候補は次の構成である。

```text
RAGScope.Logging.Write      exposed
  ↓
RAGScope.Logging.Runtime    private
  ↓
Sink
```

`Logging.Write`は`ToLogSpec`を満たす値を受け取り、`LogSpec`へ変換する。

Logging Runtimeは`LogSpec`へ実行時情報を加えて`LogRecord`を作り、その`LogRecord`をSinkへ渡す。

Runtime内部は次の2操作へ分ける案を第一候補とする。

```text
completeLogRecord
  LogSpec -> LogRecord

writeLogRecord
  LogRecord -> Sink
```

`writeLogRecord`という名前は、実際に`LogRecord`を受け取る処理へ使う。

### Feature Logging instance

`RAGScope.<Feature>.Logging`の`ToLogSpec <FeatureEvent>`は、意図的なorphan instanceとして維持する。

UseCaseからFeature Loggingをimportさせず、Logging packageからFeatureへの逆依存も作らない。

本番用に必要なinstanceを読み込むimport経路として、`RAGScope.Application.LoggingInstances`を置く。

```haskell
module RAGScope.Application.LoggingInstances () where

import RAGScope.Search.Logging ()
import RAGScope.Index.Logging ()
```

`Application.Observability`がこれをimportする。

### 今回の設計レビューで得た観点

依存図の矢印ごとに、「依存元moduleが依存先のどの型・関数を使うのか」を説明できる必要がある。

特に次の場合は、責務の置き場所を見直す。

- 受け取った値を加工せず、別moduleへ渡すだけになっている。
- あるlibraryが所有する中間表現が、その値を必要としない別libraryへ出ている。
- 「ObservabilityだからTracingとLoggingをまとめる」のように、名前から責務を決めている。
- 複数libraryを本番環境で接続する処理の置き場所がなく、どれか1つのRuntimeへ押し込まれている。

この場合は、本番構成を組み立てる`RAGScope.Application.*`側に接続処理を置けないか先に検討する。

### AI支援時の反省

初期レビューでは、既存ノートに書かれていた次の流れを「現在案」として理解することを優先し、その流れ自体に不自然な責務移動がないかを十分に検証できなかった。

```text
本番用instanceでtoLogSpec
→ Observability Runtime
→ Logging Runtime
```

今後は既存ノートを読むときも、次を確認する。

1. 各矢印について、呼ぶ関数・渡す値・必要なimportを具体的に説明できるか。
2. 値を中継するだけのmoduleがあれば、本来そのmoduleにない責務が入っていないか。
3. 中間表現を、その表現を所有するlibraryの外へ出す必要が本当にあるか。
4. 既存案に理由が書かれていなければ、書かれていること自体を採用理由にしない。
5. 既存案を説明するだけでなく、より単純な依存や責務分割がある場合は積極的に代案を出す。

## 2026-08-29 FeatureとApplicationのCabal libraryを分ける

### 変更前

`ragscope` package内のFeatureとApplicationを、1つのprivate library `ragscope-internal`へまとめていた。

```text
ragscope
└─ ragscope-internal
   ├─ RAGScope.<Feature>.Event
   ├─ RAGScope.<Feature>.UseCase
   ├─ RAGScope.<Feature>.Logging
   ├─ RAGScope.Application.Execution
   ├─ RAGScope.Application.Observability
   └─ RAGScope.Application.LoggingInstances
```

### 問題

Cabalの`build-depends`はlibrary component単位で設定する。Application側が必要とするLogging / Tracing系packageを`ragscope-internal`の`build-depends`へ追加すると、同じlibraryにいるFeature / UseCaseからもそれらをimportできる。

そのため、設計上「UseCaseはLoggingやTracingの具体APIを知らない」と決めても、その禁止をCabalで強制できていなかった。

### 採用した方向

`ragscope` package内を次の2つのprivate named libraryへ分ける。

```text
ragscope
├─ ragscope-features
│  ├─ RAGScope.<Feature>.Event
│  └─ RAGScope.<Feature>.UseCase
│
└─ ragscope-application
   ├─ RAGScope.<Feature>.Logging
   ├─ RAGScope.Application.Execution
   ├─ RAGScope.Application.Observability
   └─ RAGScope.Application.LoggingInstances
```

`ragscope-features`にはFeature / UseCaseが必要な依存だけを与え、Logging / Tracing系packageへの`build-depends`を持たせない。

`ragscope-application`は`ragscope-features`へ依存し、本番構成の組み立てに必要な基盤libraryへ依存できる。

`RAGScope.<Feature>.Logging`はFeature event型と`ToLogSpec`の両方を使うため、`ragscope-application`側へ置く。これにより、Feature LoggingのためのLogging依存をUseCase側libraryへ持ち込まない。

`RAGScope.<Feature>.Event`はFeature Loggingから参照されるため、`ragscope-features`から他libraryへ公開するmoduleにする。

### 今後の確認観点

設計が変わるたびに、module分割だけでなく次も確認する。

1. そのmoduleが属するlibraryの`build-depends`を、同じlibrary内の全moduleが使えて問題ないか。
2. 「このmoduleだけが使う」と説明している外部依存を、同じlibraryの他moduleからもimportできる状態になっていないか。
3. `exposed-modules` / `other-modules`で隠せる問題と、library自体を分けないと遮断できない問題を区別できているか。
4. 新しいRuntime / backend / 本番構成の組み立て責務が増えたとき、既存libraryの依存先を不必要に増やしていないか。
