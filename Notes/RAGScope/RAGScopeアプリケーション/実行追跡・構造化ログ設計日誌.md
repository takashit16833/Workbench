# 実行追跡・構造化ログ設計日誌

実行追跡・構造化ログ設計で、途中の判断、見つかった問題、設計レビューで得た観点を残す。

現在採用している設計そのものは [[実行追跡・構造化ログ設計ノート]] と [[実行追跡・構造化ログ実行設計ノート]] を参照する。静的依存は [[実行追跡・構造化ログ静的依存.canvas]] を参照する。

## 2026-08-29 package境界を8 packageから4 packageへ整理する

### 変更前

Observability Port / Runtime、Logging Core / Runtime、Tracing Core / Port / OpenTelemetry Adapterを、それぞれ別Cabal packageとして分離していた。

```text
ragscope
ragscope-observability
ragscope-observability-runtime
ragscope-logging-core
ragscope-logging
ragscope-tracing-core
ragscope-tracing
ragscope-tracing-otel
```

この構成では、責務や依存集合が異なる単位を見つけるたびにpackage境界を追加していた。

### 問題

禁止依存をCabalで機械的に止めること自体は必要だが、`build-depends`はlibrary componentごとにも分けられる。

そのため、

```text
責務が違う
↓
packageを分ける
```

をそのまま適用すると、packageとlibraryの役割が重なり、1 packageにpublic main libraryが1つだけある境界が増えていた。

特にObservability RuntimeやTracing Core / Adapterは、別packageにしなくても同じ責務package内の別libraryとして依存集合を分けられる。

### 採用した方向

packageは大きな責務のまとまりに使い、その内側をpublic / private libraryへ分ける。

```text
ragscope
├─ private: ragscope-features
└─ private: ragscope-application

ragscope-observability
├─ public: main
├─ public: runtime
└─ private: internal

ragscope-logging
├─ public: core
├─ public: main
└─ private: internal

ragscope-tracing
├─ public: core
├─ public: main
└─ public: otel
```

moduleの責務は変更しない。変更するのはCabal package / libraryへの割り当てである。

### 依存禁止の維持

packageを4つへ減らしても、library単位の`build-depends`で次を機械的に維持する。

- `ragscope-features`はObservability mainだけを使い、Runner / Logging / Tracingを使えない。
- ApplicationはObservabilityのpublic `runtime`を使えるが、private `internal`へは依存できない。
- Observability `internal`はTracing main / `core`だけを使い、`otel`へは依存しない。
- Tracing `otel`だけがOpenTelemetry SDKへ依存する。
- Logging `core`はJSON / SQLiteへ依存しない。
- Loggingの内部Runtime / Sink / Adapterはprivate `internal`へ置き、Applicationから直接使わせない。

Logging `internal`の中でJSON / SQLite Adapterをさらに別private libraryへ分け、Runtimeから外部形式依存を機械的に遮断する必要があるかは、Runtimeの具体的な組み立てを決める段階で再確認する。

### RunnerからTraceContextへの依存

`RAGScope.Observability.Runner`の候補APIには、

```haskell
currentTraceContext :: m TraceContext
```

があるため、Runner moduleは`RAGScope.Tracing.Context`を直接必要とする。

従来の静的依存Canvasではこのmodule依存が抜けていたため、4 packageへの再配置と同時に

```text
RAGScope.Observability.Runner
  → RAGScope.Tracing.Context
```

を追加する。

module数は18のまま変わらない。詳細図のmodule依存はApplication / Feature 14本、Observability / Tracing 10本、Logging 12本の計36本になる。

### 今後の判断基準

新しい境界を追加するときは、順番を次のようにする。

1. moduleの責務を分ける必要があるか。
2. componentごとに依存集合や公開範囲を変える必要があるか。
3. 2が必要ならlibrary境界で表現できるか。
4. packageとして独立させる追加理由がある場合だけpackageを分ける。

package数やlibrary数そのものを設計目的にしない。

## 2026-08-29 Observability RuntimeからLoggingを外す

### 変更前

productionの`MonadObservability` instanceでFeature eventを`LogSpec`へ変換し、その`LogSpec`をObservability Runtimeへ渡す案で検討していた。

```haskell
instance ToLogSpec event
      => MonadObservability event AppM where
  emit event =
    Observability.Runtime.emitLogSpec (toLogSpec event)
```

その結果、静的依存図には次の依存があった。

```text
Observability.Runtime
  ├─→ RAGScope.Logging
  └─→ RAGScope.Logging.Runtime
```

Observability Runtimeは`LogSpec`を受け取り、Logging Runtimeへ渡す役割まで持っていた。

### 問題

`LogSpec`を必要とするのはLoggingであり、Observability Runtime自身は`LogSpec`を使って判断や状態管理をしない。

Observability Runtimeが行っていたのは、

1. production側で作られた`LogSpec`を受け取る。
2. 現在の`TraceContext`を付けてLogging Runtimeへ渡す。

という中継だった。

この構造では、Loggingの中間表現である`LogSpec`がObservabilityへ出ており、Observability RuntimeにLoggingとの接続責務まで集まっていた。

### 採用した方向

`event -> LogSpec`変換はLogging packageの中で行う。

Logging側は具体的なFeature event型を知るのではなく、`ToLogSpec`を満たす値として受け取る。

```haskell
write
  :: ToLogSpec a
  => TraceContext
  -> a
  -> m ()
```

productionの`MonadObservability` instanceは`event`を変換せず、現在の`TraceContext`と一緒にLoggingへ渡す。

```haskell
instance ToLogSpec event
      => MonadObservability event AppM where
  emit event = do
    context <- Observability.Runtime.currentTraceContext
    Logging.Write.write context event
```

`RAGScope.Logging.Write`が`toLogSpec`を呼び、`LogSpec`をLogging Runtimeへ渡す。

```text
event + TraceContext
  ↓ Logging.Write
toLogSpec
  ↓
LogSpec
  ↓ Logging Runtime
LogRecord
  ↓
Sink
```

### Application.Observability

ObservabilityとLoggingをproductionでどう接続するかは、Observability library自身ではなくRAGScope Application側で決める。

そのため`RAGScope.Application.Observability`を置く。

このmoduleは次を担当する。

- productionの`MonadObservability` instance
- Observability Runtimeを使ったUseCaseの実行
- `emit`時のcurrent `TraceContext`取得
- `event + TraceContext`をLoggingの公開入口へ渡す

これにより、Observability RuntimeからLoggingへの静的依存を削除できる。

### Loggingの公開入口とRuntime

`ragscope-logging`では、別packageから呼ぶ公開入口と、その後ろのRuntimeを分ける。

現在の第一候補は次の構成である。

```text
RAGScope.Logging.Write      exposed
  ↓
RAGScope.Logging.Runtime    private
  ↓
Sink
```

`Logging.Write`は`ToLogSpec`を満たす値を受け取り`LogSpec`へ変換する。

Logging Runtimeは`LogSpec`から`LogRecord`を完成し、完成した`LogRecord`をSinkへ渡す。

Runtime内部は次の2操作へ分ける案を第一候補とする。

```text
completeLogRecord
  LogSpec -> LogRecord

writeLogRecord
  LogRecord -> Sink
```

`writeLogRecord`という名前は、実際に`LogRecord`を受け取る処理へ使う。

### Feature Logging instance

`RAGScope.<Feature>.Logging`の`ToLogSpec <FeatureEvent>`は意図的なorphan instanceとして維持する。

UseCaseからFeature Loggingをimportさせず、Logging packageからFeatureへ逆依存も作らない。

productionで必要なinstanceへimport chainを作るため、`RAGScope.Application.LoggingInstances`を置く。

```haskell
module RAGScope.Application.LoggingInstances () where

import RAGScope.Search.Logging ()
import RAGScope.Index.Logging ()
```

`Application.Observability`がこれをimportする。

### 今回の設計レビューで得た観点

依存図の矢印には「そのmoduleが本当にその依存先の何を使うのか」を説明できる必要がある。

特に次の場合は責務の置き場所を疑う。

- 受け取った値を加工せず別moduleへ渡すだけになっている。
- あるlibraryの中間表現が、その値を必要としない別libraryへ出ている。
- 「ObservabilityだからTracingとLoggingをまとめる」のように、名前から責務を逆算している。
- 複数libraryをproduction用に接続する処理の置き場所がなく、どれか1つのRuntimeへ押し込まれている。

この場合は`RAGScope.Application.*`のようなcomposition側に接続責務を置けないか先に検討する。

### AI支援時の反省

今回の初期レビューでは、既にノートへ書かれていた

```text
production instanceでtoLogSpec
→ Observability Runtime
→ Logging Runtime
```

という流れを「現在案」として理解することを優先し、その流れ自体に未説明の責務移動がないかを十分にレビューできていなかった。

今後は既存ノートを読むときも、特に次を確認する。

1. 各矢印について、呼ぶ関数・渡す値・必要なimportを具体的に言えるか。
2. 中継だけをするmoduleがあれば、そこに本来ない責務が入っていないか。
3. 中間表現は、その表現を所有するlibraryの外へ出す必要が本当にあるか。
4. 既存案に理由が書かれていなければ、書いてあること自体を採用理由にしない。
5. 設計案を説明するだけでなく、より単純な依存や責務分割があれば積極的に代案を出す。

## 2026-08-29 FeatureとApplicationのCabal libraryを分ける

### 変更前

`ragscope` package内のFeatureとApplicationを、1つのprivate library `ragscope-internal`へまとめていた。

```text
ragscope
└─ ragscope-internal
   ├─ RAGScope.<Feature>.Event
   ├─ RAGScope.<Feature>.UseCase
   ├─ RAGScope.<Feature>.Logging
   ├─ RAGScope.Application.Execution
   ├─ RAGScope.Application.Observability
   └─ RAGScope.Application.LoggingInstances
```

### 問題

Cabalの`build-depends`はlibrary component単位で与えるため、Application側が必要とするLogging / Tracing系依存を`ragscope-internal`へ追加すると、同じlibraryにいるFeature / UseCaseからもそれらをimportできる。

そのため、設計上は「UseCaseはLoggingやTracingの具体APIを知らない」としていても、その禁止をCabalで強制できていなかった。

### 採用した方向

`ragscope` package内を次の2つのprivate named libraryへ分ける。

```text
ragscope
├─ ragscope-features
│  ├─ RAGScope.<Feature>.Event
│  └─ RAGScope.<Feature>.UseCase
│
└─ ragscope-application
   ├─ RAGScope.<Feature>.Logging
   ├─ RAGScope.Application.Execution
   ├─ RAGScope.Application.Observability
   └─ RAGScope.Application.LoggingInstances
```

`ragscope-features`にはFeature / UseCaseが必要な依存だけを与え、Logging / Tracing系packageへの`build-depends`を持たせない。

`ragscope-application`は`ragscope-features`へ依存し、production compositionに必要な基盤libraryへ依存できる。

`RAGScope.<Feature>.Logging`はFeature event型と`ToLogSpec`の両方を使うため、`ragscope-application`側へ置く。これによりFeature LoggingのためのLogging依存をUseCase側libraryへ持ち込まない。

`RAGScope.<Feature>.Event`はFeature Loggingから参照されるため、`ragscope-features`から他libraryへ見せるmoduleにする。

### 今後の確認観点

設計が育つたびに、module分割だけで満足せず、次を確認する。

1. そのmoduleが属するlibraryの`build-depends`を、同じlibrary内の全moduleが使えて問題ないか。
2. 「このmoduleだけが使う」と説明している外部依存が、同じlibraryの他moduleからもimport可能になっていないか。
3. `exposed-modules` / `other-modules`で隠せる問題と、library自体を分けないと遮断できない問題を区別する。
4. 新しいRuntime / backend / composition責務が増えたとき、既存libraryの依存集合を不必要に広げていないか。
