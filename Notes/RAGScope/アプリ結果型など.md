# アプリ結果型など
できます。むしろ別スレへ移る前に、**この型設計が実際のRAGScopeの処理でどう見えるか**を一度通しておくのはかなり良いと思います。

以下は**BR-0006の候補設計を動かした擬似Haskell**です。まだ採用済み設計ではありません。また、BR-0006で未決定になっている`FeatureAction`と専用`ExecutionResult`はあえて使わず、いちばんシンプルな形で書きます。現在の実装では`AppResult = ExceptT AppError IO`、logging側の`emit`は`IO (Either LoggingFailure ())`なので、その2軸を合成する案です。  BR-0006でもこの構造が現在の検討案になっています。

## まず、最終的に書きたいコード

いきなりゴールから見ると、文書処理はこんな感じになってほしいです。

```haskell
processDocument :: Logger -> FilePath -> AppAction Chunks
processDocument logger path = do
  document <-
    observe
      logger
      (readDocument path)
      documentReadEvent

  parsed <-
    observe
      logger
      (pure $ parseDocument document)
      documentParseEvent

  chunks <-
    observe
      logger
      (pure $ chunkDocument parsed)
      documentChunkEvent

  pure chunks
```

かなり気持ちいいです笑

見た目としては、

```text
文書読み込み
    >>=
文書パース
    >>=
チャンク化
```

なのですが、実際には各`observe`の内部で、

```text
機能処理
↓
その結果のログ出力
↓
両方の結果を合成
↓
続行可能なら値を返す
失敗ならAppActionを短絡
```

までやっています。

# 1. 個々の機能処理

まず、文書読み込みなどの**機能そのもの**はloggingを知りません。

擬似的にはこうします。

```haskell
readDocument
  :: FilePath
  -> IO (Either AppError Document)

parseDocument
  :: Document
  -> Either AppError ParsedDocument

chunkDocument
  :: ParsedDocument
  -> Either AppError Chunks
```

ポイントは、

```haskell
readDocument
```

が知っている失敗は、

```haskell
AppError
```

だけということです。

たとえば、

```haskell
readDocument path =
  -- ファイルを読む
  -- IOExceptionなどはここでAppErrorへ変換
  ...
```

で、

```haskell
parseDocument document =
  -- Markdownをparse
  -- parse失敗ならAppError
  ...
```

となります。

この時点では、

```text
「ログを出せたか？」
```

は一切考えません。

つまり、

```text
readDocument
parseDocument
chunkDocument
```

は**RAGScopeの機能処理**です。

# 2. logging側

現在の`emit`は概念的に、

```haskell
emit
  :: Logger
  -> event
  -> IO (Either LoggingFailure ())
```

です。

なので例えば、

```haskell
emit logger DocumentReadSucceeded
```

なら、

```haskell
Right ()
```

または、

```haskell
Left LoggingSinkFailure
```

が返ります。

ここでも`AppError`は知りません。

つまりここまで完全に別軸です。

```text
機能処理
Either AppError a

logging
Either LoggingFailure ()
```

```haskell
data DocumentReadEvent
```

のような閉じたイベント型があるとします。

そして、

```haskell

documentReadEvent result =
```

```text
↓
```

という順番です。

# 4. `ExecutionOutcome`

そして今回の**事実の直積**です。

```haskell
data ExecutionOutcome a = ExecutionOutcome
  { featureResult :: Either AppError a
  , loggingResult :: Either LoggingFailure ()
  }
```

これは、

> この観測境界で、実際に何が起きた？

だけを表します。

たとえば文書パース成功 + ログ成功なら、

```haskell
ExecutionOutcome
  { featureResult = Right parsedDocument
  , loggingResult = Right ()
  }
```

文書パース成功 + ログ失敗なら、

```haskell
ExecutionOutcome
  { featureResult = Right parsedDocument
  , loggingResult = Left LoggingSinkFailure
  }
```

文書パース失敗 + ログ成功なら、

```haskell
ExecutionOutcome
  { featureResult = Left parseError
  , loggingResult = Right ()
  }
```

そして最重要ケース、

```haskell
ExecutionOutcome
  { featureResult = Left parseError
  , loggingResult = Left LoggingSinkFailure
  }
```

も普通に表せます。

この型自身は、

```text
続行するべきか？
アプリ全体として成功か？
```

を判断しません。

ただの**事実**です。

# 5. `ExecutionFailure`

ここで直和が登場します。

```haskell
data ExecutionFailure
  = LoggingFailed LoggingFailure
  | FeatureFailed AppError
  | FeatureAndLoggingFailed AppError LoggingFailure
```

こちらは単なる事実ではなく、

> この組み合わせをRAGScopeの実行失敗としてどう分類する？

を表します。

そして、

```haskell
interpretOutcome
  :: ExecutionOutcome a
  -> Either ExecutionFailure a
```

を定義します。

```haskell
interpretOutcome outcome =
  case
    ( outcome.featureResult
    , outcome.loggingResult
    )
  of

    -- ① 機能成功 + logging成功
    (Right value, Right ()) ->
      Right value

    -- ② 機能成功 + logging失敗
    (Right _, Left loggingFailure) ->
      Left $
        LoggingFailed loggingFailure

    -- ③ 機能失敗 + logging成功
    (Left appError, Right ()) ->
      Left $
        FeatureFailed appError

    -- ④ 機能失敗 + logging失敗
    (Left appError, Left loggingFailure) ->
      Left $
        FeatureAndLoggingFailed
          appError
          loggingFailure
```

ここがまさに、

```text
事実の直積
    ↓
意味の直和
```

です。

# 6. `AppAction`

これをアプリケーション全体の失敗チャネルにします。

```haskell
type AppAction a =
  ExceptT ExecutionFailure IO a
```

`runExceptT`すると、

```haskell
runExceptT
  :: AppAction a
  -> IO (Either ExecutionFailure a)
```

です。

だから、

```haskell
do
  document <- ...
  parsed   <- ...
  chunks   <- ...
```

の途中で、

```haskell
Left ExecutionFailure
```

になった瞬間、それ以降を実行しません。

ここが最初にやりたかった`>>=`の気持ちいいところですね。

# 7. そして`observe`

いよいよ例のイケてるやつです笑

擬似的にはこんな責務です。

```haskell
observe
  :: ToEventSpec event
  => Logger
  -> IO (Either AppError a)
  -> (Either AppError a -> event)
  -> AppAction a
```

実装イメージは、

```haskell
observe logger featureAction toEvent =
  ExceptT $ do

    -- ① 機能処理を実行
    featureResult <-
      featureAction

    -- ② 機能処理の結果からイベントを作る
    let event =
          toEvent featureResult

    -- ③ ログを出力
    loggingResult <-
      emit logger event

    -- ④ 独立した2つの結果を直積にする
    let outcome =
          ExecutionOutcome
            { featureResult
            , loggingResult
            }

    -- ⑤ RAGScopeとしての意味へ解釈
    pure $
      interpretOutcome outcome
```

ここ、大事なので型だけ追ってみます。

最初、

```haskell
featureResult
  :: Either AppError a
```

です。

次に、

```haskell
loggingResult
  :: Either LoggingFailure ()
```

です。

これを、

```haskell
ExecutionOutcome
  featureResult
  loggingResult
```

にすると、

```haskell
outcome
  :: ExecutionOutcome a
```

になります。

そして、

```haskell
interpretOutcome outcome
```

すると、

```haskell
Either ExecutionFailure a
```

になります。

これを`ExceptT`で包むことで、

```haskell
AppAction a
```

になる。

型の流れだけ書くと、

```text
IO (Either AppError a)
        │
        │ 実行
        ▼
Either AppError a
        │
        │ 結果からイベント生成
        ▼
      event
        │
        │ emit
        ▼
Either LoggingFailure ()
        │
        │
        ├────────────┐
        │            │
Either AppError a    │
        │            │
        └─────┬──────┘
              ▼
     ExecutionOutcome a
              │
              │ interpretOutcome
              ▼
 Either ExecutionFailure a
              │
              │ ExceptT
              ▼
        AppAction a
```

かなり綺麗です。

## 全体を1枚にすると

今回の候補設計を一番短くまとめると、こうです。

```text
                  ┌─────────────────────┐
                  │   機能処理          │
                  │ read / parse / ...  │
                  └─────────┬───────────┘
                            │
                            ▼
                  Either AppError a
                            │
             結果に対応するeventを生成
                            │
                            ▼
                         emit
                            │
                            ▼
             Either LoggingFailure ()
                            │
             ┌──────────────┴──────────────┐
             │                             │
             ▼                             ▼
    Either AppError a          Either LoggingFailure ()
             │                             │
             └──────────────┬──────────────┘
                            ▼
                  ExecutionOutcome a
                    「起きた事実」
                            │
                            │ interpretOutcome
                            ▼
              Either ExecutionFailure a
                    「その意味」
                            │
                            │ ExceptT
                            ▼
                      AppAction a
                            │
                            │ >>=
                            ▼
                    次の機能処理
```

そして利用側は、

```haskell
processDocument logger path = do
  document <- observe logger (readDocument path) documentReadEvent
  parsed   <- observe logger (pure $ parseDocument document) documentParseEvent
  chunks   <- observe logger (pure $ chunkDocument parsed) documentChunkEvent
  pure chunks
```

だけになる。

私は今回のブレストで一番面白いところは、**`ExecutionOutcome`そのものではなく、これによって`AppAction`の`>>=`が「機能失敗」と「ログ失敗」の両方を自然に短絡できるようになるところ**だと思います。

最初の「文書読み込み >>= 文書パース >>= …で気持ちよくなりたい」が、loggingという別軸を発見したことで一度崩れかけたのに、最終的には**一段上の`AppAction`として戻ってきた**感じですね。これは別スレでBR-0006をレビューするときのかなり良い土台になると思います。

はい。`FeatureAction`を入れると、構造としては **`observe`の入力側にもう1段モナドが入る**感じになります。

まず型はこうです。

```haskell
type FeatureAction a =
  ExceptT AppError IO a

type AppAction a =
  ExceptT ExecutionFailure IO a
```

そして各機能処理を、

```haskell
readDocument
  :: FilePath
  -> FeatureAction Document

parseDocument
  :: Document
  -> FeatureAction ParsedDocument

chunkDocument
  :: ParsedDocument
  -> FeatureAction Chunks
```

のように揃える案です。

すると`observe`は前回の、

```haskell
observe
  :: Logger
  -> IO (Either AppError a)
  -> (Either AppError a -> event)
  -> AppAction a
```

ではなく、

```haskell
observe
  :: Logger
  -> FeatureAction a
  -> (Either AppError a -> event)
  -> AppAction a
```

になります。

実装イメージはこうです。

```haskell
observe logger featureAction toEvent =
  ExceptT $ do

    -- FeatureActionを実行して、
    -- AppError / 成功値という「機能処理の事実」に戻す
    featureResult <-
      runExceptT featureAction

    let event =
          toEvent featureResult

    loggingResult <-
      emit logger event

    let outcome =
          ExecutionOutcome
            { featureResult
            , loggingResult
            }

    pure $
      interpretOutcome outcome
```

つまり、

```text
FeatureAction a
    │
    │ runExceptT
    ▼
Either AppError a
    │
    │ + emit
    ▼
ExecutionOutcome a
    │
    │ interpretOutcome
    ▼
Either ExecutionFailure a
    │
    │ ExceptT
    ▼
AppAction a
```

となります。

## `FeatureAction`のメリットが出るのは「observeの内側」

たとえば文書読み込み1ステップの内部が、実際には複数処理だったとします。

```text
パス解決
↓
ファイル読み込み
↓
文字コード検証
↓
Document生成
```

これらを全部まとめて「文書読み込み」という1つの観測点にしたい。

その場合、

```haskell
readDocument :: FilePath -> FeatureAction Document
readDocument path = do
  resolvedPath <-
    resolvePath path

  bytes <-
    readFileBytes resolvedPath

  text <-
    decodeDocument bytes

  pure $
    Document text
```

と、**FeatureActionの内部では`AppError`だけを使って`>>=`できます**。

そして外から見ると、

```haskell
observe logger (readDocument path) documentReadEvent
```

で一発です。

ここでは役割が綺麗に分かれます。

```text
FeatureAction
────────────────────
パス解決
>>= ファイル読み込み
>>= decode

「文書読み込み」という
1つの機能処理を構成する


AppAction
────────────────────
文書読み込み + ログ
>>= パース + ログ
>>= chunk + ログ

アプリ全体を構成する
```

これなら、以前「FeatureActionを`>>=`する理由ないのでは？」と言った話とも両立します。

**大きなアプリフローをFeatureActionでつなぐ理由はない。
でも、1つの観測単位の内部をFeatureActionで組み立てる理由はあり得る。**

ということですね。

## ただし、かなり重要な弱点があります

これを全部に適用すると、

```haskell
parseDocument
  :: Document
  -> FeatureAction ParsedDocument
```

のようになります。

でも文書パースが純粋処理なら、本来は、

```haskell
parseDocument
  :: Document
  -> Either ParseError ParsedDocument
```

などで十分です。

RAGScopeのHaskell規約も、**副作用を必要としない検証・変換・判断を`IO`や`IO`内包結果型へ慣習的に巻き込まない**方針です。

なので、

```haskell
type FeatureAction a =
  ExceptT AppError IO a
```

を作ったからといって、

```haskell
readDocument   :: ... -> FeatureAction Document
parseDocument  :: ... -> FeatureAction ParsedDocument
chunkDocument  :: ... -> FeatureAction Chunks
```

と**全部同じ型へ統一するのは、むしろRAGScopeの方針に反します**。

ここがBR-0006で、

> `ExceptT AppError IO a`を個々の機能処理用として残す必要があるか、それとも型エイリアス自体が不要か

を未決定にしている理由でもあります。

---

## なので現時点では、2案あります

### A. `FeatureAction`を正式な共通型として残す

IOを伴う機能境界では、

```haskell
readDocument
  :: FilePath
  -> FeatureAction Document
```

とする。

純粋処理には使わない。

```haskell
parseDocument
  :: Document
  -> Either ParseError ParsedDocument
```

のまま。

必要なところで`AppError`へ変換して`AppAction`へ持ち上げます。

これは、

```text
FeatureAction = IOを伴う機能境界用
AppAction     = loggingまで含むアプリ実行用
```

という二層構造です。

### B. `FeatureAction`という共通型自体を作らない

必要な機能だけ、

```haskell
readDocument
  :: FilePath
  -> ExceptT AppError IO Document
```

と書く。

あるいは、

```haskell
readDocument
  :: FilePath
  -> IO (Either AppError Document)
```

でもよい。

そして`observe`側がそれを受け取って`AppAction`へ変換する。

こちらは型エイリアスを一つ減らせます。

---

私は今のところ、**B寄りです**。

理由は、`FeatureAction`を導入すると名前があるぶん、

> 「RAGScopeの機能はFeatureActionで書く」

という暗黙の圧力が生まれやすいからです。

でも実際には、

```text
純粋なparse
純粋なvalidation
IOを伴うread
HTTPを伴うfetch
```

で自然な型は違います。

一方`AppAction`には明確な存在理由があります。

```haskell
type AppAction a =
  ExceptT ExecutionFailure IO a
```

これは、

> **機能処理と必須loggingを含めた、アプリケーション全体の線形な実行**

というRAGScope固有の責務を持っている。

`FeatureAction`にはそこまで強い共通責務がまだ見えていません。

なので今回の流れを描くなら、私はこう考えています。

```text
各機能
┌─────────────────────────┐
│ 純粋なら Either / 純粋値 │
│ IOなら ExceptT等も使える │
└───────────┬─────────────┘
            │
            │ AppErrorまで確定
            ▼
          observe
            │
     ┌──────┴──────┐
     ▼             ▼
機能処理結果     logging結果
     │             │
     └──────┬──────┘
            ▼
   ExecutionOutcome
            │
   interpretOutcome
            ▼
        AppAction
            │
           >>=
            ▼
       次のobserve
```

つまり、**`FeatureAction`を混ぜると`observe`の左側が綺麗になる可能性はある。でも、アーキテクチャ上どうしても必要な型かというと、まだ怪しい**。

ここはBR-0006レビューでかなり良い論点だと思います。

そして`observe`はやっぱり、こうして見るとかなり中心人物ですね笑。
