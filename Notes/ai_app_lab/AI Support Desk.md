# AI Support Desk

> **学習用の小さなRAGバックエンド**。このノートがAI Support Deskの機能範囲の正本。全体方針は[README](README.md)を参照。

## 目的と学べること

社内マニュアル・FAQ・障害対応手順から関連情報を検索し、**根拠のある回答**を返す。AIアプリケーションの検索・回答・品質改善・API・運用を一つの題材で順に学ぶ。

案件要求との対応：
- RAG/AI検索、Embedding、Chunking、Hybrid、Rerank、プロンプト
- 参照根拠、回答不能な質問、検索評価・回答評価、改善サイクル
- Haskellによる検索・アプリケーション処理、PythonのFastAPI/PydanticによるAIサービス
- LLM API、観測性、遅延・トークン/費用計測、キャッシュ、CI/CD、基本的なクラウド配置

**これはRAGScopeの再実装でも、汎用RAGプラットフォームでもない。** 利用者が質問して、評価し、改善できる小さなプロダクトを作る。

## 中核ユースケース（固定）

1. 利用者が日本語で質問する。
2. 登録済み文書・FAQから適切な箇所を検索し、必要ならRerankする。
3. 上位の根拠をContextとしてLLMへ渡し、回答と参照元を返す。
4. 根拠が見つからない場合は、無理に回答せず「わからない」を返す。
5. 開発者が固定の評価問題を使って、検索・回答の品質を再現可能に比較する。

扱うデータは**架空のITサポート用文書**（DB接続、社内申請手順、FAQ、障害対応など）。実際の顧客情報・秘密情報は使わない。

## 最小構成と責務

~~~text
CLI / （後から）Haskell HTTP API
          |
          v
Haskellアプリケーション
  文書取り込み制御 / 検索（PostgreSQL + pgvector）
  Dense・Sparse・RRF / Context選択 / 評価 / 回答フロー
          |                         |
          v                         v
Python推論側                 PostgreSQL
  Embedding / Rerank / LLM    文書・チャンク・ベクトル
  （後から）FastAPI + Pydantic
~~~

- **Haskell**: 問い合わせの処理順序、チャンク・根拠の管理、検索・集約・評価、失敗時の分岐。純粋な集計ロジックとIOを分ける。
- **Python**: Hugging Face / PyTorch等を使ったEmbedding・Rerank・LLM呼び出し。FastAPI/Pydanticで推論用の型付きHTTP APIを作る段階を設ける。
- **PostgreSQL/pgvector**: 文書・チャンク・ベクトルの永続化と検索。
- **モデル**: まずローカルで動くものを一つ。商用LLM APIや複数モデル比較は評価・運用フェーズで追加する。
- 初期はrag-labの既存構成・コードを**参考にして取り込む**。最初から共有基盤・サービスメッシュ・複数デプロイを作らない。

### 論理的な入出力

質問：質問文字列。返す情報：**回答、参照した文書/チャンクの識別子、検索・推論の結果/エラー状態**。参照元は実際に取得したチャンクから組み立て、LLMが出した架空の引用をそのまま信用しない。

評価では少なくとも **question / expected relevant chunk IDs / reference answer** を扱う。外部に提供する正確なJSON SchemaやHTTPパスは該当段階で最小限決め、ノートに追記する。最初から完成形を固定しない。

## 段階と完成条件

### S1：小さなRAGが最後まで動く（MVP）

- Markdownと短いFAQを登録（最初はCLIから）。
- 質問→検索→Rerank→上位Context→LLM→回答と参照元の表示。
- 回答できない質問も1例含める。
- **完了**：手順書どおりに初期化・登録・質問を実行でき、成功例と根拠なし例が再現できる。

### S2：Python AI APIを作る

- PythonでFastAPI/Pydanticを用いた、必要最小限の**モデル推論API**（Embedding、Rerank、回答生成）を実装する。
- Haskellが処理全体を制御し、Pythonの推論エンドポイントを利用する。
- 必要に応じてHaskell側に利用者向けHTTP APIを追加（Python側を全体の司令塔へ変更しない）。
- JSON型、バリデーション、モデル失敗、タイムアウトの境界をテストする。
- **完了**：PythonのAPIをHTTPから呼べ、Haskellの検索・回答経路からも使える。

### S3：Retrieval / Answer Evaluation

- 少量の固定された質問、関連チャンクID、参照回答を作る。
- Retrieval：Hit@K・Recall@K・MRRなどでDense/Sparse/Hybrid/Rerankを同条件比較。
- Answer：回答の正確性、Contextへの根拠忠実性、回答不能時の挙動を少量の評価データで比較。
- LLM-as-a-Judgeを使う場合、まず人が確認した小規模データとのズレを検証。判定を無条件の正解とはしない。
- **完了**：変更前後の指標と差分をコマンドで再現できる。UIのダッシュボードは不要。

### S4：業務文書らしい入力・日本語の改善

- 小さなPDF/FAQを追加し、テキスト抽出と失敗時の扱いを学ぶ。
- 日本語Embedding、全文検索方式、Chunkingを**評価を根拠に**比較・改善する。
- **完了**：実験条件と結果を残し、少なくとも一つの変更の良し悪しを説明できる。

### S5：LLMOpsと推論最適化

- 質問ごとの処理時間（検索・Rerank・LLM）、Token数、費用見積もり、失敗を記録する。
- Trace/ログ、プロンプトバージョン・モデル切替、簡単なキャッシュを試す。
- 外部LLM APIを1プロバイダだけ追加して品質・速度・コストを比較。料金や機密データの取り扱いに注意。
- **完了**：同じ質問群で品質・遅延・費用を並べて比較できる。

### S6：最小の運用・配置（選択）

- Docker、CI/CD、シークレット管理、基本的なAPI保護、必要最低限のAWS/GCP配置と削除手順。
- **完了**：外部環境にデプロイ、疎通確認、ログ確認、完全停止・後片付けができる。

## 今回は作らないもの（勝手に増やさない）

- 本格的な有人サポート管理（チケット、通知、権限階層、顧客管理、課金）。
- 大規模マルチテナント、SaaS管理画面、複雑なチャットUI。
- 自律的に外部ツールを実行するAIエージェント（→ [[Agent Worker]]）。
- 画像Embedding・画像検索（→ [[Visual Search Lab]]）。
- 汎用ワークフローエンジン、抽象的なプロバイダ共通フレームワーク、RAGScopeと同等の大規模実験プラットフォーム。
- 大量の文書コネクタ、Kubernetes、GPU推論基盤、高可用性クラスタ。必要になれば別途合意して段階追加する。

## 実装を始めるAIへの指示

- **READMEとこのノートを確認し、いま取り組むS1〜S6の一段だけ**を実装する。
- rag-labは学習済みの実装として活用するが、コードをコピーする際は動作とライセンスを確認。既存のRAGScope構想を自動的に移植しない。
- 仕様の境界（中核ユースケース・責務・対象外）を変えるときは利用者の了承を得てノートも更新する。
- ドキュメントを増やすことより、CLI/APIで再現できる動作と小さなテストを優先する。
