# AIアプリ開発・学習計画

> 2026-10-09 時点の学習方針。**市場の要求から逆算して、実装を通じて技術を学ぶためのノート**。採用応募や実務経験の代替を目的としない。
>
> **このREADMEと各アプリノートが、今後の実装で守るべきスコープの基準。** 新しいアイデアを思いついても、黙って仕様に加えない。

## 背景

Workbenchに記録したAI関連案件と、DrumRole・DMM・Insight Edge・Prefab・カイテク等の案件票を比較した。

共通していたのは、LLMを呼ぶだけでなく、**AI機能を通常のソフトウェアに組み込み、品質・性能・コスト・運用を考えて改善する力**への要求だった。特にDMMではLLMOps・評価・推論最適化、DrumRoleでは推論パイプライン・構造化出力・評価・画像Embeddingが目立った。

これは確認した案件群からの**定性的な学習要件の抽出**であり、市場全体の統計ではない。案件名や個別製品名は「学ぶ技術の手がかり」であって、全製品を実装する義務ではない。

## 目標

**AIアプリケーションを構築し、評価し、改善し、運用できるエンジニアになること。**

- 業務経験そのものは個人開発では取得できない。それ以外の知識、設計判断、実装力、テスト、計測、説明力をできるだけ獲得する。
- Haskellは本人が使いたい重要な学習目的。**やめず、アプリケーションの中核に積極的に使う。**
- AIモデル・推論ライブラリ・Python固有のWeb技術（FastAPI、Pydantic等）はPythonで直接実装し、Pythonの実践力も伸ばす。
- 「技術を少しずつ加える」より、**毎段階で実際に動く小さな完成品**を作る。
- RAGScopeの反省から、包括的な要求定義・ドメインモデリング・ADR・チケット分割を先に完成させようとしない。

## 実装の共通方針

1. **Haskell中心、Pythonを適材適所に。** Haskellは検索・評価・ドメイン・処理制御、Pythonはモデル依存の推論、PyTorch、FastAPI/Pydantic等を担当する。各アプリノートの境界を優先。
2. **Vertical slice優先。** 最初はCLIや最小APIでもよい。入力→処理→結果を実際に動かしてから拡張する。見栄えのよいUIは優先しない。
3. **設計は最小限。** 各アプリノートとREADMEを出発点とし、テスト・動作確認を省かない。実装が必要になるまで複雑な抽象化・共通基盤を作らない。
4. **測ってから改善。** 精度、品質、速度、コストは同条件で比較する。主観的な「良さそう」だけで完成としない。
5. **ローカルで完結する入口を維持。** 有料APIやクラウドは後段の学習。費用の発生するリソースは明示的に確認してから作る。
6. **アプリは原則独立。** 別アプリの機能を無断で吸収・統合しない。共通化は実際の重複と便益が確認できたときだけ判断する。

## 開発時のスコープ保護（人・AI共通）

- 着手前に**このREADMEと対象アプリノートの両方**を読む。対象のコードがあれば最新状態も確認する。
- 「目的」「中核ユースケース」「対象外」「完成条件」は**合意済みの仕様境界**。技術選択の細部は調整可能だが、境界を変える前に利用者へ変更案と理由を提示し、了承を得る。
- 他のAIや案件票を根拠に、勝手に機能・フレームワーク・サービス・UI・データモデルを追加しない。新しいアイデアは提案として扱い、未承認なら実装しない。
- 各段階は「触れる入力・再現手順・確認できる出力」をもって完了する。実装済みと予定を混同しない。
- 仕様変更に合意したら、**該当アプリノートを先にまたは同時に更新**する。READMEはアプリ間の境界や目標を変更するときに更新する。
- このフォルダは**仕様・学習方針のノート**であり、WorkBenchのTaskやProjectを代替する管理台帳ではない。タスク・進捗の重複管理はしない。

## 進める順番

1. rag-labでRetrieval Evaluationを作り、検索方式の比較を経験する。
2. [[AI Support Desk]] の最小完成版 → 回答評価 → LLMOps/コスト → 必要ならクラウド。
3. [[Agent Worker]] の最小完成版 → Tool Calling・承認 → 評価。
4. 興味が続く場合に [[Visual Search Lab]] を実施する。

**最初に全部作らない。** その時点の完成品を使い、次に学びたい技術に必要な一段だけ加える。
