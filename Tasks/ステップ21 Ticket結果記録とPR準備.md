# ステップ21：Ticket結果記録とPR準備

Step 20でRS-0015の完了条件を確認できたら、正本Ticketへ実施結果を記録し、残作業を`main`へ統合するPull Requestを作成できる状態までブランチを整理する。

## やること

- RS-0015の`結果`へ、実際に完成した内容と検証結果を簡潔に記録する
- `結果`には、実装した共通エラー・構造化ログ基盤、利用できる出力処理と実行context、実行した確認コマンドと結果を含める
- Step 18で確定したJSON encoding失敗の設計判断と、関連設計へ反映した内容を記録する
- 後続機能へ残す適用事項、既知の制約があれば記録する
- 最新の`main`と作業ブランチを取得し、commit履歴とファイル差分を確認する
- PRへ含める変更がRS-0015の残作業として説明できる範囲になっているか確認する
- 現在の継続ブランチには、RS-0015残実装より前から`.gitignore`の「非公開メモフォルダ追加」commitが存在するため、PR準備時に最新`main`との関係を再確認する
- 上記の既存commitがPRへ不要な差分として残る場合は、共有済み履歴を独断でrewriteせず、ユーザーと整理方法を決める
- Pull Requestテンプレートと現在のプロジェクト管理規約を確認し、PRタイトル・本文・確認結果を準備する

## Ticket statusの扱い

RAGScopeの現行プロジェクト管理規約では、実質的な変更を`done`にするには関連変更がデフォルトブランチへ反映されている必要がある。

そのため、作業ブランチ上で実装と`結果`記録が完了しただけでは、RS-0015を機械的に`status: done`へ変更しない。`main`への統合後、現在の正本と規約を再確認して最終状態を反映する。

## このステップでは勝手に行わないこと

- Pull Requestの作成
- Ready for reviewへの変更
- Pull Requestのmerge
- `main`への直接commit
- 共有済みbranchのrebase / force-push / commit amend
- branch削除

これらはそれぞれ独立した操作として、ユーザーから明示的に指示された場合だけ行う。

## 完了の目安

- RS-0015の`結果`に、実装内容・確認方法・設計判断・制約が現在の事実として記録されている
- 最新`main`との差分とbranch履歴を説明できる
- PRへ含めるべき変更と、無関係な既存差分を区別できている
- PR作成時に使用する確認結果と変更概要をまとめられる
- Ticketのstatusを早まって`done`にしていない
- ユーザーの明示指示があれば、次の操作としてPull Request作成へ進める状態になっている
