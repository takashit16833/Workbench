## クローズを止める主な点

### 1. 「共通エラーそのもの」の型がまだない

現在の`RAGScope.Error.Types`には、

```haskell
ErrorCategory
ErrorCode
ErrorMessage
FieldName
ErrorContext
ErrorValue
ErrorCause
```

まではあります。

ただし、5項目をまとめた例えば

```haskell
data AppError = AppError
  { category :: ErrorCategory
  , code :: ErrorCode
  , message :: ErrorMessage
  , context :: Maybe ErrorContext
  , cause :: Maybe ErrorCause
  }
```

のような**共通エラー本体がありません**。

Step 15の完了条件は「共通エラー設計の5項目をRAGScopeアプリケーション内部で表現できる」ですし、RS-0015も「設計に従った共通エラーのHaskell型」が条件です。

ここは明確に未完です。

### 2. 正常／失敗境界がまだない

Step 15では、

> 正常結果と予想可能な失敗を、型または明示的な結果で区別

することが要求されています。

現在のブランチには、そのための型や関数は追加されていません。最新commit `a7ca241` の変更も、`Types.hs`への個別型追加だけです。

最小なら、

```haskell
type AppResult a = Either AppError a
```

くらいでもよいと思います。

`ExceptT`まで入れる必要はありません。むしろそれはTask自身が再評価対象Ideaとして分離しています。

### 3. 現在のAPIだと、安全性の境界がかなり開いている

ここは少し重要です。

現在は、

```haskell
ErrorCode (..)
ErrorMessage (..)
FieldName (..)
ErrorContext (..)
ErrorValue (..)
```

と、ほぼすべてのconstructorを公開しています。

そのため機能コードから、

```haskell
ErrorCode "whatever.i.want"
```

と自由に作れます。

また、

```haskell
ErrorContext arbitraryMap
```

も直接作れます。

ところがStep 15自身は、

- エラーコードを機能処理から任意文字列として自由入力させない
    
- `context`へ何でも入れられる任意Mapを安易に公開しない
    

ことを要求しています。

したがって、**「どういうAPIから作らせるか」まではもう一段必要**です。

機能固有コードを今作る必要はありませんが、少なくとも共通層が無制限なconstructorをそのまま通常利用APIとして公開する状態は解消したいです。

### 4. `FieldName` に `Ord` がない

これは小さいですが、コード上の具体的な問題です。

```haskell
newtype FieldName
  = FieldName Text
  deriving (Eq, Show)
```

となっていますが、`ErrorContext`は、

```haskell
Map FieldName ErrorValue
```

です。

通常、

```haskell
Map.fromList
Map.singleton
Map.insert
```

などを使うには`Ord FieldName`が必要です。

logging側の`FieldName`は実際に、

```haskell
deriving (Eq, Ord, Show)
```

になっています。

なのでここは、

```haskell
deriving (Eq, Ord, Show)
```

が自然です。

### 5. `cause = SomeException` と正本の記述を合わせる必要がある

いま実装は、

```haskell
type ErrorCause = SomeException
```

です。

これは先ほど話していた方針としては、私もかなり良いと思います。

ただし現在の正本とTaskは、

> 元の例外や下位エラー

を`cause`に保持すると書いています。

`SomeException`では、任意の非例外な型付き下位エラーは保持できません。

ですのでここは、

**A. `cause`は技術的な例外だけを保持する、と設計を具体化する**

または

**B. 非例外の下位エラーも保持できる型にする**

のどちらかへ揃える必要があります。

私は今でも **A + `type ErrorCause = SomeException`** を推します。型付きドメインエラーは`AppError`へ変換して消費すればよく、全部`cause`へ残す必要はないと思います。

ただ、クローズ前には正本との表現を一致させたいです。

## もう1つ、名称・責務で直したいところ

現在の`ErrorValue`は、

```haskell
LogText
LogNumber
LogBool
LogArray
LogObject
```

となっていて、コメントも「構造化ログへ記録可能なJSON値」です。さらに`ErrorContext`のコメントが、

> イベント固有情報またはエラー固有の安全な補助情報

となっています。

これはlogging側の`LogValue` / `Payload`からかなり直接的に持ってきた形に見えます。実際、logging側にはほぼ同じ型があります。

Step 15では、

> logging側の`LogError`はログへ投影するための表現として区別する

ことが要求されています。

なのでError側で`LogText`という名前を使うより、

```haskell
ErrorText
ErrorNumber
ErrorBool
...
```

など、**Errorの世界の型として命名した方が責務がきれい**です。

また`ErrorContext`は「イベント固有情報」ではありません。そこはコメント修正でよいでしょう。

なお、「ErrorContextとLoggingの値型を共通化すべきか」はちゃんと別Ideaになっているので、今ここで共通化へ踏み込む必要はありません。
