# ステップ15：共通エラー型を完成させる

RS-0015のうち、RAGScopeアプリケーション内部で共通利用するエラー表現と、正常結果・失敗結果を明示的に扱う境界を完成させる。

着手時に、正本のRS-0015、`design/エラー設計.md`、現在の`RAGScope.Error.Types`と関連コードを確認する。

## やること

- 現在`ErrorCategory`だけの`RAGScope.Error.Types`を、共通エラーを表現できる形まで実装する
- `category`、`code`、`message`、`context`、`cause`について、エラー設計の意味を保てるHaskell型を決める
- `message`には外部へ公開してよい安全な説明だけを保持し、下位例外のメッセージをそのまま公開しない
- `cause`は元の例外や下位エラーを内部で保持するための情報として扱い、ログや利用者向け表現へ流さない
- `context`は安全な補助情報だけを表現できるようにし、通常の機能処理から何でも入れられる任意Mapを安易に公開しない
- エラーコードを機能処理から任意文字列として自由入力させないための境界を考慮する
- 正常結果と予想可能な失敗を、型または明示的な結果で区別して呼び出し元へ返せるようにする
- logging側の`LogError`はログへ投影するための表現として区別し、アプリケーション内部の共通エラーそのものと混同しない
- 必要な自動テストを追加し、実装した型と失敗境界の基本的な振る舞いを確認する
- 実装によって現在設計を具体化・変更した場合だけ、正本の`エラー設計.md`へ同じ変更で反映する

## このステップでは決めないこと

- 文書処理など各機能固有のエラーコードや失敗条件
- HTTPレスポンスやCLI終了コードの具体的な表現
- retry・timeoutの方針
- JSON Schema・fixtureの網羅的な適合テスト
- 本番Loggerの初期化
- JSON encoding失敗を独立した失敗経路として扱うかの最終判断
- 将来必要になるかもしれない抽象やtypeclassの先行導入

## 完了の目安

- 共通エラー設計の5項目をRAGScopeアプリケーション内部で表現できる
- 正常結果と予想可能な失敗を明示的に区別して扱える
- `cause`と安全に公開できる情報の境界が型・API上で曖昧になっていない
- 機能固有のエラーコードやcontextを共通層へ先回りして作り込んでいない
- logging実装との責務分離を保っている
- 追加・変更したコードのテストとビルドが成功する
