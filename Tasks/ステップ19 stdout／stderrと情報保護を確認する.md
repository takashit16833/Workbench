# ステップ19：stdout／stderrと情報保護を確認する

RS-0015の出力境界と情報保護について、個々の部品が存在するだけでなく、実際の利用境界でも契約を守れることを確認する。

現在のstderr Backendは構造化ログを1イベント1行でstderrへ出力するが、executableはまだ最小のプレースホルダーであり、stdoutとstderrの分離を代表実行として確認する経路は未完成。

## やること

- 本格的なCLI機能を先行実装せず、RS-0015の完了条件を確認できる最小の統合経路またはテスト方法を決める
- 利用者へ返す正常結果がstdoutへ、構造化ログがstderrへ出力され、両者が混在しないことを確認する
- stderrへ出力するログが1イベント1行のJSONになっていることを確認する
- 通常の機能処理が具体的なstderr処理へ直接依存せず、Logger / Sinkの境界を通して出力先を差し替えられる状態を保つ
- 文書本文、秘密情報、認証情報など、設計で記録対象外とした値を不用意にpayloadやerror contextへ流せないか確認する
- `cause`、元の例外メッセージ、スタックトレースが利用者向け出力や構造化ログへ混入しないことを確認する
- アプリケーション処理の失敗とログ出力失敗が重なった場合に、元の処理失敗を上書きせず、失敗した同じSinkへ再帰的にログを書かないことを確認する
- 不足する場合は、代表的な自動テストまたは最小の実行確認を追加する

## このステップではやらないこと

- 本格的なCLIコマンドの実装
- 文書処理など各機能固有のログ観測点の実装
- CloudWatch送信、分散tracing、性能集計
- ログへ何でも入れられる汎用payload / context APIの追加
- 情報保護のために元データを安易に伏せ字加工して記録すること。安全性を確認できない値は記録しない

## 完了の目安

- stdoutとstderrの役割分離をテストまたは代表実行で確認できる
- 構造化ログがstderrへ1イベント1行で出力される
- 記録禁止情報と`cause`がログ・利用者向け表現へ漏れない境界を確認できる
- Sinkを差し替えられる責務分離を維持している
- ログ出力失敗が元の処理失敗を上書きせず、再帰ログも起こさない
- 必要な確認結果が自動テストまたは再現可能な実行手順として残っている
