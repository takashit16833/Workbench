# BR-0006 アプリケーション実行を機能処理結果とログ出力結果から合成する

> [!warning] 非正本
> このIdeaは現在仕様そのものではありません。正本と矛盾する場合は正本を優先します。

## 背景

機能処理の失敗である`AppError`と、必須ログ出力の失敗である`LoggingFailure`は独立して発生する。

`LoggingFailure`を`AppError`へ変換すると両者を区別できず、機能処理とログ出力が同時に失敗した場合に元の`AppError`を保持する要求も表現しにくい。そのため、1つの観測境界で起きた事実と、アプリケーションとしての成功・失敗の意味を分けて表現する。

## 決定

- 機能処理結果とログ出力結果を独立した事実として`ExecutionOutcome`に保持する。
- `ExecutionOutcome`を`interpretOutcome`で`Either ExecutionFailure a`へ解釈する。
- アプリケーション全体の線形な実行は`AppAction = ExceptT ExecutionFailure IO`で合成する。
- `FeatureAction = ExceptT AppError IO`という共通型エイリアスは設けない。
- 個々の機能処理では、純粋値、`Either`、`IO (Either AppError a)`、`ExceptT AppError IO a`など、その処理に自然な型を使用する。
- `ExecutionResult`は設けず、`Either ExecutionFailure a`を最終的な結果表現として使用する。
- 機能処理結果と必須ログ出力結果を合成して`AppAction`へ持ち上げる共通境界として`observe`を設ける。
- 既存の`AppResult = ExceptT AppError IO`は共通アプリケーション実行型としての役割を失うため削除する。

## 事実と意味を分ける

```haskell
data ExecutionOutcome a = ExecutionOutcome
  { featureResult :: Either AppError a
  , loggingResult :: Either LoggingFailure ()
  }

data ExecutionFailure
  = FeatureFailed AppError
  | LoggingFailedAfterSuccess LoggingFailure
  | FeatureFailedWithLoggingFailure AppError LoggingFailure

interpretOutcome
  :: ExecutionOutcome a
  -> Either ExecutionFailure a
```

対応は次のとおり。

```text
Right a       × Right ()             -> Right a
Right _       × Left loggingFailure  -> Left (LoggingFailedAfterSuccess loggingFailure)
Left appError × Right ()             -> Left (FeatureFailed appError)
Left appError × Left loggingFailure  -> Left (FeatureFailedWithLoggingFailure appError loggingFailure)
```

`ExecutionOutcome`は「何が起きたか」という直積の事実を表す。`ExecutionFailure`は、その組み合わせをアプリケーション実行上の失敗の意味へ変換した直和を表す。

機能処理が成功しても必須ログ出力が失敗した場合はアプリケーション全体を失敗とするため、成功値`a`は失敗値へ保持しない。機能処理とログ出力が両方失敗した場合は、元の`AppError`を主たる失敗として保持しつつ`LoggingFailure`も失わない。

## AppAction

```haskell
type AppAction a =
  ExceptT ExecutionFailure IO a
```

`AppAction`は、機能処理だけではなく、その結果に対する必須ログ出力まで成立したアプリケーション実行単位を表す。

```text
機能処理 + 必須ログ
  -> AppAction
  >>= 次のAppAction
```

## FeatureActionを設けない

`ExceptT AppError IO a`自体の利用は禁止しない。複数のIO処理を`AppError`で短絡しながら組み立てる局所的な処理では利用できる。

ただし、RAGScopeの機能処理には純粋な変換・検証とIO処理の両方があり、すべてを`ExceptT AppError IO`へ統一する共通責務はない。`FeatureAction`という名前を設けることで、純粋処理まで共通モナドへ巻き込む設計圧力を作らない。

`observe`へ入る時点では、必要に応じて機能処理結果を`IO (Either AppError a)`へ変換し、観測境界の共通形として扱う。

## observe

`observe`は次を1つの境界として扱う。

```text
機能処理
  -> Either AppError a
  + 必須ログ出力
  -> Either LoggingFailure ()
  -> ExecutionOutcome
  -> interpretOutcome
  -> AppAction
```

ログ出力が失敗した場合は、その失敗を同じログ経路へ再帰的に書き込まず、`ExecutionFailure`として呼び出し側へ返す。

`observe`がLoggerや機能固有イベントをどの型で受け取るかは、RS-0015の実装で既存のLogging公開境界との依存方向を確認して確定する。

## ExecutionResultを設けない

専用の`ExecutionResult`は`Either ExecutionFailure a`と同じ成功・失敗を重複して表現するため採用しない。

`runExceptT AppAction`の結果をそのまま`Either ExecutionFailure a`として扱う。

## 関連する既存Idea

- `BR-0003 ExceptT AppError IOを共通失敗チャネルにする`: `ExceptT AppError IO`は必要な局所IO処理で利用できるが、アプリケーション全体の共通失敗チャネルにはしない。共通実行は`AppAction`へ置き換える。
- `BR-0005 アプリケーション失敗とログ出力失敗が重なった場合の優先関係`: 元の`AppError`を失わず、`LoggingFailure`も別の失敗情報として保持する判断を具体化する。
